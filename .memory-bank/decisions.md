# Ключевые решения (ADR) — ChatCenter

## ADR — ВК переехал на vk.ru: детект новых сообщений по списку чатов (2026-07-23, v1.2.109–115)

**Статус**: ✅ Действующее (ожидает финальной визуальной проверки пользователем на живом ВК).

### Контекст / проблема
ВК перевёл веб-версию с `vk.com` на `vk.ru`. Из-за этого сломались наши уведомления ВК (шёл только звук самого ВК):
1. Всё определение «это ВК?» сверяло только `vk.com` → `detectMessengerType('vk.ru')` возвращал `unknown` → хук ВК и наблюдатели не запускались (**исправлено в v1.2.109**: добавлено распознавание `vk.ru` рядом с `vk.com` в 4 точках — [messengerConfigs.js](../src/utils/messengerConfigs.js), [monitor.preload.cjs](../main/preloads/monitor.preload.cjs), [unreadCounters.js](../main/preloads/utils/unreadCounters.js), [navigateToChat.js](../src/utils/navigateToChat.js); тест `messengerConfigs.vitest.js`).
2. На новом vk.ru **нет всплывашки «Новое сообщение»** (старый toast-наблюдатель `_scanVkToasts` даёт 0), а большой запасной впрыск `vkExecFallback` блокируется страницей (`VK-EXEC inject failed` — это ожидаемо, не поломка).

### Решение
Ловить новые сообщения **по списку чатов** внутри основного preload-хука `vk.hook.js` (он на vk.ru грузится — подтверждено логом). Наблюдатель `MutationObserver` (тротлинг 500 мс) сканирует строки списка:
- строки чатов — `[class*="ConvoListItem" i]` (по дампу диагностики: реальный класс `ConvoListItem ConvoListItem--click`);
- непрочитанность — класс строки с «unread» ИЛИ вложенный `[class*="unread"/"Counter"/"Badge"]` (в дампе — `DIV.UnreadCounter`);
- имя — `[class*="ChannelTitle"/"title"/"peer"/"name"]`; превью — `[class*="PostPreview"/"preview"]`; аватар — `img[src^=http]`;
- мусор ИСКЛЮЧАЕТСЯ: скрытый для скринридера `vkuiVisuallyHidden` («36 минут назад»), дата `*__date*` («· 36м»), счётчик `UnreadCounter`;
- эмит `__CC_NOTIF__ {src:'vk-list'}` → дальше общая логика мьюта/звука (Правило 2 CLAUDE.md).

**Базовая линия**: первый непустой замер запоминается без отправки; шлём только НОВЫЕ отпечатки «имя|текст». Дедуп внутри прохода.

### Ключевые решения по поведению
- **Каналы ВК (broadcast) УВЕДОМЛЯЕМ** — по явному решению пользователя (2026-07-23): «сообщения надо все». Фильтр каналов не добавляли (можно добавить одной строкой, если передумает).
- **Заголовок вкладки НЕ используем** как сигнал: у vk.ru в заголовке нет счётчика непрочитанных («Мессенджер» без «(N)»).
- Старый toast-наблюдатель оставлен (нетронут) — на случай старого vk.com / edge-страниц.

### Ограничения (честно)
- Ловятся только ВИДИМЫЕ строки списка (vk.ru, вероятно, виртуализирует длинный список) — чат вне видимости можно пропустить.
- Мьют КОНКРЕТНОГО чата в самом ВК хук не видит (знает только мьют на уровне приложения).

### Как откатить / выключить
Убрать блок `_scanVkList`/`_vkListObserver` в `vk.hook.js` (детект отключится, останется старый toast-путь) или `git revert` коммитов v1.2.112–115.

**Связано**: [[features]] (v1.2.109–115), [[webview-injection]] (грабли детекта), [[messengers]] (vk.ru).

## ADR — Почему родные уведомления и ServiceWorker мессенджеров намеренно ВЫКЛЮЧЕНЫ (25 июня 2026)

**Статус**: ✅ Действующее решение (с ранних версий; зафиксировано 25 июня 2026 после расследования v1.2.20-1.2.22).

### Что именно выключено
В [`main/utils/sessionSetup.js`](../main/utils/sessionSetup.js) для **каждого** мессенджера (webview-сессии) стоят **два замка**:
1. **Запрет разрешения `notifications`** ([sessionSetup.js:24-31](../main/utils/sessionSetup.js#L24)): `setPermissionRequestHandler` и `setPermissionCheckHandler` возвращают `false` для `notifications`. → сайт мессенджера НЕ может показать ни одного системного уведомления.
2. **Убийство ServiceWorker** ([sessionSetup.js:32-42](../main/utils/sessionSetup.js#L32)): при старте сессии чистится SW storage, и по событию `running-status-changed` (SW пытается запуститься) — снова чистим. → SW не доживает до регистрации, в логе `AbortError: Operation has been aborted`.

### Что за «родные уведомления»
Это **системные всплывашки Windows**, которые делает **сам сайт** мессенджера (через `Notification` API / `ServiceWorkerRegistration.showNotification`). Они в стиле мессенджера (иконка + имя «Макс»/«WhatsApp»), **без наших кнопок, стиля и функций**.

### Почему выключили (полная причина)
У ChatCenter **своя система уведомлений**:
- Перехват новых сообщений через наблюдатель в `monitor.preload` (DOM + хук `Notification`) → событие `__CC_NOTIF__`.
- Показ **своей** плашки/ленты (ribbon, `main/notification.*`) с нашими кнопками «Перейти»/«Прочитано», стэкингом, закреплением, фирменным стилем.

Если оставить родные уведомления включёнными — будет **ДВА уведомления** на каждое сообщение (наше + системная серая всплывашка мессенджера) и **потеря контроля** над стилем/функциями. Поэтому родные намеренно глушим, а показываем только своё.

### Важное следствие (чтобы будущие сессии не копали впустую)
- `AbortError: Failed to register a ServiceWorker … Operation has been aborted` в логе — это **НЕ баг и НЕ проблема `<webview>`**. Это **результат нашего намеренного убийства SW**. Ожидаемо.
- Поэтому затея «перейти на WebContentsView, чтобы оживить SW-уведомления» **НЕ решает задачу**: SW мёртв не из-за webview, а из-за наших замков. **Доказано 25 июня** (v1.2.22, Вариант A): в ОТДЕЛЬНОМ нормальном окне Electron (та же сессия) SW падает с той же ошибкой.

### Когда пересматривать
Только если решим **отказаться от своей системы уведомлений** в пользу родных (большое архитектурное решение: риск двойных уведомлений + потеря наших функций). Тогда: снять оба замка в `sessionSetup.js` + перехватывать/подавлять родные. **Пока — НЕ трогаем.**

**Связано**: [mistakes/electron-core.md](mistakes/electron-core.md) (крах WebContentsView на Win11), [webcontentsview-migration-plan.md](webcontentsview-migration-plan.md) (Вариант A + плюсы/минусы миграции).

## ADR — Откат миграции `<webview>` → WebContentsView (20 мая 2026, v0.91.0)

**Статус**: ✅ Принято, откат выполнен

**Контекст**: Electron официально пишет «we recommend to not use the webview tag, consider WebContentsView». Мы попытались мигрировать (16 версий v0.89.41-v0.90.2).

**Что обнаружено**: на Windows 11 + Electron 41 child WebContentsView крашит native main процесс при `addChildView()` + `loadURL`. Подтверждено в Electron GitHub issues:
- [#44934](https://github.com/electron/electron/issues/44934) — App crashes when adding child view to WebContentsView on Windows 11 (closed/not planned)
- [#45367](https://github.com/electron/electron/issues/45367) — addChildView(WebContentsView) не рендерит (closed/not planned)
- [#44897](https://github.com/electron/electron/issues/44897) — preload не загружается в child WebContentsView
- [#47247](https://github.com/electron/electron/issues/47247) — webContents в WebContentsView крашит Electron

**Решение**: **полный откат** к BrowserWindow + `<webview>` — production-tested архитектура работает в проекте с v0.1.0.

**Условия пересмотра**: проверять каждые 6-12 месяцев. Повторная миграция возможна только если:
1. Issue #44934 или #45367 закрыт как «fixed» в Electron release notes
2. Есть rollback план + изолированный production-тест
3. WebContentsView работает на Windows 11 в нашей конфигурации (multi-child views)

**Альтернативы для будущего**:
- Дождаться фикса Electron (не на нашей стороне)
- Полная смена фреймворка (Tauri, Wails) — отдельная задача
- iframe вместо `<webview>` — отвергнут (Telegram/WhatsApp CSP)

**Полный урок и 7 правил для будущих миграций** — в [`mistakes/electron-core.md`](.memory-bank/mistakes/electron-core.md) → секция «УРОК v0.89.41-v0.91.0».

## ADR — Notification BrowserWindow: итоги серии багов v0.89.15-v0.89.23 (18 мая 2026)

**Статус**: ✅ Принято и реализовано

**Контекст**: за 3 дня (15-18 мая) серия пользовательских жалоб привела к 9 версиям (v0.89.15-v0.89.23) и 4 новым ловушкам (#20-#23) для одного компонента — **notification BrowserWindow** (Messenger Ribbon в `main/notification.*` + `main/handlers/notifHandlers.js` + `main/handlers/notificationManager.js`).

### Какие баги случились и **почему** решили именно так

**1. Ghost hit-test region после `.hide()` на Win11 (v0.89.18, ловушка #20)**

Корневая причина: `transparent: true` + `frame: false` BrowserWindow на Win11 оставляет невидимый hit-test регион после `.hide()` (известная Electron issue #15947).

**Альтернативы** (отклонены):
- ❌ Перейти на non-transparent окно — потеряем кастомный дизайн ribbon
- ❌ Использовать native Notification API целиком — у нас кастомные кнопки «Перейти / Прочитано» / стэкинг / закрепление, нативный API такого не даёт
- ❌ Игнорировать (закрыть глаза) — клики «глотались», UX страдал

**Принятое решение**: helper `safeHideTransparentWindow()` который перед `.hide()` уводит окно за экран (`-30000`) в размер 1×1. Скрытое окно за пределами всех мониторов размером 1px физически не может ловить клики.

**Почему так**: 
- Сохраняет существующий дизайн
- Не требует архитектурного переписывания
- Гарантия на уровне Windows compositor (окно вне всех мониторов)
- 5 точек применения (notif/dock/pin) через единый helper — DRY

---

**2. `setIgnoreMouseEvents(true)` ломал клики (v0.89.22, ловушка #21)**

Корневая причина: в v0.89.18 я добавил `setIgnoreMouseEvents(true)` в helper как «тройную защиту». Но это нарушило **ловушку #27 (v0.71.7)**: ломает `-webkit-app-region: drag` у dock/pin окон. У 5 точек `.show()` не было парного `restoreMouseEvents(false)` → state `true` оставался → клики проходили сквозь видимое окно.

**Альтернативы** (отклонены):
- ❌ Добавить `restoreMouseEvents` во все 5 точек show — fragile, легко забыть в будущем
- ❌ Оставить `setIgnoreMouseEvents` + написать тесты — не закрывает root cause

**Принятое решение**: УДАЛИТЬ `setIgnoreMouseEvents` целиком из helper. Защита от ghost hit-test полностью покрывается через `setBounds(offscreen 1×1) + hide()` — это сам по себе достаточный механизм.

**Почему так**:
- Меньше кода = меньше точек отказа
- Соблюдает ловушку #27 нашего проекта
- Соответствует Electron docs «state persists until explicitly changed» — мы избегаем самого state-management
- Регрессионный тест в pre-commit (`.cjs`) — физически запрещает вернуть `setIgnoreMouseEvents(true)`

---

**3. «Пустая полоса»: slideIn animation + offsetHeight (v0.89.23, ловушка #22)**

Корневая причина: CSS `slideIn` animation 300ms сдвигает element с `translateX(380px)` до `translateX(0)`. `offsetHeight` ignores transform (MDN). Поэтому `calcHeight()` сразу видит финальную height нового element и main process расширяет окно — но element ещё за правым краем визуально → пустая полоса 60-300ms.

**Альтернативы** (отклонены):
- ❌ Убрать slideIn animation целиком — потеря UX-плавности
- ❌ Использовать `getBoundingClientRect()` (учитывает transform) — добавляет ms к перерасчёту, не решает race (element только что добавлен, размер ещё формируется)
- ❌ Hardcode delay 300ms на main — magic number, ломается если CSS animation поменяют
- ❌ Использовать transition height вместо transform translate — более тяжёлая правка, ломает дизайн slideIn

**Принятое решение**: `slideInDone` флаг на element. `calcHeight()` пропускает elements где `slideInDone === 'false'`. После `animationend` event → ставим `'true'` + новый `reportHeight()`. Страховка setTimeout 600ms если `animationend` не сработает.

**Почему так**:
- Использует **event-driven** механизм (animationend) — авторитативное завершение, не угадывание времени
- Страховка через timeout — защита от edge cases (cascade delay, animation overrides)
- Минимальная инвазивность — добавил один dataset attribute + listener, ничего не сломал в существующей логике

---

**4. IPC race `raw=0 items=1` (v0.89.23, ловушка #23)**

Корневая причина: `notif:resize` идёт через async IPC. `reportHeight` использует `setTimeout(fn, 60)` для коалесcинга. Если renderer прислал поздний `resize(0)` от прошлого dismiss ПОСЛЕ того как main process получил новое `notif:show` → main скрывает окно несмотря на наличие items.

**Альтернативы** (отклонены):
- ❌ Включить порядковые номера в IPC сообщения — большая правка, нужны на всех endpoints
- ❌ Убрать setTimeout 60ms — может вызвать множественные resize за короткое время (caterpillar effect при rapid additions)
- ❌ Делать reportHeight synchronously — может вернуть stale layout (нужен flush)

**Принятое решение**: в main process проверять `if (raw=0 && itemsCount > 0) return`. Игнорировать stale `resize(0)` если main УЖЕ знает что есть item. Следующий reportHeight от renderer пришлёт правильное значение.

**Почему так**:
- Использует **авторитативное состояние** main process (`notifItems[]`) — единственная Source of Truth
- Не требует синхронизации между renderer/main — main решает сам по своему state
- Простая проверка, понятная любому коду reader

---

### Общие принципы из всей серии (правила на будущее)

🟢 **Принцип #1**: для CSS-анимируемых свойств — `getComputedStyle()`, не `el.style`. Inline style не отражает CSS keyframes (MDN).

🟢 **Принцип #2**: для определения visual position — `getBoundingClientRect()`, не `offsetHeight`. offsetHeight ignores transform.

🟢 **Принцип #3**: для transparent BrowserWindow на Win11 — `setBounds(offscreen 1×1) + hide()`, БЕЗ `setIgnoreMouseEvents` (ломает app-region drag, ловушка #27).

🟢 **Принцип #4**: при IPC + setTimeout-coalescing — main process не доверяет slепо последнему received значению. Проверять консистентность с авторитативным state.

🟢 **Принцип #5**: при diagnostic logging — читать MDN для каждого свойства которое логируешь. Inline style ≠ computed style ≠ visual state.

### Регрессионная защита (всегда в pre-commit)

`src/__tests__/transparentWindowGuard.test.cjs` падает локально если:
- сырой `notifWin.hide()` без safeHide
- сырой `dockState.win.hide()` без safeHide
- `setIgnoreMouseEvents(true)` вернётся в helper
- safeHide не использует setBounds или offscreen координаты

Это гарантирует что **ловушки #20 и #21 не повторятся** — физически невозможно сделать коммит с регрессией.

### Серия закрыта — что осталось

12 ловушек документировано в [`mistakes/notifications-ribbon.md`](mistakes/notifications-ribbon.md):
- #1-#19: исторические (v0.89.6 → v0.89.18)
- #20: ghost hit-test (v0.89.18)
- #21: setIgnoreMouseEvents ломает клики (v0.89.22)
- #22: пустая полоса от slideIn (v0.89.23)
- #23: IPC race stale resize=0 (v0.89.23)

Diagnostic logging (v0.89.20-21-23) пока **остаётся в коде** — на случай если новый баг проявится. Удалим в отдельном patch'е если 1-2 недели не будет повторений.

## ADR-NEW — `tg-media/` как LRU-кеш под управлением приложения (15 мая 2026, v0.89.17)

**Статус**: ✅ Принято и реализовано

**Контекст**: В v0.89.15 решено НЕ играть медиа из TDLib-папок (нестабильны: `temp/` чистится, `optimizeStorage` удаляет даже completed). Скачанные файлы копируются в `userData/tg-media/<fileId>_<size>.<ext>` через `stabilizeForPlayback()`. Это решило проблему стабильности URL, но создало новую: папка растёт без ограничений (TDLib `optimizeStorage` нашу папку не трогает).

**Решение**: реализовать LRU-кеш для `tg-media/` — точный аналог TDLib `optimizeStorage`:
- **Лимит размера** 1 ГБ
- **TTL** 7 дней
- **Immunity** 5 минут (mtime обновляется при чтении через cc-media handler)
- **wipeAll** для ручной кнопки «Очистить кеш»

**Альтернативы** (отклонены):
- Использовать `readFilePart` TDLib API для streaming — сложно (IPC overhead, backpressure, edge cases). У нас есть локальный диск — копия проще.
- Симлинки `tg-media/file → tdlib-sessions/file` — на Windows требуют админ прав.
- Mirror TDLib cleanup: после `optimizeStorage` сканировать `tg-media/` и удалять файлы, чьи исходники в `tdlib-sessions/` пропали — нужна привязка `tg-media name → tdlib file`. Сложнее чем независимый LRU.
- Префикс `accountId_` в именах для per-account очистки — LRU саморегулируется через TTL, префиксы не нужны (TODO-3 в `code-todo.md`).

**Почему LRU+TTL правильный выбор**:
1. **Стандарт индустрии**: Telegram Desktop, Telegram Web K, WhatsApp, Signal — все используют LRU+TTL
2. **TDLib официально документирует** алгоритм в [optimizeStorage](https://core.telegram.org/tdlib/getting-started#storage-optimization)
3. **Простой и предсказуемый**: пользователь знает что 1 ГБ — лимит, 7 дней — TTL
4. **Безопасный**: immunity 5 минут защищает играющие сейчас файлы

**Реализация**: [`main/native/backends/tgMediaCleanup.js`](tgMediaCleanup.js). 4 точки интеграции: `getCleanupStats`, `media.cleanup`, `tdlibStartup` (фон-чистка при init), `ccMediaProtocol` (touch mtime при read).

**Last verified**: 15 мая 2026, v0.89.17, 20 тестов в `tgMediaCleanup.vitest.js`.

## ADR-077 — Ранний выход повторяющейся проверки обязан ставить будильник; поздний успех загрузки засчитываем (2026-09-24, v1.2.498)

**Контекст.** Ревью v1.2.497 тремя проверяющими нашло две дыры: (1) пульс интернета умирал, если нажать
«Проверить связь» раньше защитного промежутка — внеочередная проверка гасила будильник, а сама проверка
выходила без нового; (2) введённый предел ожидания выбрасывал страницу, догрузившуюся в первые 2 секунды после
него, и подменял код настоящей беды своим техническим кодом.

**Решение 1.** КАЖДЫЙ ранний выход из `check()` в `main/handlers/netPulseHandlers.js` обязан вызвать
`schedule()`. Альтернатива «не гасить таймер во внеочередной проверке» отвергнута: тогда внеочередная проверка
конкурировала бы с плановой и они шли бы вдвоём.

**Решение 2.** Запись, ушедшая в ожидание ПО ПРЕДЕЛУ (поле `timedOut`), в `shouldAcceptLoaded` обходит окно
«эха страницы-ошибки»: отказа загрузки не было, значит и страницы-ошибки быть не может. Прошлую зависшую
загрузку глушим `el.stop()` ПЕРЕД новой попыткой, а не в момент предела — иначе на медленном канале мы сами
убиваем почти готовую страницу.

**Решение 3.** Предел растёт по попыткам (45 → 90 → 135 → 180 секунд, `attemptTimeoutFor`). Постоянные 45 секунд
на слабой связи давали петлю «не успел → бросили → начали заново».

**Решение 4.** Код-причина беды не подменяется техническим кодом предела: `code` остаётся прежним, факт ожидания
едет отдельным полем. Правило на будущее: вводя новый код-причину, проверь, кто ещё смотрит на старый.

**Последствия.** Механизм возврата сети больше не выключается нажатием кнопки; недописанное сообщение не теряется
из-за лишней перезагрузки; на медленной связи страница успевает открыться. Риск: если страница честно грузится
дольше 3 минут, её всё равно бросят — по журналам проекта таких случаев нет (обычная загрузка 5–30 секунд).

## ADR-076 — Предел ожидания попытки и «нелечимые» коды прокси (2026-09-24, v1.2.497)

**Контекст.** Механизм переподключения помечает запись фазой «идёт попытка» и на это время закрывает ей все
обычные выходы (будильник, возврат интернета, признание успешной загрузки) — это защита от эха страницы-ошибки
(v1.2.453). Выходом был только ответ `loadURL`. На мёртвом посреднике (VPN/прокси) ответа можно не дождаться.

**Решение 1.** Ввести ПРЕДЕЛ ОЖИДАНИЯ попытки `ATTEMPT_TIMEOUT_MS = 45000` (гонка с таймером внутри
`shared/reconnectAttempt.js`), по истечении — запись возвращается в «ждём». Альтернатива «сторож снаружи, в хуке»
отвергнута: она требует нового хранилища в `useWebviewReconnect.js`, где действует страж «useRef = 2».

**Решение 2.** Долгая пауза (5 минут после 10 неудач) включается при `netOnline !== false`, а не строго `=== true`.
При выключенном пульсе вердикт `null`, и прежнее правило давало вечные перезагрузки раз в минуту. При `false`
попытка вообще не доходит до загрузки (ветка `net-down`), поэтому там лестница оставлена прежней.

**Решение 3.** В повторы входят ТОЛЬКО те беды посредника, которые лечатся временем: -111, -120, -121, -130.
Требующие человека (-115 способ входа, -127 логин, -131 испорченная настройка, -136 сертификат) — не входят
никогда: повтор их не вылечит, а страница будет дёргаться впустую. Закреплено тестом-ловушкой.

**Последствия.** Зависшая попытка теперь всегда заканчивается; журнал получил строки о начале попытки и о
превышении предела. Риск: если у мессенджера честная загрузка длится дольше 45 с, попытка прервётся и начнётся
заново — по журналам проекта таких случаев нет (5–30 с), но при появлении жалоб число поднимать здесь.

## ADR-075 — Об интернете судим по СВОЕМУ пульсу, а не по событиям online/offline; он командует только переходом (2026-09-22, v1.2.491)

**Контекст**: за два настоящих обрыва стандартные события `online/offline` не пришли ни разу (0 строк за журнал). По документации Electron
они надёжны только когда «все запросы гарантированно провалятся» (провод выдернут); «true» ничего не значит. Из-за этого после возврата
интернета веб-страницы ждали до 60 с или кнопку, а TDLib узнавал о сети на 2 минуты позже.

**Решение**: главный процесс сам щупает интернет (`net.fetch` к трём служебным адресам, 60 с / 15 с при беде, сразу после сна и по
просьбе окна) и сообщает окну и TDLib ТОЛЬКО ПЕРЕХОД. В окне вердикт превращается в синтетическое событие `online`/`offline` —
существующие слушатели оживают без переделки (одна точка правды, три потребителя). TDLib получает `setNetworkType(other)` — по его
документации это обязательный вызов при смене сети. Открытые страницы под присмотром проб: два провала подряд → при живом пульсе
перезагрузка по лестнице, при мёртвом — экран без перезагрузки; перед перезагрузкой страницу СПРАШИВАЮТ, не ожила ли сама.

**Почему так**: пульс отвечает на вопрос «интернет есть?», а обещание `loadURL` — «этот сайт открылся?». Их нельзя смешивать: 21.09 два
сайта были недоступны 3,5 часа при живом интернете. Поэтому долгая пауза (5 мин) включается только при пульсе `true`.

**Отвергнуто**: (а) опрос из окна приложения — нет пробуждения компьютера и команды TDLib; (б) слать пульс на каждую проверку —
лестница дёргалась бы каждую минуту; (в) `networkTypeNone` на «пропал» — сами отключили бы TDLib по ложному пульсу.

**Связано**: `reconnect-plan.md` раздел 4e; `shared/netPulsePlan.js`, `shared/openPageWatch.js`, `shared/reconnectAttempt.js`;
грабля «online/offline — не источник правды» в `mistakes/electron-core.md`.

## ADR-074 — Предел «вечных» уведомлений: число — внешний потолок, реальная высота — внутренний; место под новую — постоянное (2026-09-19, v1.2.488–489)

**Контекст**: настройка «не закрывать уведомления сами» (`dismissMs=0`) копит карточки. Предел по ЧИСЛУ (`MAX_PERSISTENT_ITEMS`,
v1.2.339/340) считает карточку в 180 точек; раскрытая — 130…420 → 6 карточек = до 2516 точек при экране 796 (журнал 19.09.2026).

**Решение**: два предела. Внешний — прежнее число (его требует страж `notificationWindowBounds.test.cjs`). Внутренний —
перед добавлением новой «вечной» карточки мерить ФАКТИЧЕСКИЕ высоты живых карточек (закрывающиеся не считать) и снимать
старейшие, пока `стопка + резерв ≤ availHeight − 20` (`shouldTrimOldest`, [notification-limits.js](../main/notification-limits.js)).
Минимум одна карточка остаётся всегда. Гаснущие сами не затронуты.

**Резерв под новую — ПОСТОЯННЫЕ 160 точек**, а не «высота свежей» и не медиана. Почему: высоту новой карточки до отрисовки
знать нельзя. Переоценка → снимаем лишнюю карточку НАВСЕГДА. Недооценка → стопка разово вылезет на разницу, main зажмёт окно
до экрана, следующее уведомление снимет лишнее — САМОИСПРАВЛЯЕТСЯ. Медиана отвергнута числами: `[200,200,400]`/796 даёт 2
снятия вместо 1 (как и «по свежей»). Асимметрия цен ошибок → выбираем недооценку.

**Отвергнуто**: (а) делитель 180→420 в числе — снова «средняя карточка», при коротких текстах режет вчетверо больше нужного;
(б) снимать ПОСЛЕ добавления по факту — карточка мигала бы (появилась и тут же ушла старая).

**Связано**: дело [notif-window-input-loss-case.md](./notif-window-input-loss-case.md) (это НЕ лечение обрыва мыши — устранение
усилителя); грабля «линейка обязана пропускать закрывающиеся» в `mistakes/notifications-ribbon.md`; тесты `notifPersistentTrim.vitest.js`.

## ADR-073 — Диагностический снимок: опознавание мессенджера только общим определителем, объём ограничен ПО ПОСТРОЕНИЮ, при переполнении — сводка, а не обрывок (2026-09-18, v1.2.484)

**Проблема (две беды в одном инструменте)**. Подробный снимок страницы ВК `runVkFullProbe`:
1. **не собирался НИ РАЗУ** — условие запуска было «мессенджер называется `vk` ИЛИ адрес содержит
   `vk.com`», а ВК переехал на `vk.ru` (v1.2.109, тогда починили четыре других места) и мессенджер у
   пользователя пользовательский (`custom_…`). Доказательство: записей `vkFull` в `chatcenter.log`
   **0 за всю историю файла**;
2. оживлять «как есть» было нельзя — строки с меткой `vkFull` журнал пишет ЦЕЛИКОМ, а снимок нёс до
   30 сообщений с разметкой по 12 000 знаков каждое = сотни килобайт на каждый переход между чатами.

**Решение (три правила для любых диагностических снимков)**:
1. **Опознавание мессенджера — только общим определителем** `detectMessengerType(url)`
   (`src/utils/messengerConfigs.js`). Свои проверки вида `url.includes('vk.com')` заводить нельзя:
   при переезде домена их забывают. Имя мессенджера как ЕДИНСТВЕННЫЙ признак тоже не годится —
   мессенджер бывает пользовательским.
2. **Объём ограничивается ПО ПОСТРОЕНИЮ**, а не обрезкой в конце: каждое поле имеет свой предел
   (текст сообщения 200 знаков, цепочка родителей 300, строка списка 120, образец текста страницы
   400), количество элементов ограничено (10 сообщений, 12 строк). Разметка элементов (`outerHTML`)
   в снимок не входит — это была основная масса.
3. **Если снимок всё же превысил потолок (12 000 знаков — столько же, сколько журнал отводит на
   подробности), печатается КОРОТКАЯ СВОДКА**, а не обрезанный JSON. Обрезка «по символам» даёт
   нечитаемый огрызок: это поймала собственная проверка первого варианта правки.
4. **Частота**: не больше 3 снимков на жизнь страницы и не чаще одного в 2 минуты — иначе переходы
   между чатами превращают журнал в свалку.

**Побочное правило**: диагностический инструмент, который может «молча не запуститься», обязан быть
проверяемым — либо пишет строку при запуске, либо по журналу видно «0 записей за всю историю».
Девять месяцев мёртвого снимка никто не заметил именно потому, что он молчал.

Связано: [[ADR-067]] (какой маршрут осмотра страницы надёжен), [[ADR-071]] (канал `monitor-diag`).

## ADR-072 — Память «что уже показывали» у детекторов списка чатов КОПИТСЯ со сроком годности, а не переписывается каждым проходом (2026-09-18, v1.2.481)

**Проблема (второй раз тот же корень)**. Детекторы, которые следят за списком чатов, сравнивают
текущий проход с предыдущим. Если память «уже видели» ЗАМЕНЯТЬ набором текущего прохода, любое
кратковременное выпадение строки (статус «печатает» вместо текста, перерисовка списка, пустой
текст, временно не распознано «непрочитано») стирает отпечаток — и сообщение уходит повторно.
Случаи: Ozon v1.2.437 (карточка вопроса повторялась каждую минуту), ВК v1.2.481 (одно «Угуу» ушло
четыре раза за 37 секунд, журнал 2026-09-18 13:30:08/28/34/41).

**Решение**: память хранит `отпечаток → время`, на каждом проходе ДОПОЛНЯЕТСЯ, записи старше срока
годности удаляются. Для ВК срок — 10 минут (`_VK_SEEN_TTL`), у Ozon — потолок по числу записей.

**Почему со сроком, а не «навсегда»**: вечная память молча съест ПОВТОРНОЕ одинаковое сообщение
(«ок», «да»), а это уже потеря уведомления. Срок годности делает забывание управляемым:
в пределах срока — защита от повторов, после — сообщение снова считается новым.

**Почему не расширение заслонок от повторов (10 с в интерфейсе, 8 с в главном процессе)**: это
лечение следствия. Мигание строки может длиться дольше любого разумного окна, а широкое окно
заглушит настоящие одинаковые сообщения.

**Обязательное дополнение**: пропуск строки в детекторе обязан писаться в журнал с причиной
(у ВК — `skipTx=` / `skipSpam=` плюс `память=N` в строке `vk-list`). Молчаливый пропуск и был
причиной того, что жалобу пришлось разбирать по косвенным признакам.

**Где ещё может быть та же схема (НЕ проверено)**: перехватчики МАКСа и WhatsApp — записано в
`code-todo.md`.

Связано: [[ADR-067]], запись про Ozon v1.2.437 в `features.md`.

## ADR-071 — Служебные сообщения из перехватчика шлём каналом `monitor-diag`, а не `console.log` из мира preload (2026-09-18, v1.2.480)

**Проблема**. Когда в v1.2.476 дописанный к перехватчику ВК второй файл молча не выполнился, разбирать
было НЕЧЕМ: программа нигде не сообщала, что именно и в каком объёме она вставила в страницу.
Попытка добавить такой отчёт упиралась в вопрос «а каким способом он вообще доедет до журнала».

**Измерено по `chatcenter.log` (2026-09-18, не предположение)**:

| Способ | Записей в журнале |
|---|---|
| `console.log('__CC_DIAG__ozon monitor hookType=…')` — из мира **preload** (v1.2.324) | **0 за всю историю файла** |
| `ipcRenderer.sendToHost('monitor-diag', …)` — тот же мир preload | **12 записей только за сутки** (`monitor-start`) |

Разница в том, КТО пишет: `console.log` из мира preload не попадает в обработчик `console-message`
хоста (у него слушается консоль СТРАНИЦЫ), а `sendToHost` идёт по ipc-каналу, у которого есть
слушатель — `src/utils/webviewSetup.js` (ветка `e.channel === 'monitor-diag'` → `traceNotif`).
Отдельно подтверждено: `console.log` из ГЛАВНОГО мира страницы (внутри самих хуков, метки `vk-list`,
`__CC_NOTIF__`) в журнал доходит — там источник другой.

**Решение**:
1. Любой служебный отчёт из `*.preload.cjs` — только через `ipcRenderer.sendToHost('monitor-diag', …)`.
   `console.log` из preload использовать нельзя: он немой.
2. Впрыск перехватчика обязан отчитываться: `hook-inject: type=<мессенджер> parts=<сколько файлов
   склеено> len=<длина> dir=<откуда прочитан>`. Счётчик `parts` обязателен: при любом разбиении хука
   на части потеря куска станет видимой сразу, а не спустя сутки разбора.
3. Диагностику, чьё расследование закрыто, убираем из хука (место дорого — потолок 300 строк), а в
   коде оставляем однострочную памятку, где её взять из истории правок.

**Цена**: одна строка в журнале на каждую загрузку веб-вкладки (редкое событие, не спам).

Связано: [[ADR-067]] (почему разовые осмотры делаем через `executeJavaScript`), запись в
`mistakes/webview-navigation-ui.md` про немой `console.log` из preload.

## ADR-069 — Картинку в карточке веб-мессенджера берём ТОЛЬКО из блока превью, а клик по ней не отдаём смотрелке (2026-09-18, v1.2.478)

**Проблема**. У нативного Telegram в карточке уведомления есть фотография (данные TDLib,
`shared/notifAlbum.js`). У веб-мессенджеров данных нет — есть только страница. Жалоба 2026-09-18:
«показывало сообщения фото, а не описывало фото словом».

**Решение (три правила сразу)**:
1. **Где ищем**: картинка берётся ТОЛЬКО внутри блока превью строки списка — того самого, откуда
   уже берётся текст (`_vkRowText`). Аватар собеседника лежит в другом блоке, поэтому перепутать их
   структурно невозможно. Это ответ на пять подряд промахов по вёрстке ВК (v1.2.110–120): новых
   догадок о разметке не вводим, переиспользуем уже проверенный селектор.
2. **Кто качает**: главный процесс, тем же `downloadIcon` и тем же кэшем, что и фото отправителя;
   снимок ужимается до 480 точек (в карточке плитка меньше, тащить оригинал в окно незачем);
   ожидание ограничено `PHOTO_PREWAIT_MS = 900` мс — карточка важнее картинки.
3. **Клик**: по веб-фото полноразмерная смотрелка НЕ открывается. Смотрелка умеет только TDLib
   (качает оригинал по номеру сообщения), у веб-фото ни чата TDLib, ни номера нет — открылось бы
   пустое окно. Клик уходит карточке (обычный переход в чат).

**Как признак передаётся**: ПРЕФИКСОМ идентификатора альбома `single_web_…`, а не новым полем.
Причина приземлённая: `main/notification.js` стоит на своём потолке (729/730), и новое поле
потребовало бы там строк; префикс же читается и в окне, и в общем файле без правок.

**Честная граница (записана, чтобы потом не считать это поломкой)**: ВК в списке чатов обычно
пишет СЛОВО «Фотография», а не кладёт картинку. Тогда фото не будет — карточка выйдет как раньше
(«📷 Фото»), а журнал напишет `[notif-photo] карточка выйдет без фото …`. Отсутствие картинки —
штатный режим этого пути, а не сбой.

Связано: [[ADR-068]] (снятие пометки вложения ВК), [[ADR-019]] (картинку ссылки-превью не достаём),
[[ADR-067]] (почему разовые осмотры страницы делаем через executeJavaScript).

## ADR-068 — Пометку вложения ВК снимаем ТЕКСТОМ, но с четырьмя ограничителями (2026-09-18, v1.2.477)

**Проблема**. ВК сам дописывает в конец подписи строки списка чатов название вложения: «Сообщение»
(ответ на сообщение), «Фотография», «Голосовое сообщение». Мы копируем подпись целиком, и это слово
уезжает в карточку уведомления как мусор.

**Почему не по вёрстке** (что было бы правильнее). Точный класс элемента-пометки в строке ЛИЧНОГО чата
на vk.ru неизвестен. Узнать его можно только осмотром живой страницы, а разовый осмотр в v1.2.476 не
дал ни одной строки (см. [[ADR-067]]). Гадать по селекторам ВК проект пробовал пять раз подряд
(v1.2.110–120) — каждый раз мимо.

**Решение**: чистим текстом, но так, чтобы съесть живую речь было структурно трудно —
`shared/vkPreviewText.js`, четыре ограничителя сразу:
1. пометка снимается ТОЛЬКО с самого конца строки;
2. сверка С УЧЁТОМ РЕГИСТРА — ВК пишет пометку с большой буквы, живая речь идёт с маленькой
   («удали это сообщение», «пришли мне фотографию»);
3. пометка должна быть ОТДЕЛЬНЫМ словом (перед ней пробел или начало строки) — «СуперСообщение» цело;
4. список пометок ЗАКРЫТЫЙ (названия вложений ВК), а не «любое слово».

Плюс результат никогда не пустой: от фото без подписи остаётся «📷 Фото» (иначе карточку выбросил бы
страж пустого текста в главном процессе).

**Цена**: сообщение, которое в точности заканчивается пометкой ВК («… Фотография» отдельным словом с
большой буквы), потеряет это слово. Вероятность низкая, потеря — одно слово.

**Прецедент, из-за которого ограничителей четыре**: v1.2.115, где чистка «по словам» откусила хвост
фразы «буду через 5 минут» → «буду через».

Связано: [[ADR-067]].

## ADR-067 — Разовый осмотр чужой страницы делаем через executeJavaScript, а не дописыванием файла к хуку (2026-09-18, v1.2.477)

**Проблема**. Чтобы увидеть реальную вёрстку строки списка чатов ВК, в v1.2.476 к хуку ВК дописывался
второй файл (`vkRowDiag.hook.js`) — тот же `<script>`, та же страница. За целую сессию работы он не дал
**ни одной** строки в журнале, хотя сам хук ВК в это время работал (48 строк `vk-list`) и трижды
отправлял карточки (11:10:13, 11:11:07, 11:12:45) — а дамп снимается ровно в этом месте.

**Что проверено и исключено** (измерено, не предположено): файл лежал и в исходниках, и в сборке;
проводка есть и в исходном `monitor.preload.cjs`, и в собранном `out/preload/monitor.mjs`; склейка
«хук + диагност» синтаксически верна (`node --check`) и в поддельной странице (jsdom) ставит
`window.__ccVkRowDiag`; оба возможных пути чтения файла смоделированы отдельным прогоном и работают.

**Причина не установлена.** Поэтому решение принято не «почему», а «чем пользоваться»:

**Решение**: для разовых осмотров чужой страницы брать `executeJavaScript` из интерфейса — маршрут,
доказанный ТЕМ ЖЕ журналом: в 10:52:11 он написал `probe[doc]`, `ws-hook: attached`,
`wv-err-catcher: attached` с той же самой страницы ВК. Дописывание второго файла к хуку для разовых
осмотров больше не применяем.

**Побочное правило**: любой впрыск-диагност обязан первой же строкой сообщать, что он установился, и
эту строку надо искать в журнале ПЕРЕД тем, как ждать данные. Отсутствие строки установки — сигнал
«маршрут не доехал», а не «данных ещё нет».

## ADR-066 — Один и тот же срок ожидания задаём в ОДНОМ месте, даже если ждут разные пути (2026-09-17, v1.2.475)

**Проблема**. Одно входящее сообщение ловят два наблюдателя, и каждый перед показом ждёт «богатую»
версию (имя отправителя, номер сообщения, ссылка на фото). Сроки ожидания были прописаны в РАЗНЫХ
файлах и разными числами: 500 мс в `webviewSetup.js` и 1200/200 мс в `consoleMessageHandler.js`.
У МАКСа богатая версия приходит примерно через секунду — ровно между этими числами. Быстрый путь
сдавался первым и показывал бедную карточку, следом приходила богатая → ДВЕ карточки на одно
сообщение, причём с разными картинками.

**Решение**: срок живёт в одном месте — `shared/notifEnrichWait.js`, функция
`enrichWaitMsFor(url, defaultMs)`.
- для МАКСа — общий `MAX_ENRICH_WAIT_MS = 1200`;
- остальным возвращается ИХ собственный привычный срок (аргумент `defaultMs`), чтобы правка не
  меняла поведение там, где всё работало;
- проверка адреса — по хосту `web.max.ru`, не подстрокой `max.ru` (иначе попадают `climax.ru` и
  `formax.ru` — грабля v1.2.418).

**Цена**: уведомления МАКСа появляются примерно на 0,7 секунды позже. Осознанно: одна карточка с
фотографией лучше двух мгновенных.

**Общее правило**: если два разных места ЖДУТ ОДНО И ТО ЖЕ событие, их сроки обязаны браться из
одного источника. Разные числа на одно событие — это не «настройка под путь», а будущий разъезд.

Связано: [[ADR-065]] (склейка пары копий — лечит следствие этого же разъезда).

## ADR-065 — Исключение из защиты делаем ТОЧЕЧНЫМ: «смотреть можно, класть нельзя, совпадение съедается» (2026-09-17, v1.2.474)

**Проблема**. У веб-мессенджеров одно сообщение ловят несколько независимых наблюдателей. Чтобы не
плодить карточки, в v1.2.318 добавили кросс-ключ «мессенджер + отправитель + текст» — он склеивает
копии, у которых РАЗНЫЕ номера сообщений. В v1.2.319 МАКС из этого механизма исключили ЦЕЛИКОМ,
потому что МАКС кодирует событие в номере сообщения (`max-sidebar:<отправитель>:<непрочитано>`) и
только так отличает два ОДИНАКОВЫХ сообщения подряд (защита v1.2.55).

Побочный эффект вскрылся 2026-09-17: копия без номера кросс-ключ КЛАЛА, а копия МАКСа его даже не
СМОТРЕЛА → на одно сообщение приходили две карточки (одна с фото, другая с логотипом).

**Решение**: исключение разделено на три отдельных права вместо одного «нельзя».

| Право | МАКС | Прочие веб | Зачем |
|---|---|---|---|
| СМОТРЕТЬ кросс-ключ | ✅ да | ✅ да | ловит пару «одно сообщение — две двери» |
| КЛАСТЬ кросс-ключ | ❌ нет | ✅ да | иначе два одинаковых подряд слипнутся (регресс v1.2.55) |
| СЪЕДАТЬ при совпадении | ✅ да | ❌ нет | ключ гасит ровно ОДНУ парную копию; следующее такое же сообщение снова покажется |

**Общее правило на будущее**: когда защита кому-то мешает, не выключать её для него целиком —
разложить на отдельные права (читать / писать / расходовать) и отключить ровно то, что мешает.
Полное исключение закрывает одну дыру и открывает другую, причём молча.

**Где применяется**: `decideNotifDedup` в `main/handlers/notifDedupDecision.js`, поле `consumeKey`;
расходует ключ `main/handlers/notificationManager.js`.

**Сопутствующее решение**: погашенная копия отдаёт своё фото уже показанной карточке
(`findCardToImproveIcon` + `improveIconOnExistingCard`) — иначе склейка теряла бы фотографию
отправителя, которая была только у погашенной копии.

Связано: [[ADR-064]] (итог обращения к защите пишет вызывающий), `mistakes/notifications-ribbon.md`.

## ADR-064 — Спасательное окно не должно жить внутри того, что удаляют; авто-перезагрузка — только когда терять уже нечего (2026-09-16, v1.2.472)

**Проблема**: окно «Повторим через N с» (переподключение самого приложения, v1.2.452) было
нарисовано ВНУТРИ стартовой заставки `#cc-splash`. Заставку удаляют через полсекунды после
готовности — значит при обрыве связи ВО ВРЕМЯ РАБОТЫ показывать окно было негде, и пользователь
видел голый красный экран «Ошибка рендера» без выхода (жалоба 2026-09-16, доказано журналом:
`net::ERR_NETWORK_CHANGED` на отметке +161 секунда после старта).

**Решение 1 — окно переживает заставку.** Перед удалением заставки узел окна переносится в
документ (`detach()` в `index.html`) и встаёт по центру экрана (`cc-bn--float`). Вид при запуске
не меняется: пока заставка на месте, окно рисуется там же, где раньше.

🔴 **Оба места, которые убирают заставку, обязаны звать `detach()`**: обычный путь
(`hideCcSplash` в `src/main.jsx`) и предохранитель 3 минуты (`src/boot-probe.js`). Иначе беда
вернётся молча через второе место. Закреплено проверкой в `bootNet.vitest.js`.

**Решение 2 — авто-перезагрузка только там, где терять нечего.** Сбой корня программы = красный
экран во весь экран, работать всё равно нельзя → окно само перезагружает страницу по отсчёту.
Сбой ОТДЕЛЬНОЙ панели (её ловит `src/components/ErrorBoundary.jsx`) = программа продолжает
работать, у панели есть своя кнопка «Попробовать снова» → окно показывается, но перезагрузки НЕТ
(`onLoadError(msg, { soft: true })`). Иначе внезапная перезагрузка вырывала бы работу из-под рук
из-за отвалившейся боковой панели.

**Урок общего характера**: если спасательный механизм нарисован внутри временного элемента, он
работает ровно столько, сколько живёт этот элемент. Проверять надо не «показывается ли окно», а
«показывается ли оно в тот момент, когда беда реально случается».

Связано: [[ADR-060]] (красный экран — для ошибок кода, окно повтора — для сбоев загрузки),
[[ADR-053]] (событие «загрузилась» — не доказательство успеха).

## ADR-063 — «Страница жива» доказывает СОДЕРЖИМОЕ страницы, а не факт ответа нашего сторожа (2026-09-16, v1.2.470 → ИСПРАВЛЕНО в v1.2.471)

**Проблема**: карточку «фоновая страница Ozon недоступна» решили показывать не сразу, а отменять,
если страница поднимется сама. Встал вопрос: по какому признаку считать, что она поднялась.

**Что уже известно проекту** (ADR-053, v1.2.453): событие «страница загрузилась» приходит И на
странице-ошибке, которую Chromium рисует сам на месте неудачной загрузки. Верить ему нельзя.

### 🔴 ПЕРВАЯ РЕДАКЦИЯ ЭТОГО РЕШЕНИЯ БЫЛА ОШИБОЧНОЙ — оставляем как урок

В v1.2.470 было записано: «ответ нашего сторожа изнутри страницы — доверяем СРАЗУ, потому что на
странице-ошибке нашего сторожа нет и быть не может». **Это утверждение неверно.** Придирчивая
перепроверка в тот же день доказала прогоном:

* сторож впрыскивается на КАЖДОЕ событие «документ готов» (`ozonBgWatcher.js`, обработчик
  `dom-ready`) — проверки адреса там нет, значит он попадает и в страницу-ошибку;
* попав туда, он через 2,5 секунды пишет стартовую диагностику (`ozon.hook.js`, ветка
  `reason === 'initial'` срабатывает ВСЕГДА, даже при нуле строк на странице).

Итог первой редакции: при настоящей длительной недоступности Ozon карточка НЕ появлялась, а в
журнале стояла ложная строка «страница поднялась САМА за 3 с».

**Урок общего характера**: «наш код там не запустится» — это НЕ факт, а догадка, пока не открыт
тот файл, который решает, где он запускается. Грабля записана в
[mistakes/webview-injection.md](mistakes/webview-injection.md).

### ✅ ДЕЙСТВУЮЩЕЕ РЕШЕНИЕ (v1.2.471)

Доказательств два, оба опираются на СОДЕРЖИМОЕ, а не на факт ответа:

1. **Сколько в странице элементов.** После события «загрузилась» спрашиваем саму страницу.
   Порог `OZON_BG_ALIVE_MIN_NODES = 300` не выдуман: ровно это число уже стоит внутри
   `ozon.hook.js` как признак «страница ещё не загрузилась». Заглушка Chromium — меньше сотни,
   настоящий Ozon — тысячи.
2. **Данные, которых на пустой странице быть не может**: уведомление о вопросе/сообщении/отзыве
   либо счётчик БОЛЬШЕ НУЛЯ (`isOzonAliveProof`). Диагностика с `rows=0` — не доказательство.

Запасной путь (спросить нечем): прежнее правило проекта — верим событию «загрузилась» только
спустя `ERROR_PAGE_GRACE_MS` после сбоя. Спросить не удалось — НЕ засчитываем и пишем причину.

**Цена**: один лишний вопрос к странице на каждое событие загрузки после сбоя (одна строка кода,
выполняется только когда беда уже случилась).

**Где применяется**: `createOzonBgFailWatch` в `shared/ozonBgFailWatch.js`.
Связано: [[ADR-053]] (событие загрузки — не доказательство), [[ADR-062]] (память не живёт на
пересоздаваемом объекте).

## ADR-062 — Память «уже предупреждали» НИКОГДА не живёт на объекте, который пересоздаётся (2026-09-16, v1.2.467)

**Контекст**. Карточка «Не удалось открыть фоновую страницу Ozon» приходила часто, хотя код обещал
показать её один раз. Пометка «уже сообщил» стояла на самом элементе фоновой страницы, а элемент
пересоздаётся: журнал 2026-09-16 показал **9 созданий за один запуск** приложения.

Это ВТОРОЙ случай той же болезни в одном месте кода. Первый — v1.2.438: память «этот вопрос уже
показывали» держали в хранилище чужой страницы Ozon, и она умирала при каждой перезагрузке страницы
(раз в минуту). Тогда память перенесли в наше приложение (`shared/ozonNotifDedup.js`).

**Решение**. Любая пометка «уже предупреждали / уже показывали» обязана жить **вне того объекта,
о котором она говорит**: в нашем приложении, а не на элементе страницы, не в чужом хранилище и не
в самом объекте. И обязана иметь СРОК МОЛЧАНИЯ — иначе о непрошедшей беде никто не узнает.

**Как отличить правильное место от неправильного — один вопрос**: «что будет с этой пометкой, если
объект пересоздадут?» Исчезнет — место неправильное.

**Следствия**.
1. Новую защиту «сообщить один раз» не писать заново: в проекте уже есть `shared/ozonNotifDedup.js`
   со сроком молчания и потолком записей — расширять его новым источником.
2. Срок молчания обязателен и конечен. «Один раз навсегда» — это потеря диагностики.
3. Когда карточку НЕ показали, это обязано попасть **в журнал** с причиной. Молчание без записи
   неотличимо от «всё хорошо» — на эту же ошибку проект наступал в v1.2.462 (защита от повторов
   писала, только когда ловила) и в v1.2.466 (окно повтора молчало при отказе).
4. Общая память живёт между тестами одного файла → в тестах обязателен сброс в `beforeEach`.
   Без него проверки зависят от порядка запуска (проверено прогоном «наоборот»: падают 4 из 20).

**Где применено**: [shared/ozonNotifDedup.js](../shared/ozonNotifDedup.js)
(`OZON_BG_FAIL_SOURCE`, `decideOzonBgFailNotice`), [ozonBgWatcher.js](../src/utils/ozonBgWatcher.js).
**Проверка живая**: [ozonBgWatcher.vitest.js](../src/__tests__/ozonBgWatcher.vitest.js) — «пять
разных элементов подряд → карточка одна», «три страницы упали разом → карточка одна».
Связано с [[ADR-059]] (ошибаться только в безопасную сторону) и [[ADR-061]].

## ADR-061 — Заглушку «показывать нечего» ставим в РАЗБОРЕ, и только для видов, про которые точно известно (2026-09-16, v1.2.465)

**Контекст**. Одно и то же сообщение показывалось тремя разными надписями: «[медиа]» в уведомлении,
«📎 вложение» в списке чатов, пустой пузырь в переписке. Каждое место подставляло СВОЮ заглушку.
Когда стало известно, что за вид приходит (`messageUnsupported`), встал вопрос: где ставить подпись.

**Решение**. Подпись ставится **в разборе сообщения** (`tdlibMapper`), а не в местах показа.
Показывающие места текст не сочиняют — они берут готовый.

**Почему не в местах показа**. Их три, и они принадлежат разным слоям (главный процесс, интерфейс,
окно уведомления). Три копии одной подписи разъедутся при первой же правке — ровно так и появились
три разные надписи для одного сообщения.

**Второе правило — словарь коротким**. В словарь «показывать нечего» попадает вид, только если про
него ТОЧНО известно, что содержимого нет. Сегодня там одна строка. Незнакомый вид подписи НЕ
получает: выдумывать за пользователя нельзя, а старое поведение («[медиа]») хотя бы честно говорит
«не знаю». Это прямое продолжение [[ADR-059]] — ошибаться только в безопасную сторону.

**Третье — порядок важен**. Подпись подставляется ПОСЛЕ расчёта «это эмодзи-сообщение?», иначе
подпись из слов сочли бы эмодзи и нарисовали гигантским шрифтом.

**Следствия**.
1. Новый вид «нечего показывать» добавляется ОДНОЙ строкой в словарь — и чинит сразу три места.
   ⚠️ Уточнено в v1.2.466: это верно только потому, что словарь спрашивают ДВА составителя — разбор
   `mapMessage` (переписка + уведомление) и `messagePreview` (список чатов). Изначально второго
   спросить забыли, и список чатов показывал своё; поймано придирчивым ревью. Появится третий
   составитель — обязан спросить тот же словарь, иначе надписи снова разъедутся.
2. Служебные записи («добавлен участник») в словарь не входят: у них своя подпись для списка чатов,
   а показ в переписке — отдельная задача.
3. Запись `[tdlib-empty]` из v1.2.461 остаётся: именно она называет очередной вид, и без неё
   словарь пополнять нечем.

**Где применено**: [tdlibMapperMedia.js](../main/native/backends/tdlibMapperMedia.js)
(`emptyMessageFallbackText`), [tdlibMapper.js](../main/native/backends/tdlibMapper.js).
**Проверка живая**: [unsupportedMessage.vitest.js](../src/__tests__/unsupportedMessage.vitest.js) —
ловушки «незнакомый вид подписи не получает», «служебные не попали», «копии не расползлись».

## ADR-060 — Красный экран остаётся для ошибок КОДА, окно повтора — только для сбоев ЗАГРУЗКИ (2026-09-16, v1.2.464)

**Контекст**. Аварийное окно повтора (причина + отсчёт + кнопка) научили подниматься из
перехватчиков ошибок отрисовки. Возник соблазн заменить им красный экран целиком — он выглядит
пугающе и ничего не даёт пользователю.

**Решение**. Разделяем два РАЗНЫХ случая, и каждый показывает своё:
| Случай | Что показываем | Почему |
|---|---|---|
| кусок программы **не догрузился** (сеть, dev-сервер, пробка) | окно повтора | лечится повтором, пользователь может помочь сам |
| ошибка **в самом коде** (опечатка, обращение к пустому значению) | красный экран с текстом и стеком | повтор НЕ поможет; нужен текст ошибки, иначе чинить не по чему |

Решает одна маска `LOAD_FAIL` в `index.html` — единственное место, где это различие описано.

**Почему не заменить красный экран везде**. Тогда настоящая поломка кода выглядела бы как «сеть
барахлит»: программа бесконечно перезагружалась бы по лестнице пауз, а причина была бы не видна ни
пользователю, ни разработчику. Это тот же класс ошибки, что в [[ADR-059]] — глушение диагностики
ради красивого вида.

**Следствия**.
1. Новый перехватчик ошибок отрисовки ОБЯЗАН передавать сообщение в `onLoadError`, а не решать сам.
2. Маску нельзя копировать в `src/` — это сторожит тест (`bootNet.vitest.js`).
3. Окно не поднимается, когда приложение уже работает (заставки нет): у панелей своя кнопка
   «Повторить», а перезагружать рабочее приложение из-за одной упавшей панели нельзя (та же
   ошибка, что чинили в v1.2.453).

**Где применено**: `index.html` (`LOAD_FAIL`, `onLoadError`, `show` возвращает результат),
`src/main.jsx`, `src/components/ErrorBoundary.jsx`.
**Проверка живая**: `src/__tests__/bootNet.vitest.js` — ловушки «чужая ошибка окно НЕ поднимает»
и «приложение работает → окна нет».

## ADR-059 — Проверка, которая ГЛУШИТ уведомления, ошибается только в одну сторону: не уверена — пропусти (2026-09-15, v1.2.463)

**Контекст**. Жалоба: МАКС уведомлял о СВОИХ отправленных сообщениях. Причина — признак «исходящее»
измерялся, но решения по нему не принимал никто (см. `mistakes/webview-injection.md`). Надо было
сделать настоящую проверку, но различать своё и чужое приходится по вёрстке ЧУЖОЙ страницы, а она
меняется без предупреждения и не описана нигде.

**Решение**. Любая проверка, которая ГЛУШИТ уведомление, обязана быть построена так, чтобы её ошибка
была **односторонней**: сомневаешься — ПРОПУСКАЙ. Конкретно для `maxOutgoingDecision`:
- «своё» ставится только при ЯВНОМ перевесе (отступ пузыря справа меньше отступа слева более чем на
  40 точек);
- пузырь во всю ширину строки (очень длинное своё сообщение) → «не знаем» → пропускаем;
- нет замера, нулевые размеры, исключение → «не знаем» → пропускаем.

**Почему так**. Цена двух ошибок РАЗНАЯ и несопоставимая:
| Ошибка | Что видит человек | Цена |
|---|---|---|
| приняли чужое за своё | уведомление НЕ пришло | **потерянное сообщение клиента** — тихо, заметят поздно |
| приняли своё за чужое | лишняя карточка о своём сообщении | раздражает, видно сразу, чинится следующей правкой |

Симметричное правило («ставим то, что вероятнее») выглядит точнее, но при сдвиге вёрстки начинает
терять входящие — а это ровно то, ради чего программа существует.

**Следствия**.
1. Каждое такое правило обязано иметь ветку «не знаю» с ОТДЕЛЬНОЙ причиной в журнале — иначе
   непонятно, правило промахнулось или признак изменился.
2. В тесте обязательна ловушка на ЗАПРЕЩЁННЫЙ случай («широкое входящее НЕ должно стать своим»),
   а не только на успешный.
3. То же правило применимо к любым будущим глушилкам: «заглушённый чат», «спам», «фантом»,
   «уже прочитано». Связано с [[ADR-058]] (ограничение обязано работать на всех путях) — там про
   полноту, здесь про сторону ошибки.

**Где применено**: [maxDiagnostics.js](../main/preloads/utils/maxDiagnostics.js) `maxOutgoingDecision`,
проводка — [monitor.preload.cjs](../main/preloads/monitor.preload.cjs).
**Проверка живая**: [maxOutgoing.vitest.js](../src/__tests__/maxOutgoing.vitest.js) — ловушки на
широкое входящее, пузырь во всю ширину, недостаточный перевес и сбой замера.

## ADR-058 — Ограничение величины обязано работать на ВСЕХ путях её изменения (2026-09-15, v1.2.459)

**Контекст**: в v1.2.457 ширине списка чатов задали потолок «не шире 40 % окна». Проверку
(`clampChatListWidth`) поставили на двух путях — загрузка настроек и перетаскивание разделителя.
Третий путь, сброс по двойному щелчку, ставил значение по умолчанию НАПРЯМУЮ и про потолок не знал.
Нашла это придирчивая самопроверка, а не пользователь: при действующем минимуме окна (900 точек)
потолок 360 больше значения по умолчанию 340, поэтому правило де-факто не нарушалось.

**Решение**: если для величины введено ограничение, оно применяется в ОДНОЙ общей функции, и через
неё обязаны проходить ВСЕ пути изменения этой величины — загрузка, изменение пользователем, сброс,
восстановление. Отдельный путь «в обход» — дефект, даже если сегодня он недостижим.

**Почему это важно, хотя «сейчас не срабатывает»**: недостижимость держится на ДРУГОМ числе из
другого файла (минимальная ширина окна в `main/utils/windowManager.js`). Изменят его — правило
сломается молча, без ошибки и без записи в журнале. Такие связки надо закрывать сразу.

**Как проверяется**: ловушка в `src/native/hooks/useChatListResize.vitest.jsx` — сброс при узком окне
обязан дать значение не больше потолка. До фикса падала (`expected 340 to be 280`).

**Родственное правило для памяти**: снятая настройка не должна выдаваться за действующую. Проверка
в `src/__tests__/projectHealth.test.cjs` требует, чтобы упоминание снятой настройки сборки в памяти
сопровождалось пометкой «устарело» (см. ADR-057).

**Связано с**: ADR-055 (потолок ширины панели ИИ), ADR-057 (подпись ≠ вшивание значка),
[[features]] v1.2.457, v1.2.459, [[code-todo]] TODO-40.
