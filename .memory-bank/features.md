### v1.2.458 — 🔴 ЖАЛОБА «почему значок старый у программы»: значок НИКОГДА не вшивался в файл программы

**ЖАЛОБА** (2026-09-11, со скриншотом рабочего стола): у ярлыка «ЦентрЧатов» стандартный значок Electron («атом»), а не наш знак.

**КОРЕНЬ (🟢 доказан выводом самого сборщика)**: в `package.json` в разделе сборки стояло
`"signAndEditExecutable": false`. Эта настройка отключает НЕ ТОЛЬКО подпись, но и правку ресурсов
исполняемого файла — то есть вшивание значка и описания. Сборщик прямо писал об этом в журнале
КАЖДОЙ сборки, включая нашу от 2026-09-11:

```
executable resource editing and code signing skipped — signAndEditExecutable is false.
To skip only code signing while keeping icon and metadata applied, use signExecutable: false instead.
exe=dist\win-unpacked\ЦентрЧатов.exe
```

Итог: `ЦентрЧатов.exe` оставался с родным значком Electron, а ярлык рабочего стола берёт картинку
именно из файла программы. Настройку ставили ради «установщик без подписи» (запись в
[CHANGELOG.md](CHANGELOG.md) про упаковку установщика) — цель была НЕ подписывать, а побочно
отключилось и вшивание значка.

**Почему внутри приложения значок был ПРАВИЛЬНЫЙ**: значок окна и трея приложение рисует на ходу
своим кодом (`nativeImage.createFromBuffer(drawMark(...))` в [windowManager.js](../main/utils/windowManager.js)
и [overlayIcon.js](../main/utils/overlayIcon.js)). Ярлык так не умеет — ему нужен значок, зашитый в файл.
Отсюда и странное ощущение «в программе новый, на ярлыке старый».

**ФИКС**: `"signAndEditExecutable": false` → `"signExecutable": false` — ровно то, что советует сам
сборщик: подпись по-прежнему пропускается (сертификата нет), а значок и описание вшиваются.

**❌ ОПРОВЕРГНУТАЯ ВЕРСИЯ (важно для истории)**: сначала я решил, что виноват ещё и УСТАРЕВШИЙ файл
значка — дата `build/icon.ico` (10.09 17:21) была РАНЬШЕ последней правки рисовалки
`shared/appIconMark.js` (17:46) и раньше коммитов v1.2.450-451, менявших знак. Проверил фактом:
перерисовал значок из единого источника (`node scripts/make-app-icon.cjs`) — файлы вышли
**побайтно теми же** (`git status` пуст, `build/icon.ico` те же 4479 байт). Значит файл значка был
АКТУАЛЬНЫМ, а правки v1.2.450-451 меняли масштаб значка в трее и панели задач (он считается на ходу),
а не содержимое `.ico`. Урок: дата файла — НЕ доказательство устаревания; доказательство — перегенерация
и сравнение.

**КАК ПРОВЕРЕНО**: пересборка установщика — в журнале БОЛЬШЕ НЕТ строки «executable resource editing
… skipped», зато есть правка ресурсов; размер `ЦентрЧатов.exe` отличается от чистого `electron.exe`.
Линт 0; цепочка 48/48; полный `vitest` 206 файлов / 2752 теста; лимиты 649/649; память 44/44.

**ЧТО ПРОВЕРИТЬ ВРУЧНУЮ**: установить `dist/ЦентрЧатов-Setup-1.2.458-x64.exe` → у ярлыка на рабочем
столе наш знак.
⚠️ **Windows кэширует значки ярлыков**: если остался старый — удалить ярлык и создать заново (или
перезайти в систему). Это не дефект приложения, но без этого знания легко решить, что фикс не помог.

**ОСТАТОЧНЫЕ РИСКИ**: (а) 🟢 подпись по-прежнему не ставится — установщик остаётся неподписанным,
Windows может показывать предупреждение при запуске (так было и раньше, поведение не менялось);
(б) 🟢 живьём не смотрел — запускать приложение мне нельзя.

### v1.2.457 — 🔴 ЖАЛОБА «дёргание при переключении между мессенджерами» + список чатов считается с окном + разгрузка памяти

**Коммит**: `504a0ea` (ветка `feature/virtualization`, 2026-09-11). Приложение при разработке не запускалось — правило проекта; всё доказано тестами.

**ЖАЛОБА**: «дёргание при переключении между мессенджерами».

**КОРЕНЬ (🟢 доказан чтением кода, не догадка)**: приложение НАРОЧНО меняет геометрию страницы при открытии веб-вкладки — на миг делает обёртку уже на 1 точку и возвращает обратно («пинок раскладки», [useWebViewLifecycle.js](../src/hooks/useWebViewLifecycle.js), v1.2.416, Ловушка 64). Смысл пинка: расклеить адаптивный сайт, который при первой отрисовке прочитал неверный размер (из-за этого когда-то чернел веб-МАКС). НО делался он **на каждое открытие вкладки и ДВАЖДЫ** — через 200 мс и через 700 мс. То есть при каждом переключении страница дважды за секунду перекладывалась. Пинок применялся ко ВСЕМ веб-мессенджерам (Telegram, WhatsApp, ВК, Ozon, МАКС), а не только к тому, ради которого заводился.

**ПОЧЕМУ ЭТО ЛИШНЕЕ**: слипание раскладки — событие РАЗОВОЕ, оно случается при первом показе страницы, а не при каждом возврате на уже открытую вкладку. К тому же исходная причина чёрного экрана веб-МАКС была опровергнута дважды: сначала v1.2.417 (убивали ServiceWorker), потом окончательно v1.2.434 (наш собственный впрыск прятал корень приложения) — пинок остался «на всякий случай».

**ФИКС**: пинок делается только при ПЕРВОМ открытии каждой вкладки. Отметка хранится на самом элементе (`wrap.__ccRelayoutKicked`) — приём проекта (так же помечены подключённые слушатели в `useWebviewReconnect`), поэтому НОВЫХ хранилищ в приложении не появилось: добавление хранилища в работающее приложение ломает горячую перезагрузку (см. v1.2.452). Отметка ставится ПОСЛЕ повтора на 700 мс: ушёл с вкладки раньше — в следующий раз пинок будет снова (первый показ мог и не состояться).
**ЗАЩИТА НЕ ПОТЕРЯНА**: сторож чёрного экрана ([webviewBlackWatchdog.js](../src/utils/webviewBlackWatchdog.js), v1.2.431) раз в 60 с делает «фото» кадра активной веб-вкладки и при пустом кадре сам делает ТОТ ЖЕ пинок — у него своя реализация, моей отметкой он не ограничен (проверено чтением: строки с `wrap.style.width` там свои).
В журнал добавлена строка уровня TRACE «пинок НЕ нужен … вкладка уже открывалась» — по ней видно, что фикс работает.

**ВТОРОЕ — TODO-40 ЗАКРЫТ ЧАСТИЧНО: список чатов считается с размером окна** ([useChatListResize.js](../src/native/hooks/useChatListResize.js)). ### v1.2.456 — ДОВОДКА ПО СОБСТВЕННОМУ РЕВЮ v1.2.455: потолок панели вынут из анимируемого свойства + три дыры в проверках

**Коммит**: `504a0ea` (ветка `feature/virtualization`, 2026-09-11). Приложение при разработке не запускалось — правило проекта; всё доказано тестами.

**КОНТЕКСТ**: придирчивая самопроверка v1.2.455 нашла 4 замечания (одно — свежая беда, внесённая самой правкой). Пользователь сказал «план исправления, делай полностью» — закрыты все четыре плюс пункт про журнал.

**№1 🟡 → 🟢 ПАНЕЛЬ ОТСТАВАЛА ПРИ ИЗМЕНЕНИИ РАЗМЕРА ОКНА** (внесено v1.2.455, закрыто здесь)
В v1.2.455 потолок «не больше половины окна» был вписан ПРЯМО в ширину внешнего слоя панели: `width: min(458px, 50vw)`. Но на ширине этого слоя висит плавный переход 0.15 с ([AISidebar.jsx](../src/components/AISidebar.jsx), `transition: 'width 0.15s'` — он делает красивое сворачивание панели). Факт уровня 1 (MDN, CSS transitions): переход срабатывает на изменение ВЫЧИСЛЕННОГО значения свойства, а `vw` вычисляется в точки сразу → при каждом изменении размера окна ширина менялась и каждый раз запускалась анимация. Итог: край панели ехал за краем окна с отставанием, и в эти доли секунды ряд мог не влезть (а он помечен «лишнее срезать»).
ФИКС: ширина внешнего слоя — снова ПОСТОЯННОЕ число, а потолок задан ОТДЕЛЬНЫМ правилом `maxWidth: AI_PANEL_MAX_CSS` (`'50vw'`, новый экспорт [shared/panelWidthCap.js](../shared/panelWidthCap.js)). Свойства `max-width` в списке перехода нет → его изменение анимацию не запускает, ширина при изменении размера окна постоянна, а сворачивание панели по-прежнему плавное.
ВНУТРЕННИЙ слой намеренно оставлен с выражением `min(...)`: у него задан ещё и минимум ширины (чтобы содержимое не переливалось во время сворачивания), а по правилам вёрстки минимум побеждает максимум — отдельный потолок там просто не сработал бы. Перехода на внутреннем слое нет, поэтому отставания он не создаёт.
Перетаскивание ([useAIPanelResize.js](../src/hooks/useAIPanelResize.js)) пишет ровно то же, что и отрисовка: снаружи постоянное число, внутри — выражение с потолком.

**№2 🟡 ДВА ИСТОЧНИКА ДЛЯ ОДНИХ ЧИСЕЛ**: [useAppBootstrap.js](../src/hooks/useAppBootstrap.js) зашивал `Math.max(240, Math.min(600, …))` при восстановлении ширины, а те же 240/600 с v1.2.455 живут в общем файле. Смена потолка в одном месте молча не доехала бы до восстановления. ФИКС: берём `AI_PANEL_MIN_PX` / `AI_PANEL_MAX_PX` из общего файла.

**№3 🟡 «УЗЕЛ ВЕЛИЧИН» НЕ СВЕРЯЛСЯ АВТОМАТИЧЕСКИ**: вынесенная в v1.2.455 кнопка «↓ вниз» получает всё нужное одним узлом. Переименование величины линтер поймает, а вот ДОБАВЛЕНИЕ новой величины в модуль без добавления её в узел — не поймает ничем: кнопка упала бы у пользователя в момент нажатия. **№4 🟡 У ПАНЕЛИ ИИ НЕ БЫЛО ТЕСТА ОТРИСОВКИ ВООБЩЕ**: все проверки потолка были «по тексту кода» — они не заметили бы, что правильное правило написано, но в готовую разметку не попало. ВЫБРАННЫЙ СПОСОБ — правило вёрстки `min(<сохранённое>px, 50vw)`, а НЕ слушатель размера окна. Почему:
- слушатель — это новый хук; добавление хука в работающее приложение ломает горячую перезагрузку (v1.2.452, проходили дважды);
- слушатель, записывающий ширину в настройки, УНИЧТОЖИЛ бы выбор пользователя: сузил окно — и 458 навсегда стали 300;
- правило вёрстки пересчитывает сам браузер при каждом изменении размера: ноль слушателей, ноль перерисовок, сохранённое число цело (окно вернули широким — панель снова 458).
Факты уровня 1 (MDN): `min()` берёт наименьшее из списка и допускает смешение единиц; `vw` = 1% ширины окна, пересчитывается при изменении размера; `min-width` при конфликте побеждает `max-width` — поэтому внутреннему слою панели задано ТО ЖЕ выражение, а не отдельный потолок (иначе он вылез бы за внешний слой и был бы обрезан — та же беда v1.2.454, но внутри панели).
Правило стоит в ЧЕТЫРЁХ местах: внешний и внутренний слой [AISidebar.jsx](../src/components/AISidebar.jsx), заглушка [appFallbacks.jsx](../src/appFallbacks.jsx) (иначе при загрузке кода панель «прыгала» бы), и перетаскивание [useAIPanelResize.js](../src/hooks/useAIPanelResize.js) — там жёсткий потолок 600 заменён на `aiPanelMaxPx(window.innerWidth)`, иначе панель упиралась бы в невидимую стену (тянешь — число растёт, на экране ничего). `window.innerWidth` читается прямо в обработчике — это НЕ слушатель и НЕ хук.
⚠️ Ширину СПИСКА ЧАТОВ специально НЕ ограничивали — [code-todo.md](code-todo.md) TODO-40: «узкий вид» списка включается по числу из состояния, а не по реальной ширине, и потолок из вёрстки рассогласовал бы их (панель узкая, строки внутри широкие). Починили бы одно и сломали другое.

**КОРЕНЬ (🟢 доказан чтением кода и сохранённых настроек, не догадка)**
В главном ряду [App.jsx](../src/App.jsx) рядом стоят: боковая полоса (`shrink-0`) → СЕРЕДИНА (`flex-1`) → разделитель 6 точек (`shrink-0`) → панель ИИ.
1. Панель ИИ сжиматься НЕ умеет **по построению** ([AISidebar.jsx](../src/components/AISidebar.jsx)): внешняя обёртка `shrink-0` с жёсткой шириной из настроек, а внутренняя получает и `width`, и `minWidth`. На машине пользователя в `chatcenter.json` было `aiSidebarWidth = 458.4` при окне `1542`.
2. Середина — `flex-1`, но **без `min-width: 0`**. Правило вёрстки (уровень 1, спецификация CSS Flexbox: у флекс-элемента `min-width` по умолчанию `auto`): растягивающийся блок НЕ сжимается ниже минимальной ширины своего содержимого, пока это прямо не разрешить.
3. Внутри середины та же беда на два уровня глубже — ряд «список чатов + переписка» и сама область переписки в [InboxMode.jsx](../src/native/modes/InboxMode.jsx) тоже `flex: 1` без разрешения сжиматься.
4. Ряд помечен `overflow-hidden` → превышение НЕ давало прокрутки, а просто уходило за край. Отсюда «молча»: ни ошибки, ни записи в журнале.

**ЧЕГО В КОДЕ НЕТ ВООБЩЕ**: ни одна ширина панелей не сверяется с шириной окна (`window.innerWidth` для раскладки не используется нигде) — то есть окно могло стать любым, панели этого не замечали.
