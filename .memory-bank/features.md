### v1.2.129 — ВК: переносы строк/абзацы поста в уведомлении (не «простыня»)

Дата: 24 июля 2026. Жалоба (со скриншотом): длинный пост канала ВК приходит в карточке уведомления одной сплошной строкой — абзацы и пункты 1️⃣2️⃣ слиплись, хотя в самом ВК форматирование есть.

**Корень (по коду + MDN).** Текст строки списка собирает `_vkNodeText` ([vk.hook.js](../main/preloads/hooks/vk.hook.js)): обходит дочерние узлы, берёт текст и `alt` у картинок-эмодзи, но НЕ добавляет `\n` для `<br>` и блочных тегов — т.е. ведёт себя как `textContent`. Факт уровня 1 (MDN Node.textContent, <https://developer.mozilla.org/en-US/docs/Web/API/Node/textContent>): `textContent` НЕ отражает переносы от `<br>`/блочных элементов (в отличие от `innerText`, который учитывает рендер). У ВК переносы поста хранятся РАЗМЕТКОЙ (`<br>` / отдельные блоки-абзацы), а не символами `\n` → при сборе терялись. Прошлый фикс v1.2.122 (`_cleanMultiline` сохраняет `\n`) на этот случай не действовал: сохранять было нечего.

**Проверено, что виноват именно сбор (не показ/доставка).** Показ раскрытой карточки — `white-space:pre-wrap` ([notification.css:176,187](../main/notification.css)) + текст через `textContent` ([notification.js](../main/notification.js)) → переносы показались бы, если бы были. Обработчик входящих ([webviewHandleNewMessage.js:100-108](../src/utils/webviewHandleNewMessage.js)) убирает только хвост «#N», `\n` не трогает; отправка из хука через `JSON.stringify` сохраняет `\n`. На скрине текст пришёл ПОЛНЫЙ и в режиме переноса, но без абзацных разрывов → разрывов в тексте нет = потеря при сборе.

**Что сделано.** В `_vkNodeText`: `<br>` → `\n`; блочные теги (DIV/P/LI/UL/OL/BLOCKQUOTE/PRE/SECTION/ARTICLE) → перенос вокруг вложенного текста. `_cleanMultiline` (без изменений) схлопывает лишние пустые строки (максимум одна пустая). Эмодзи (img alt) и инлайн-теги (SPAN и пр.) не затронуты — инлайн НЕ добавляет переносов.

**Тест.** `vkNotifyLogic.vitest.js` +3: `<br>`→перенос; блочные абзацы (DIV/P)→перенос между ними; инлайн (SPAN) без лишних переносов. Функция грузится в тест регуляркой из реального файла (структура закрытия `\n  }` сохранена).

**Остаток (не закрыт).** Запасная ветка `_vkRowText` (когда спец-блок превью не найден — собирает листья через пробел + `_cleanToastText`, который `\s+`→пробел) переносы всё ещё теряет. Для каналов работает ОСНОВНАЯ ветка (есть `ChannelPostPreview`, матчит `preview`), поэтому этот пост чинится; для некоторых личных чатов возможна отдельная доработка.

**Проверка:** `node --check` OK; линт 0; лимиты 515/515 (`vk.hook.js` 253/300); `vkNotifyLogic` 12/12; `notifHooks` 87/87. **Ручная (нужен ПОЛНЫЙ перезапуск):** длинный пост канала ВК → в карточке абзацы и пункты по строкам, как в ВК.

Файлы: `main/preloads/hooks/vk.hook.js`, `src/__tests__/vkNotifyLogic.vitest.js`. Откат: `git checkout -- main/preloads/hooks/vk.hook.js src/__tests__/vkNotifyLogic.vitest.js` + вернуть версию на v1.2.128. Ловушка — [[webview-injection]].

### v1.2.128 — Уведомления: «невидимая стена» гаснет вместе с карточкой (по видимому, а не по счётчику)

Дата: 24 июля 2026. Жалоба: после закрытия уведомления (✕ / «Прочитано» / автотаймер) иногда остаётся невидимый след, ловящий клики; убирался только сторожем через ~15с. Требование юзера: гасить СРАЗУ при закрытии, а не через 15с.

**Корень (по коду).** Окно уведомления прячется, только когда список main `notifItems[]` становится пустым (`hideIfEmpty`, [notifHandlers.js]). Но в этом списке копятся «фантомы» от стопки/альбома (ghost-накопление — прямо задокументировано в комментариях #26). Спасательный сигнал «renderer пуст» (`rendererPure`) в `reportHeight` считался по числу записей ОКНА: `items.size===0 && container.children===0` ([notification.js:64]). Если после закрытия в `items`/DOM завис невидимый огрызок высотой 0 — счётчик >0 → `rendererPure=false` → `decideNotifResize` возвращает `ignore` (h≤0 && items>0) бесконечно ([notifResizeDecision.js]) → окно висит невидимым и ловит клики. В логе `IGNORE stale 0 (items=1)` ×196.

**Что сделано.** В `reportHeight(heartbeat, dismissFinal)` добавлен флаг `dismissFinal`. В финальном отчёте ПОСЛЕ завершения закрытия карточки (стадия 3, после `el.remove()`+`items.delete()`) вызывается `reportHeight(false, true)`. Если видимого на экране не осталось (`calcHeight()===0`), `rendererPure` становится `true` по ВИДИМОЙ высоте: `(itemsCount===0 && containerCount===0) || (dismissFinal && h===0)`. Тогда существующая ветка `clear-hide` очищает фантомы (`setNotifItems([])`) и прячет окно сразу.

**Почему безопасно.** Флаг ставится ТОЛЬКО в финале закрытия. Момент добавления карточки (slideIn, где `calcHeight===0` = карточка ещё выезжает) НЕ затронут — иначе окно пряталось бы преждевременно. Правило показа `decideNotifResize` не менялось (тест `notifResizeDecision.vitest.js` не затронут). Две разные карточки: закрыл одну → вторая видима (`calcHeight>0`) → окно остаётся (верно). `calcHeight` считает только видимые карточки (пропускает `pointerEvents:none` закрывающиеся и `slideInDone==='false'` выезжающие, [notification-helpers.js:40]).

**Факты.** (1 уровень) MDN `HTMLElement.offsetHeight` возвращает 0 для скрытых/удалённых элементов → `calcHeight()===0` надёжно = «видимого нет». (2 уровень) `rendererPure` формула — [notification.js:64]. (2 уровень) `clear-hide` только при `rendererPure` — [notifResizeDecision.js].

**Тестируемость (улучшение по ревью).** Формула сигнала вынесена из инлайна в чистую `computeRendererPure({ itemsCount, containerCount, visibleHeight, dismissFinal })` ([notification-helpers.js](../main/notification-helpers.js)) — тем же приёмом, что `decideNotifResize`. Оба места `reportHeight` (обычный отчёт + heartbeat) зовут её. Тест `albumLiveCard.vitest.js` (+5 проверок: пусто по записям; НЕ пусто при добавлении h=0; ПУСТО в финале закрытия при зависшем огрызке; НЕ пусто при второй видимой карточке; пустой вызов).

**Проверено родственного пути (`forceRemoveItem`).** Улучшение «закрыть тот же путь для выброса лишних» проверено и признано НЕ требующимся: оба вызова `forceRemoveItem` (дубль-id и FIFO-выброс) находятся ВНУТРИ `addNotification` и всегда сопровождаются добавлением карточки следом → окно пустым-но-видимым не остаётся by construction. См. code-todo TODO-13.

**Проверка:** `node --check` OK; линт 0; лимиты 515/515 (`notification.js` 726/730, `notification-helpers.js` 287/300); тесты `albumLiveCard`+`notifResizeDecision` 28/28. **Ручная (нужен ПОЛНЫЙ перезапуск — сейчас работает v1.2.127):** закрыть последнее уведомление любой кнопкой / дождаться автозакрытия → окно исчезает сразу, кликается всё под ним; стена не остаётся.

Файлы: `main/notification.js`, `main/notification-helpers.js`, `src/__tests__/albumLiveCard.vitest.js`. Откат: `git checkout -- main/notification.js main/notification-helpers.js src/__tests__/albumLiveCard.vitest.js` + вернуть версию на v1.2.127. Ловушка — [[notifications-ribbon]]. Сторож 15с оставлен запаской.

### v1.2.127 — Уведомления: heartbeat-сторож без спама в лог

Дата: 24 июля 2026. Доводка v1.2.126 по ревью (тот heartbeat спамил лог каждые 5с).

**Проблема.** v1.2.126: пока окно уведомления видимо, сторож каждые 5с писал `[notif-watchdog] alive` и слал `notif:remeasure` → renderer слал `notif:resize` → обработчик писал `[notif-resize]`. Для непропадающего уведомления (`dismissMs=0`) — бесконечный спам 2 строки/5с.

**Что сделано.** (1) Heartbeat (`notif:remeasure`) шлётся ТОЛЬКО когда окно давно молчит: `msSinceResize > 12000` мс — а не каждый тик. Пока окно активно отчитывается — не трогаем. (2) `reportHeight(heartbeat)` в `notification.js`: heartbeat-отчёт отдаёт только высоту + флаг `heartbeat:true`, БЕЗ диагностики (`reportHeight→resize` / DOM snapshot) — нет спама со стороны renderer. (3) Main НЕ логирует `[notif-resize]`, если это heartbeat-отчёт с действием `show` (реальные карточки — тихий no-op). (4) Убрана поштучная запись `alive`; вместо неё `[notif-watchdog] STUCK` — печатается ТОЛЬКО если после «поко» renderer НЕ ответил свежим `resize` (реальный признак застрявшей стены / мёртвого renderer), редко.

**Итог по логике:** реальные открытые карточки → раз в ~12с тихий переотчёт (без лога, no-op по bounds). Пустое/зависшее окно → heartbeat разбудит живой renderer (скроется через `clear-hide`), а если renderer мёртв — раз в ~12с строка `STUCK` (для добивания).

**Проверка:** `node --check` OK; лимиты 515/515 (`notification.js` 724/730, `notifHandlers.js` 233/500); `mainRuntime` 98/98; линт 0. **Ручная:** открыть уведомление на >12с — лог НЕ спамит (`[notif-resize]`/`alive` не идут каждые 5с); при появлении стены — строка `[notif-watchdog] STUCK`.

Файлы: `main/handlers/notifHandlers.js`, `main/notification.js`. Откат: `git revert` v1.2.127 (вернётся спамящий heartbeat v1.2.126). Ловушка — [[notifications-ribbon]].

### v1.2.126 — Уведомления: закрыта дыра «невидимой стены» (heartbeat-сторож)

Дата: 24 июля 2026. Возврат бага «после уведомления остаётся невидимый след, ловящий клики».

**Что показал лог.** Два цикла: первый закрылся чисто (renderer дошёл до `rendererPure=true` → окно спрятано). Второй ЗАСТРЯЛ: счётчик карточек упал 5→4, renderer прислал транзиентный `raw=0 items=4 rendererPure=false` (корректно проигнорирован как «стале-0 при items>0»), и ПОСЛЕ ЭТОГО отчёты `notif:resize` оборвались — окно осталось `visible`, события hide не было.

**Корень (дыра в защите).** Вся защита от «стены» завязана на «карточек = 0»: `decideNotifResize` ([notifResizeDecision.js](../main/handlers/notifResizeDecision.js)) прячет только при `h<=0` (0/осиротевший) или `rendererPure`; сторож ([notifHandlers.js](../main/handlers/notifHandlers.js)) гасит только `isVisible && getNotifItems().length===0`. Если renderer перестал слать размер, а счётчик main остался >0 — НИ проверка размера, НИ сторож не срабатывают → окно висит на старых (высоких) bounds, его пустая часть ловит клики. (Прошлые фиксы v1.2.106-107 закрыли только ветку «items===0», эту — нет.)

**Фикс (heartbeat + запись).** (1) Сторож (`setInterval` 5с): пока окно НА ЭКРАНЕ (bounds не в минусах), шлёт `notif:remeasure` → renderer вызывает существующую `reportHeight()` → авторитетный отчёт проходит через ту же `decideNotifResize`. Живой renderer поправит размер (если bounds устарели) или скроется (если пуст → `rendererPure=true` → `clear-hide`) — даже при счётчике>0. Для реально показанных карточек это no-op (та же высота → `lastNotifBounds` совпадает → без `setBounds`). (2) Подробная запись `[notif-watchdog] alive items=… bounds=… msSinceResize=… onTop=…` — ловит застрявшую стену; если heartbeat не помог (msSinceResize растёт) — значит «мёртвый renderer», добьём прицельно. Каналы: `notification.preload.cjs` `onRemeasure`, `notification.js` `onRemeasure?.(reportHeight)`.

**Крайние случаи.** Скрытое/офскрин окно (safeHide уводит в минус) — heartbeat не шлётся (проверка `onScreen`). Реальные карточки — heartbeat даёт тот же размер, окно не дёргается. `focusable:false`/прозрачность не затронуты. Взаимодействие с v1.2.125: «пружина» держит стену поверх всех, поэтому heartbeat важен вдвойне (иначе стена ещё и сверху).

**Проверка:** `node --check` (3 файла) OK; лимиты 515/515 (`notification.js` 722/730, `notifHandlers.js` 224/500, preload 59/600); `mainRuntime` 98/98; линт 0. **Требует визуальной проверки:** поймать стену снова → прислать строки `notif-watchdog alive` (ожидается, что heartbeat её убирает; если нет — лог покажет «мёртвый renderer»).

Файлы: `main/handlers/notifHandlers.js`, `main/preloads/notification.preload.cjs`, `main/notification.js`. Откат: `git revert` v1.2.126 (уберёт heartbeat+запись, вернётся сторож только на `items===0`). Ловушка — [[notifications-ribbon]].

### v1.2.125 — Уведомления: окно надёжно «поверх всех» (высокий уровень + reassert)

Дата: 24 июля 2026. Фикс: окно уведомления иногда уходило за окна других программ.

**Проблема.** Модалка уведомления должна быть всегда сверху, но иногда её перекрывали чужие окна (напр. редактор кода).

**Причина (по коду).** `createNotifWindow` ([notificationManager.js]) ставил простой `alwaysOnTop: true` (низкий уровень «поверх всех») и НЕ переустанавливал верх. Полоска задач же ([dockPinState.js], фиксы v1.2.61-63, подтверждены рабочими) использует `setAlwaysOnTop(true, 'screen-saver', 1)` — самый высокий уровень (по документации Electron `setAlwaysOnTop`) — плюс периодический возврат наверх, потому что Windows опускает topmost-окно при переключении окон / клике по панели задач. Уведомлению этот приём не достался.

**Что сделано.** Окну уведомления добавлено то же, что у дока: (1) `notifWin.setAlwaysOnTop(true, 'screen-saver', 1)` сразу после создания и в обработчике события `show` (мгновенно наверх при каждом показе); (2) «пружина» — `setInterval` раз в 1с: пока окно ВИДИМО (`isVisible()`), снова поднимает наверх. `setAlwaysOnTop` не крадёт фокус, `focusable:false` сохранён. Таймер `notifTopTimer` останавливается в обработчике `closed` (не тикает после уничтожения окна; при скрытом окне тик — no-op).

**Крайние случаи / проверки.** `node --check` OK; `mainRuntime` 98/98 (парсинг+рантайм main); лимит `notificationManager.js` 334/500; линт 0. Тик interval при скрытом/уничтоженном окне защищён проверками `isDestroyed()`/`isVisible()`.

**Остаток (предел Windows, не наш баг).** Над полноэкранной игрой или системным окном даже уровень `screen-saver` может не встать — это ограничение ОС, не лечится. Полоска задач и уведомление оба на `screen-saver` — при полном наложении (низ-право) теоретически возможен спор z-порядка, на практике почти не пересекаются.

**Требует визуальной проверки:** уведомление стабильно поверх редактора/браузера/других окон при переключении между ними.

Файл: `main/handlers/notificationManager.js`. Откат: убрать `setAlwaysOnTop('screen-saver')` + `notifTopTimer` (вернётся простой `alwaysOnTop: true`), или `git revert` v1.2.125. Ловушка — [[notifications-ribbon]].
