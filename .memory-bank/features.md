### v1.2.134 — ВК: основной адрес vk.ru + убрана лишняя красная ошибка запасного впрыска (вариант А)

Дата: 2026-07-27. Две связанные правки по ВК.

**1. Основной адрес ВК → vk.ru.** Стартовый URL вкладки ВК был `https://vk.com/im` (сам редиректил на vk.ru — лишний перескок). Теперь `https://vk.ru/im` в трёх местах: [constants.js](../src/constants.js) (×2) и [main.js](../main/main.js) (список мессенджеров, `isDefault`). Распознавание «это ВК?» ОСТАВЛЕНО понимающим оба (`vk.com` ИЛИ `vk.ru`) — безвредная страховка + этого требует тест `messengerConfigs.vitest.js`.

**2. Убрана красная ошибка `GUEST_VIEW_MANAGER_CALL` при старте (вариант А).** При каждом запуске в лог падала красная `[ERROR] GUEST_VIEW_MANAGER_CALL … Script failed to execute` + `VK-EXEC inject failed`. КОРЕНЬ (по коду + логу + истории): у ВК исторически ТРИ слоя ловли сообщений — (1) основной перехватчик списка чатов на vk.ru (console-путь, `vk-list`, v1.2.112) — РАБОТАЕТ; (2) запасной `executeJavaScript`-впрыск `vkExecFallback` (v1.2.46, для старого vk.com toast/sidebar); (3) «журнал явки» `monitor-ready` (heartbeat через preload) — координатор, включающий запасной ТОЛЬКО если основной не отметился. Диагностика (лог) показала: `monitor-ready` НЕ приходит НИ ОТ КОГО (`journalKeys=(пусто)`, `[IPC-*]`=0) — служебный ipc-канал preload молчит у всех мессенджеров. Поэтому гейт «основной жив» никогда не срабатывал → запасной впрыск запускался КАЖДЫЙ раз → на vk.ru он блокируется защитой страницы (CSP) → красная ошибка. Уведомления ВК при этом идут через слой (1), не через (2).

**Фикс (вариант А):** в `vkExecFallback.schedule` ([shared/vkExecFallback.js](../shared/vkExecFallback.js)) добавлен ранний выход, если адрес вкладки `vk.ru` — запасной впрыск там НЕ планируется (основной путь работает; впрыск всё равно блокируется — страховки на vk.ru нет в любом случае). Для `vk.com` (если встретится) поведение сохранено. Временная диагностика v1.2.13x (`[diag-vk-ipc]` в webviewSetup + `journalKeys/msSince` в vkExecFallback) удалена.

**Почему не вариант Б (чинить журнал):** журнал `monitor-ready` молчит у ВСЕХ мессенджеров (общая скрытая недоработка preload-ipc) — чинить его ради глушения одного лишнего слоя = «подпорка к подпорке» + риск для всех. Вариант А убирает лишний слой прямо. Побочная находка (отдельная задача): preload-ipc heartbeat не работает нигде; на уведомления не влияет (работают console-пути), но счётчики непрочитанного через тот канал могут быть неточны.

**Проверка:** `node --check` OK; `npm run lint` 0; тест `vkExecFallback` 17/17; синтаксис constants/main OK. **Ручная (нужен ПОЛНЫЙ перезапуск):** в логах ВК больше НЕТ `GUEST_VIEW_MANAGER_CALL`/`VK-EXEC inject failed`; уведомления ВК приходят; вкладка ВК открывается сразу на vk.ru. Откат: `git checkout -- shared/vkExecFallback.js src/utils/webviewSetup.js src/constants.js main/main.js` + версия на 1.2.133. См. [[decisions]] ADR-023.

### v1.2.129 — ВК: переносы строк/абзацы поста в уведомлении (не «простыня»)

Дата: 24 июля 2026. Жалоба (со скриншотом): длинный пост канала ВК приходит в карточке уведомления одной сплошной строкой — абзацы и пункты 1️⃣2️⃣ слиплись, хотя в самом ВК форматирование есть.

**Корень (по коду + MDN).** Текст строки списка собирает `_vkNodeText` ([vk.hook.js](../main/preloads/hooks/vk.hook.js)): обходит дочерние узлы, берёт текст и `alt` у картинок-эмодзи, но НЕ добавляет `\n` для `<br>` и блочных тегов — т.е. ведёт себя как `textContent`. Факт уровня 1 (MDN Node.textContent, <https://developer.mozilla.org/en-US/docs/Web/API/Node/textContent>): `textContent` НЕ отражает переносы от `<br>`/блочных элементов (в отличие от `innerText`, который учитывает рендер). У ВК переносы поста хранятся РАЗМЕТКОЙ (`<br>` / отдельные блоки-абзацы), а не символами `\n` → при сборе терялись. Прошлый фикс v1.2.122 (`_cleanMultiline` сохраняет `\n`) на этот случай не действовал: сохранять было нечего.

**Проверено, что виноват именно сбор (не показ/доставка).** Показ раскрытой карточки — `white-space:pre-wrap` ([notification.css:176,187](../main/notification.css)) + текст через `textContent` ([notification.js](../main/notification.js)) → переносы показались бы, если бы были. Обработчик входящих ([webviewHandleNewMessage.js:100-108](../src/utils/webviewHandleNewMessage.js)) убирает только хвост «#N», `\n` не трогает; отправка из хука через `JSON.stringify` сохраняет `\n`. На скрине текст пришёл ПОЛНЫЙ и в режиме переноса, но без абзацных разрывов → разрывов в тексте нет = потеря при сборе.

**Что сделано.** В `_vkNodeText`: `<br>` → `\n`; блочные теги (DIV/P/LI/UL/OL/BLOCKQUOTE/PRE/SECTION/ARTICLE) → перенос вокруг вложенного текста. `_cleanMultiline` (без изменений) схлопывает лишние пустые строки (максимум одна пустая). Эмодзи (img alt) и инлайн-теги (SPAN и пр.) не затронуты — инлайн НЕ добавляет переносов.

**Тест.** `vkNotifyLogic.vitest.js` +3: `<br>`→перенос; блочные абзацы (DIV/P)→перенос между ними; инлайн (SPAN) без лишних переносов. Функция грузится в тест регуляркой из реального файла (структура закрытия `\n  }` сохранена).

**Остаток (не закрыт).** Запасная ветка `_vkRowText` (когда спец-блок превью не найден — собирает листья через пробел + `_cleanToastText`, который `\s+`→пробел) переносы всё ещё теряет.
