### v1.2.69 — Док: hover-подсказка убрана (петля дёрга невозможна структурно) + дед-бэнд

Дата: 17 июля 2026. Свежий лог `[dock-bounds]` (16:39-40) показал: cooldown из v1.2.68 петлю НЕ убрал — `preview-grow`(h37→129)↔`preview-shrink`(h129→37) по-прежнему шли парами 2-3/с. `bottomMoved=false` везде (низ не двигается — привязка ок). Плюс `src=resize` с ползущим низом (`816→817→818`) и дрожанием x при тиках.

Проверка окна уведомлений (по требованию юзера «проблема была и с другими окнами»): в логе `[notif-window]` только `move`/`hide`, петли grow/shrink НЕТ. Ключ: окно уведомлений НЕ меняет размер при наведении. Значит структурная причина петли дока — именно ресайз окна на hover (под подсказку): рост окна под курсором → Windows шлёт ложные `mouseleave`/`mouseenter` → hide→shrink→show→grow → цикл. Cooldown это лишь глушил, но не всегда успевал.

Решение (как в окне уведомлений — не ресайзить на hover):
1. **Убрана всплывающая подсказка при наведении** ([pin-dock.js](../main/pin-dock.js)): удалены hover-listeners (`mouseenter`/`mouseleave`) и функция `showPreview`. Окно дока больше НЕ растёт на наведение → петля невозможна структурно (не заглушена, а исключена). Контент задачи открывается кликом (разворот карточки). `hidePreview` оставлена как безопасный no-op (вызовы на клике/меню/удалении не трогали).
2. **Дед-бэнд в `dock:resize`** ([dockPinHandlers.js](../main/handlers/dockPinHandlers.js)): при микро-изменении (Δширина≤6, Δвысота≤4, Δx≤6, Δy≤4) и видимом окне — `return` без `setBounds`. Гасит «медленный уход вниз»/дрожание от тиков таймера и мутаций.

Диагностический `[dock-bounds]` оставлен ещё на раунд: подтвердить, что строк `preview-grow/shrink` больше НЕТ вообще, а `src=resize` не идёт пачками.

Компромисс (честно): всплывающая подсказка-«краткое содержание» при наведении удалена — это цена за гарантированное отсутствие петли (полумеры не сработали). Если подсказка нужна — её можно вернуть отдельным окном-тултипом, которое НЕ ресайзит док (отдельная задача).

Проверки: `node --check` обоих, `npm run lint`, `npm run check-memory`. Визуально после ПОЛНОГО перезапуска: навести на вкладку — ничего не мигает, панель стоит; в логе нет `preview-grow/shrink`.

### v1.2.65 — Закреплённое переживает перезапуск (баг персистентности)

Дата: 17 июля 2026. Кто нашёл: пользователь — закреплённые задачи не сохраняются после перезапуска.

Проверка перед правкой (может это уже есть): сохранение/загрузка закрепа **уже реализованы** (v0.72.1) — `savePinItems()` → `storage.set('pinItems')`, `loadPinItems()` при старте → `restorePin`. Значит функция есть, но не работает.

Корень (факт из данных): на диске `ЦентрЧатов/chatcenter.json` (живой, mtime сегодня) — `"pinItems": []`, хотя закреплённые есть на экране. Причина: обработчик `'closed'` окна закрепа делает `pinItems.delete(pinId)` + `savePinItems()` ([dockPinHandlers.js](../main/handlers/dockPinHandlers.js), [dockPinState.js](../main/handlers/dockPinState.js)). При ВЫХОДЕ из приложения Electron закрывает все окна закрепа → у каждого срабатывает `'closed'` → пины по одному удаляются из Map, а storage перезаписывается пустым списком. Итог: сохранять нечего при следующем старте. Персистентность сама себя стирала на выходе.

🥇 Electron: `app` эмитит `before-quit` ДО закрытия окон; окна затем шлют `'closed'`. Значит выход можно распознать флагом.

Фикс: флаг `isQuitting` по `app.on('before-quit')` (в `initDockPinSystem`), проброшен в `createDockPinState` как геттер. Оба `'closed'`-обработчика (создание в dockPinHandlers, восстановление в dockPinState) в начале: `if (isQuitting) return` — на выходе НЕ трогаем storage. Последнее нормальное сохранение (с пинами) остаётся и восстанавливается при старте.

Не затронуто: явное открепление (кнопка ✕ / `pin:unpin` / `dock:unpin`) идёт через `removePin`, который удаляет и сохраняет ДО закрытия окна; его `'closed'` уже был no-op (item удалён) — поведение сохранено.

Конфликты/граничные: `before-quit` фиксирует выход один раз; если пользователь отменит выход (в этом приложении не бывает) — флаг останется true (мелкий edge). На выходе таймеры не чистятся в guard — процесс всё равно завершается.

Проверки: `node --check` обоих файлов, `npm run lint`, `npm run check-memory`, тесты области. Визуально: закрепить сообщение → **полностью закрыть программу** → открыть заново → закреплённое на месте. (Storage сейчас `[]` из-за прошлых стираний — после обновления закрепите заново, потом перезапуск.)

Откат: `git checkout -- main/handlers/dockPinHandlers.js main/handlers/dockPinState.js`.

### v1.2.64 — Док: полоска не дёргается при появлении подсказки/меню

Дата: 17 июля 2026. Кто нашёл: пользователь — при наведении открывается подсказка, но сама полоска дока дёргается и уезжает вниз; то же при закрытии.

Корень: в [pin-dock.css](../main/pin-dock.css) полоска дока была **flex-ребёнком** при `html,body { justify-content:flex-end; min-height:100vh }`. Начиная с v1.2.62 окно дока растёт/сжимается по требованию (под подсказку/меню, `dock:preview-space`/`dock:ctx-menu-space`). При каждом росте/сжатии `100vh` менялся → раскладка пересчитывалась → полоска на миг перескакивала вниз = «дёрг». Это ровно тот layout-shift, что описан в памяти sticky-overlay (v0.95.5): блок над областью с меняющимся размером нельзя делать flex-child.

Фикс: полоска приклеена к низу окна через `#dock-wrapper { position:fixed; bottom:0; left:0 }` вместо `flex-end + min-height:100vh`. Теперь окно растёт вверх прозрачной зоной (для подсказки/меню), а полоска остаётся приклеенной к низу и не двигается. Эталоны паттерна: Telegram Web K `_chatPinned.scss`, WhatsApp Web.

Проверка других модалок (по просьбе): карточка закрепа [pin-notification.html](../main/pin-notification.html) и лента уведомлений `flex-end + min-height:100vh` НЕ используют (карточка растёт вниз от фиксированного верха) — этим дёргом не страдают, не тронуты.

Связь с задокументированной историей (тот же корень — «native `setBounds` на Windows не плавный»): у ЛЕНТЫ УВЕДОМЛЕНИЙ этот класс уже ловили — ловушки #22/#23 в [mistakes/notifications-ribbon.md](./mistakes/notifications-ribbon.md) («пустая полоса» при resize + stale `resize(0)`) и ADR-принцип «анимация CSS внутри окна, `setBounds` только на финальную высоту». Но лента top-anchored (растёт вниз) → её решали ТАЙМИНГОМ (не считать не-осевший контент, игнор stale-resize). Док bottom-anchored (растёт вверх) → тайминг не применим, правильное решение — sticky-bottom (`position:fixed`), что согласуется с тем же принципом: видимая полоска не зависит от native-resize. Подсказка дока уже запрашивает рост окна после измерения своей высоты (контент осел) — соответствует уроку ловушки #22.

Совет A (пересоздание главного окна) — проверен и признан НЕ нужным: главное окно пересоздаётся лишь через `app.on('activate')` (macOS); на Windows `window-all-closed` → `app.quit()` ([main.js:491-495](../main/main.js)), т.е. мид-сессия окно не пересоздаётся, флаг-хук v1.2.63 не устаревает. Делать не стали (минимальное касание).

Конфликты/граничные: подсказка (`.dock-preview`) позиционируется относительно `.dock-tab` (position:relative) — смена `#dock-wrapper` на fixed это не ломает; контекстное меню — `position:fixed` в body, не зависит от wrapper; ширину/высоту окна `reportSize` считает по `#dock` (не изменилось).

Проверки: `npm run lint`, `npm run check-memory`, лимиты файлов (css 800). Визуально: наведение на задачу → подсказка появляется, полоска НЕ дёргается; закрытие подсказки/меню → тоже без дёрга.

Откат: `git checkout -- main/pin-dock.css`.

**Совет 1 — мгновенный возврат (реализовано):** `reassertDockTop()` (`setAlwaysOnTop('screen-saver')`, не крадёт фокус, только при видимом доке) вешается на события главного окна `blur/focus/minimize/restore`. ### v1.2.58 — VK: внутренний тост подключён к основному hook, а не только к fallback

Дата: 7 июля 2026. Кто нашёл: пользователь по кейсу VK-профиля `https://vk.com/lynxdas`; Codex по `system-diagnostics-report.json`, `chatcenter.log`, `main/preloads/hooks/vk.hook.js`, `shared/vkExecFallback.js`.

Что показала диагностика: `vkFull` видел текст VK-плашки в `bodyTextSample`, но в сохранённой диагностике было `0` событий `vk-toast`, `toast-candidate`, `toast-scan`, `emit-toast`, `source=vk-toast`. На странице профиля также было `containerFound=false`, `messageCount=0`, `sidebar=[]`, поэтому активная история и sidebar физически не могли создать уведомление. В логе был риск `VK-EXEC inject failed`, а код `shared/vkExecFallback.js` дополнительно показал, что `VK-EXEC` пропускается при живом `monitor-ready` (`VK preload alive -> VK-EXEC skip`).

Почему v1.2.57 не закрыла проблему полностью: идея `source:'vk-toast'` была правильной, но наблюдатель был добавлен только в резервный `VK-EXEC fallback`. Этот fallback не является основным путём: он запускается только когда preload не подал heartbeat, и ещё может упасть на `executeJavaScript`. Значит при нормальном живом preload VK-плашка могла быть видна диагностике, но не попадала в рабочую цепочку уведомления.

Что исправлено сейчас: `main/preloads/hooks/vk.hook.js` получил основной `__ccVkPrimaryToastObserver`. Он ставится вместе с VK notification hook на любой странице `vk.com`, наблюдает DOM за компактной видимой плашкой `Новое сообщение` / `New message`, извлекает отправителя, текст плашки и аватарку, затем отправляет обычный `__CC_NOTIF__` с `src:'vk-toast'` и стабильным `g:'vk-toast:<hash>'`.

Почему это безопасно:
- `VK-EXEC`, `vk-sidebar-unread` и active-history guard не удалены и не ослаблены;
- старые DOM-сообщения активной истории по-прежнему блокируются через `source:'vk-exec-fallback'` без `vkActiveUnread`;
- sidebar по-прежнему требует unread badge и fresh/selected правила;
- новый путь реагирует только на собственную VK-плашку с меткой `Новое сообщение`, а не на произвольный текст страницы;
- неполный тост остаётся диагностикой `block-incomplete-toast` и не создаёт карточку;
- MAX, Telegram, WhatsApp и API-источники не затронуты.

Как должно работать после исправления: если пользователь находится на профиле/ленте/фото VK и VK показывает внутреннюю плашку нового личного сообщения, в диагностике должна появиться цепочка `__CC_DIAG__vk-toast primary-bound` -> `__CC_DIAG__vk-toast candidate decision=emit-toast` -> `__CC_NOTIF__ src=vk-toast` -> `handle` -> `sound` -> `ribbon`. Если VK в плашке не отдаёт настоящий текст сообщения, ChatCenter не должен выдумывать его: карточка показывает ровно тело VK-плашки, например `прислала вам личное сообщение`.
