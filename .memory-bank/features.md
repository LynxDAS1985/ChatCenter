### v1.2.429 — Убрано предупреждение MaxListenersExceeded (11 did-stop-loading) + закрыт TODO-34

**Что**: в журнале красным светилось `MaxListenersExceededWarning: 11 did-stop-loading listeners added to [WebContents]`. Это предупреждение (не падение).

Проявилось 1 раз при долгом dev-старте.

**ФИКС**: (1) удалена отработавшая временная диагностика `process.on('warning')` из [main.js](../../main/main.js) (TODO-34 закрыт — стек найден); (2) `app.on('web-contents-created')` → `wc.setMaxListeners(30)` для всех webContents — предупреждение больше не шумит (это и рекомендует само сообщение Electron: «Use emitter.setMaxListeners()»). Порог поднят, а не снят (0=безлимит скрыл бы настоящую утечку, если появится).

**Примечание**: по своей заметке TODO-34 «если стек — внутренние файлы Electron → лимит не трогать» — но пользователь явно попросил убрать шум из журнала, а поднять предел безопасно (слушатели самоснимающиеся). ### v1.2.426 — МАКС: убран ДУБЛЬ карточки уведомления (наблюдатель + список на одно сообщение) — наблюдатель ждёт enriched дольше

**Жалоба**: на одно входящее сообщение МАКС всплывали ДВЕ карточки — одна с аватаркой, одна без.

**РАЗБОР «почему сломалось» (по журналу + истории проекта)**: у МАКС по замыслу ТРИ пути уведомлений — главный (его SW-`showNotification`) + два запасных (наблюдатель активного чата `__CC_MSG__`/`new-message` и сканер списка `max-sidebar`). Склейка держится на том, что запасной `__CC_MSG__` ЖДЁТ `enriched __CC_NOTIF__` (с аватаркой) и отменяется им ([consoleMessageHandler.js:391-397](../../src/utils/consoleMessageHandler.js)). Факты из журнала (`chatcenter.log`, сеанс v1.2.425): за весь сеанс **0 докладов главного пути** (`max-sw`), только `max-sidebar` (×10) → главный молчит (сам МАКС не звонит про ОТКРЫТЫЙ чат). А два запасных дали id=33 (наблюдатель, `icon:false`, без фото) и id=34 (`max-sidebar`, `icon:true`, с фото) на одно сообщение. Дубли вылезли ПОСЛЕ починки чёрного экрана (v1.2.423): раньше МАКС был «слепой» → запасные молчали.

**КОРЕНЬ (доказан)**: окно ожидания enriched у наблюдателя = **200 мс** ([consoleMessageHandler.js:347](../../src/utils/consoleMessageHandler.js)), а сканер списка МАКС троттлится **~350 мс** ([max.hook.js:294](../../main/preloads/hooks/max.hook.js)) → `max-sidebar __CC_NOTIF__` приходит ПОЗЖЕ 200 мс → наблюдатель не дожидается, показывает карточку без фото, потом приходит карточка с фото = две.

**ФИКС (минимальный, в существующем механизме)**: для МАКС окно ожидания enriched увеличено с 200 мс до **1200 мс** (`enrichWaitMs`, гейт `/web\.max\.ru/`). Теперь «карточка из списка» (с фото) успевает прийти и ОТМЕНИТЬ наблюдателя → остаётся одна карточка с аватаркой. Ключи склейки НЕ тронуты (защита «разные клиенты — один текст» из истории цела). Прочие мессенджеры — 200 мс без изменений. Опора на MDN `setTimeout`/`clearTimeout` (продлённая задержка даёт enriched-событию прийти и отменить таймер).

**Остаточный риск**: на ОЧЕНЬ медленной машине список может прийти позже 1200 мс → дубль вернётся (маловероятно: троттл 350 мс, запас ×3). Если появится — поднять `enrichWaitMs`.

Файлы: `src/utils/consoleMessageHandler.js` (459/462), `src/__tests__/notificationIdentity.test.cjs` (+тест-ловушка `enrichWaitMs`), `src/__tests__/fileSizeLimitsExceptions.cjs` (458→462). Проверки: линт 0; лимиты 607/607; notificationIdentity 10/10; полный vitest. **Требует ПОЛНОГО перезапуска + визуальной проверки** (входящее в МАКС → ОДНА карточка с фото). [[decisions]] ADR-041 дополнен.

**Находка #2 (🟡, ОСОЗНАННОЕ РЕШЕНИЕ — код НЕ менялся, см. Для ИСХОДЯЩИХ это даже правильнее прежнего (раньше свои сообщения ошибочно шли в статистику/автоответ).

### v1.2.423 — ФИКС чёрного экрана веб-МАКС: sandbox=no у `<webview>` МАКС (песочница ломала сокет) — единственное отличие от рабочего отдельного окна

**КАК НАШЛИ (доказательство, а не гипотеза)**: после 3 неудачных правок (пинок/SW/UA) и цепочки диагностик (сокет рвётся, не HTTP-429, не main-world WebSocket) — предложил пользователю ГОТОВЫЙ обходной путь: тумблер «🧪 Макс в отдельном окне» (`settings.useWebContentsView` → [maxTestWindowHandler.js](main/handlers/maxTestWindowHandler.js) открывает МАКС в обычном `BrowserWindow`). **Пользователь подтвердил: в отдельном окне МАКС РАБОТАЕТ полностью** (чаты, фото). А партиция и preload там ТЕ ЖЕ → значит дело НЕ в сессии, а в самом `<webview>`. Сравнил настройки: отдельное окно имеет `sandbox: false`, а `<webview>` МАКС — sandbox по умолчанию ВКЛючён. **Это единственное отличие.**

**КОРЕНЬ**: «песочница» (sandbox — усиленная изоляция рендера) у `<webview>` ломает сокет МАКС (WebSocket в Web Worker / транспорт) → `Socket disconnected` → МАКС переподключается по кругу → свой лимит «Too many requests» (~1740/сек) → чат не грузится → ЧЁРНЫЙ ЭКРАН. В отдельном окне (sandbox выключен) и в браузере — сокет живёт.

**ЧТО** ([App.jsx](src/App.jsx)): `webpreferences` вкладки для МАКС дополнен `,sandbox=no` (как в рабочем отдельном окне). Гейт по URL `/\bmax\.ru/i` — **только МАКС**; Telegram/ВК/WhatsApp/Ozon остаются в песочнице (у них проблемы нет).

**КАК РАБОТАЕТ / ОТКАТ**: `webpreferences` читается при создании `<webview>` → нужен ПОЛНЫЙ перезапуск. Откат — `git checkout src/App.jsx`.

**КАК ПРОВЕРЕНО**: линт 0; лимиты 606/606; appStructure 60/60; полный vitest. **Требует ПОЛНОГО перезапуска + визуальной проверки** (МАКС во ВСТРОЕННОЙ вкладке открывается с чатами и фото, без чёрного/шторма). Тумблер «отдельное окно» после этого можно выключить.

### v1.2.416 — ФИКС чёрного экрана веб-МАКС: возвращён РЕАЛЬНЫЙ 1px-пинок раскладки при активации вкладки (Ловушка 64)

Это НЕ «Too many requests» (тот `health[err]` был побочным шумом, на нём я сначала ошибочно застрял) — это **layout lock-in адаптивного SPA** ([[webview-stack-grouping]] Ловушка 64): МАКС (Svelte SPA) при инициализации в НЕактивной вкладке (`zIndex:0, pointerEvents:none`) читает неверный/узкий первичный размер через `ResizeObserver` → фиксирует «мобильную» раскладку → область чата схлопывается в 0×0 → чёрное. После активации окно РЕАЛЬНО не меняет размер → ResizeObserver молчит → остаётся схлопнутым.

**ПОЧЕМУ раньше работало, а теперь нет**: фикс (реальный пиксельный ресайз) БЫЛ (v0.86.8), но его УДАЛИЛИ при переводе Telegram на нативный TDLib-канал (весь webview-recovery код убрали). Веб-МАКС остался webview — и без лечения.

Guest реально видит resize → `ResizeObserver` пересчитывает layout → область чата разворачивается. Лог `[webview-relayout] 1px-пинок раскладки для <id>`. **Синтетический `dispatchEvent('resize')` НЕ используем** — SPA слушают ResizeObserver = только РЕАЛЬНЫЙ пиксельный delta (доказано в Ловушке 64).

**КАК РАБОТАЕТ / ОТКАТ**: применяется ко ВСЕМ веб-вкладкам (МАКС/WhatsApp/ВК/Ozon) — тем, кому не нужно, 1px-пинок безвреден (просто пересчёт). Native (TDLib) вкладки не трогаются. Откат — `git checkout src/hooks/useWebViewLifecycle.js`.

**КАК ПРОВЕРЕНО**: линт 0; лимиты 605/605; appStructure 60/60; полный vitest. **Требует ПОЛНОГО перезапуска** (не хот-релоад: добавление хука на лету даёт разовую ошибку React «Rendered more hooks» — это артефакт HMR, при полном старте её нет) + визуальной проверки (МАКС открывается с чатами, не чёрный).

**ГРАНИЦА**: если у МАКС окажется НЕ layout lock-in, а внутренняя гонка (как Telegram K `peer-changed`, которую пиксельный ресайз не лечил) — понадобится полный reload вкладки; пока ставим на layout lock-in (симптом совпадает).
