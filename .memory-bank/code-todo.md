## ✅ РЕШЕНО

### ✅ TODO-markread-gap (РЕШЕНО v0.94.7): «дыра» в пометке-прочитанным — read-by-visibility прыгал через провал → каскадная пометка всего бэклога

**Симптом** (лог 27 мая, топик Xiaomi Home `tg_611696632:-1001295734575:topic:281172`): чат с 8624 непрочитанными; юзер пролистал ~100 → счётчик упал до 88. Не глюк отображения — реальная пометка прочитанным.

**Корень**: `useReadByVisibility` ([src/native/hooks/useReadByVisibility.js](../src/native/hooks/useReadByVisibility.js)) копит id видимых сообщений и шлёт `markRead(chatId, lastReadMax, {source:'visibility'})` с САМЫМ ВЫСОКИМ увиденным id — без проверки на «провал» (gap) в загруженном окне. Backend: `viewMessages(client, rawId, [maxId], force_read:true)` ([tdlibBackend.js:340-346](../main/native/backends/tdlibBackend.js)); `force_read:true` двигает `readInboxMaxId` к maxId ([tdlibMessages.js:219](../main/native/backends/tdlibMessages.js)) → TDLib помечает прочитанным ВСЁ ≤ maxId. Если в окне разрыв (старые непрочитанные ~490млрд + свежие ~513млрд, между — не загружено) и видимым стало свежее → курсор прыгает на 513млрд → 8000+ старых помечаются прочитанными разом.

**Защита есть, но с дырой**: `markReadCurrentView` ([InboxMode.jsx:233-244](../src/native/modes/InboxMode.jsx)) пропускает markRead при `unreadWindowIncomplete`, НО только если `source !== 'visibility'`. Visibility-пометка проходит → защита не срабатывает (в логе `mark-read-skip-unread-window` = 0).

**Кандидаты решения** (зона markRead — была болезненная история «было 7 стало 1» v0.87.44, чинить с планом + тестом на реальной сессии):
1. **Контигуити-guard**: не двигать read-курсор через незагруженный провал — только по непрерывному ряду от cursor. Минус: нужно, чтобы store помечал gap между загруженными диапазонами (сейчас не помечает явно).
2. **force_read=false для visibility-пометки при неполном окне**: TDLib не форсит курсор через невидимое. Минус: проверить, что обычная пометка не ломается (force_read добавляли намеренно).
3. **Не префетчить свежие (load-newer), пока бэклог непрочитанных не пройден**: убирает сам провал. Минус: трогает загрузку (риск для скролл-фикса v0.94.2).

**Рекомендация**: вариант 2 (минимальный, точечный) — но СНАЧАЛА сверить TDLib docs на `force_read` + план + тест на реальной сессии. НЕ чинить вслепую.

**Приоритет**: ✅ РЕШЕНО в v0.94.7 — в [useReadByVisibility.js](../src/native/hooks/useReadByVisibility.js) добавлен гейт: если read-курсор прыгает `>200` сообщений И `>×5` от реально увиденного — пометка пропускается (курсор откатывается на непрерывный фронтир, self-heal при дозагрузке разрыва). Тот же mass-ack-guard, что в useForceReadAtBottom. Тесты +2. См. features.md v0.94.7.

### TODO-17: значок 📌 в компактном (узком) режиме списка чатов

**Контекст (v1.2.138):** при закреплении чат помечается полоской слева (3px, цвет `#f5b301`) и значком 📌 перед именем. Но в КОМПАКТНОМ режиме (узкий список — одни кружочки-аватарки) значок 📌 не виден: в [ChatListItem.jsx](../src/native/components/ChatListItem.jsx) компактная ветка `if (compact)` выходит РАНЬШЕ блока имени (там 📌), поэтому в узком виде остаётся только тонкая полоска — её легко не заметить.

**Что сделать:** в компактной ветке добавить маленький 📌 в угол аватарки — рядом с тем местом, где уже рисуется значок 🔕 «без звука» (ChatListItem.jsx, компактная ветка, блок с `bottom: -1, left: -1`).

**Почему важно:** закрепление должно читаться в ОБОИХ видах списка, а не только в широком.

**Приоритет:** 🟡 средний — видимый пробел, маленькая правка (~5 строк).

### TODO-18: устойчивый порядок закреплённых (не пересортировывать по времени)

**Контекст (v1.2.138):** `sortWithPinnedFirst` ([shared/pinnedChats.js](../shared/pinnedChats.js)) сортирует закреплённые ВНУТРИ их группы по `lastMessageTs` (времени последнего сообщения). Значит закреплённый чат прыгает вверх-вниз при каждом новом сообщении. Telegram держит закреплённые в фиксированном порядке.

**Что сделать:** внутри группы закреплённых сортировать по порядку в списке `pinnedIds` (порядок закрепления), а не по времени. Осторожно: сейчас в сортировку передаётся `pinnedSet` (Set — порядок теряется). Понадобится передавать МАССИВ `pinnedIds` (порядок есть; `togglePinnedId` кладёт новое закрепление в начало) и по нему задавать позицию.

**Почему важно:** важные закреплённые чаты не должны скакать местами при каждом сообщении — иначе теряется смысл «зафиксировал вверху».

**Осторожно:** меняет поведение, уже показанное пользователю в v1.2.138 — согласовать. Требует визуальной проверки.

**Приоритет:** 🟡 средний.

### TODO-20: перетаскивание закреплённых для ручного порядка — ⛔ СНЯТО v1.2.161 (конфликт с требованием)

**История.** Реализовывалось в v1.2.156→160 (сначала HTML5 drag в общем списке, потом вынос в отдельный `PinnedChatList` с пальцевым drag'ом ради «живого» перетаскивания как в Telegram). **Откачено в v1.2.161**: пользователь уточнил, что закреплённые должны просто быть наверху ОБЩЕГО списка и листаться ВМЕСТЕ с ним, а не быть отдельным «приклеенным» блоком. Пока порядок закреплённых = порядок закрепления (стабильный, v1.2.139). Возвращаться к перетаскиванию — только если пользователь примет отдельный блок ИЛИ будет решение заменить виртуальный список.
