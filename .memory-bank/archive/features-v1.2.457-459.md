проектом (второй прогон, правка файлов, поиск по всей папке, сборка), потому что он читает и

Признак ложного падения: в выводе `no tests` / `failed to find the runner` / `failed to find the
current suite` вместо обычного `AssertionError: expected … to be …`.

**№2 🟡 ЗАКРЫТО: сброс ширины списка чатов шёл мимо потолка окна**
[useChatListResize.js](../src/native/hooks/useChatListResize.js) — двойной щелчок по разделителю
(«вернуть как было») ставил значение по умолчанию НАПРЯМУЮ. Это был единственный из трёх путей
(загрузка настроек / перетаскивание / сброс), который не знал про введённый в v1.2.457 потолок
«список чатов не шире 40 % окна».
Честно: **в жизни недостижимо** — окно нельзя сузить меньше 900 точек (`minWidth: 900` в
[windowManager.js](../main/utils/windowManager.js)), а 40 % от 900 = 360, что больше значения по
умолчанию 340. То есть правило не нарушалось ни при каком размере окна. Чинил как хрупкость:
уменьшат минимум окна или поднимут значение по умолчанию — сломается молча.
ФИКС: сброс проходит через ту же общую проверку `clampChatListWidth`.

### v1.2.458 — 🔴 ЖАЛОБА «почему значок старый у программы»: значок НИКОГДА не вшивался в файл программы

**ЖАЛОБА** (2026-09-11, со скриншотом рабочего стола): у ярлыка «ЦентрЧатов» стандартный значок Electron («атом»), а не наш знак.

**КОРЕНЬ (🟢 доказан выводом самого сборщика)**: в `package.json` в разделе сборки стояло
`"signAndEditExecutable": false`. Эта настройка отключает НЕ ТОЛЬКО подпись, но и правку ресурсов
исполняемого файла — то есть вшивание значка и описания. Сборщик прямо писал об этом в журнале
КАЖДОЙ сборки, включая нашу от 2026-09-11:

```
executable resource editing and code signing skipped — signAndEditExecutable is false.
To skip only code signing while keeping icon and metadata applied, use signExecutable: false instead.
exe=dist\win-unpacked\ЦентрЧатов.exe
```

Итог: `ЦентрЧатов.exe` оставался с родным значком Electron, а ярлык рабочего стола берёт картинку
именно из файла программы. Настройку ставили ради «установщик без подписи» (запись в
[CHANGELOG.md](CHANGELOG.md) про упаковку установщика) — цель была НЕ подписывать, а побочно
отключилось и вшивание значка.

**Почему внутри приложения значок был ПРАВИЛЬНЫЙ**: значок окна и трея приложение рисует на ходу
своим кодом (`nativeImage.createFromBuffer(drawMark(...))` в [windowManager.js](../main/utils/windowManager.js)
и [overlayIcon.js](../main/utils/overlayIcon.js)). Ярлык так не умеет — ему нужен значок, зашитый в файл.
Отсюда и странное ощущение «в программе новый, на ярлыке старый».

**ФИКС**: `"signAndEditExecutable": false` → `"signExecutable": false` — ровно то, что советует сам
сборщик: подпись по-прежнему пропускается (сертификата нет), а значок и описание вшиваются.

**❌ ОПРОВЕРГНУТАЯ ВЕРСИЯ (важно для истории)**: сначала я решил, что виноват ещё и УСТАРЕВШИЙ файл
значка — дата `build/icon.ico` (10.09 17:21) была РАНЬШЕ последней правки рисовалки
`shared/appIconMark.js` (17:46) и раньше коммитов v1.2.450-451, менявших знак. Проверил фактом:
перерисовал значок из единого источника (`node scripts/make-app-icon.cjs`) — файлы вышли
**побайтно теми же** (`git status` пуст, `build/icon.ico` те же 4479 байт). Значит файл значка был
АКТУАЛЬНЫМ, а правки v1.2.450-451 меняли масштаб значка в трее и панели задач (он считается на ходу),
а не содержимое `.ico`. Урок: дата файла — НЕ доказательство устаревания; доказательство — перегенерация
и сравнение.

**КАК ПРОВЕРЕНО**: пересборка установщика — в журнале БОЛЬШЕ НЕТ строки «executable resource editing
… skipped», зато есть правка ресурсов; размер `ЦентрЧатов.exe` отличается от чистого `electron.exe`.
Линт 0; цепочка 48/48; полный `vitest` 206 файлов / 2752 теста; лимиты 649/649; память 44/44.

**ЧТО ПРОВЕРИТЬ ВРУЧНУЮ**: установить `dist/ЦентрЧатов-Setup-1.2.458-x64.exe` → у ярлыка на рабочем
столе наш знак.
⚠️ **Windows кэширует значки ярлыков**: если остался старый — удалить ярлык и создать заново (или
перезайти в систему). Это не дефект приложения, но без этого знания легко решить, что фикс не помог.

**ОСТАТОЧНЫЕ РИСКИ**: (а) 🟢 подпись по-прежнему не ставится — установщик остаётся неподписанным,
Windows может показывать предупреждение при запуске (так было и раньше, поведение не менялось);
(б) 🟢 живьём не смотрел — запускать приложение мне нельзя.

### v1.2.457 — 🔴 ЖАЛОБА «дёргание при переключении между мессенджерами» + список чатов считается с окном + разгрузка памяти

**Коммит**: `504a0ea` (ветка `feature/virtualization`, 2026-09-11). Приложение при разработке не запускалось — правило проекта; всё доказано тестами.

**ЖАЛОБА**: «дёргание при переключении между мессенджерами».

**КОРЕНЬ (🟢 доказан чтением кода, не догадка)**: приложение НАРОЧНО меняет геометрию страницы при открытии веб-вкладки — на миг делает обёртку уже на 1 точку и возвращает обратно («пинок раскладки», [useWebViewLifecycle.js](../src/hooks/useWebViewLifecycle.js), v1.2.416, Ловушка 64). Смысл пинка: расклеить адаптивный сайт, который при первой отрисовке прочитал неверный размер (из-за этого когда-то чернел веб-МАКС). НО делался он **на каждое открытие вкладки и ДВАЖДЫ** — через 200 мс и через 700 мс. То есть при каждом переключении страница дважды за секунду перекладывалась. Пинок применялся ко ВСЕМ веб-мессенджерам (Telegram, WhatsApp, ВК, Ozon, МАКС), а не только к тому, ради которого заводился.

**ПОЧЕМУ ЭТО ЛИШНЕЕ**: слипание раскладки — событие РАЗОВОЕ, оно случается при первом показе страницы, а не при каждом возврате на уже открытую вкладку. К тому же исходная причина чёрного экрана веб-МАКС была опровергнута дважды: сначала v1.2.417 (убивали ServiceWorker), потом окончательно v1.2.434 (наш собственный впрыск прятал корень приложения) — пинок остался «на всякий случай».

**ФИКС**: пинок делается только при ПЕРВОМ открытии каждой вкладки. Отметка хранится на самом элементе (`wrap.__ccRelayoutKicked`) — приём проекта (так же помечены подключённые слушатели в `useWebviewReconnect`), поэтому НОВЫХ хранилищ в приложении не появилось: добавление хранилища в работающее приложение ломает горячую перезагрузку (см. v1.2.452). Отметка ставится ПОСЛЕ повтора на 700 мс: ушёл с вкладки раньше — в следующий раз пинок будет снова (первый показ мог и не состояться).
**ЗАЩИТА НЕ ПОТЕРЯНА**: сторож чёрного экрана ([webviewBlackWatchdog.js](../src/utils/webviewBlackWatchdog.js), v1.2.431) раз в 60 с делает «фото» кадра активной веб-вкладки и при пустом кадре сам делает ТОТ ЖЕ пинок — у него своя реализация, моей отметкой он не ограничен (проверено чтением: строки с `wrap.style.width` там свои).
В журнал добавлена строка уровня TRACE «пинок НЕ нужен … вкладка уже открывалась» — по ней видно, что фикс работает.

**ВТОРОЕ — TODO-40 ЗАКРЫТ ЧАСТИЧНО: список чатов считается с размером окна** ([useChatListResize.js](../src/native/hooks/useChatListResize.js)). Раньше он о размере окна не знал вовсе: сохранённые 340 точек на узком окне съедали место у самой переписки. Теперь ширина ограничена 40 % окна (`chatListMaxPx`).
🔴 ВАЖНО, ПОЧЕМУ ОГРАНИЧЕНО САМО ЧИСЛО, А НЕ ВЁРСТКА (в отличие от панели ИИ, где потолок задан правилом вёрстки — ADR-055): «узкий вид» списка (одни аватарки) включается по ЭТОМУ ЖЕ числу. Ограничь мы вёрстку — показанная ширина уменьшилась бы, а решение про узкий вид осталось прежним: панель узкая, а строки внутри рисуются широкими и обрезаются. Ограничивая число, держим вид и ширину согласованными по построению. Проверено тестом: на самом узком возможном окне (900 — меньше Windows не даст) предел 360, а это заметно больше порога узкого вида (128), значит потолок НИКОГДА не загоняет список в узкий вид сам по себе.
⚠️ ПЛАТА: пересчёт при загрузке настроек и при перетаскивании, но НЕ на лету при изменении размера окна — для «на лету» нужен наблюдатель за размером, то есть новое хранилище. Остаток записан в TODO-40.
