## ADR-034 — Аватар веб-аккаунта на значке полосы: DOM-скрейп своего профиля + canvas→base64, best-effort селекторы, мягкий откат (2026-08-14, v1.2.275)

**Статус**: 🟡 Действующее, ОЖИДАЕТ визуальной проверки; селекторы аватара — best-effort (не проверены на текущих версиях сайтов вживую, запуск агенту запрещён).

### Контекст / проблема
API-аккаунты (TDLib) показывают в полосе фото (TDLib качает в `cc-media://avatars`). Веб-мессенджеры (ВК/WhatsApp/Макс/Telegram-web) — это `<webview>`; из них `accountScript` (constants.js) достаёт только ИМЯ аккаунта, фото не берётся → веб-значки были голыми логотипами. Задача: показать фото своего аккаунта, как у API.

### Решение
Отдельный хук `src/hooks/useWebAccountAvatars.js` периодически (раз ~12с) запускает в каждом веб-webview короткий скрипт `WEB_ACCOUNT_AVATAR_SCRIPT`:
- ищет аватар СВОЕГО аккаунта по НАЦЕЛЕННЫМ селекторам (шапка/профиль/настройки — WhatsApp `chatlist-header-profile-btn`, ВК `TopNavBtn`, Telegram-web `.sidebar-header .avatar-photo`, Макс `.item.settings`/`button.profile`);
- перерисовывает картинку в **base64 data-URI ВНУТРИ webview** (`canvas.toDataURL`) — иначе `blob:`-ссылка сайта действует только внутри его окна и снаружи (в нашем React) не откроется; canvas может бросить на cross-origin (CORS taint) → тогда null;
- получили → запоминаем (больше не опрашиваем этот id), лог `[web-avatar] получен аватар аккаунта: <id>`.
Проброс `App → NativeApp → NativeSidebar → RailWebIcon`; при наличии фото значок рисует его + значок мессенджера углом (как `AccountAvatar`), иначе — логотип.

### Почему так (а не иначе)
- **canvas→base64, а не ссылка**: `blob:`-URL сайта не рендерится вне его webview (проверено по коду хуков — WhatsApp хранит аватары как `blob:`). База64 работает везде.
- **Отдельный хук, а не в `accountScript`/`webviewSetup`**: `webviewSetup.js` 599/600 и `App.jsx` у потолка — расти не могут; плюс путь ИМЕНИ не трогаем (не ломаем рабочее).
- **Только «свой профиль»-селекторы, без общих «любой аватар»**: чтобы НИКОГДА не подставить фото собеседника вместо своего (лучше логотип, чем чужое лицо).
- **Мягкий откат**: нет фото → значок остаётся логотипом; ничего не ломается.

### Последствия / долги
- Селекторы — **best-effort**: где угадан — фото появится; где нет — логотип. Точные места на текущих версиях сайтов доказываются журналом (`[web-avatar] получен аватар: X`) + визуальной проверкой. Доводка селекторов — по факту, по одному мессенджеру.
- Смена залогиненного аккаунта в веб-мессенджере не обновит фото (опрашиваем один раз до успеха) — редкий случай, при необходимости снять `doneRef`.
- Потолок `App.jsx` 1020→1025 (проброс).

### Как проверено
Линт 0, guards 0, лимиты 583/583, appStructure 60/60 (проверка проводки), полный vitest 2310/2310. **Сам факт извлечения фото с каждого сайта — ОЖИДАЕТ запуска пользователем** (по журналу видно, где сработало).

## ADR-035 — Веб-аватарки: диагностика вместо угадывания + возврат к «только свой профиль» (уточнение ADR-034) (2026-08-18, v1.2.276–280)

**Статус**: 🟡 Фиксы действуют, извлечение фото ОЖИДАЕТ визуальной проверки. Уточняет [[ADR-034]].

### Контекст / проблема
ADR-034 задал принцип «только свой профиль, не фото собеседника». Но при доводке (v1.2.278-279) селекторы РАСШИРИЛИ до общих (`img.avatarImage`, `header img[draggable="false"]`) ради «чтобы хоть что-то нашлось». Результат (подтверждён скриншотом пользователя 2026-08-18): на значке Макса появилось фото ОТКРЫТОГО ЧАТА, а не своего аккаунта. То есть широкий селектор + `querySelector` (первый в разметке) = легко схватить чужой аватар.

### Решение (что зафиксировано как правило)
1. **Диагностика вместо угадывания.** Хук логирует не только успех, но и причину неудачи (`no-el` / `canvas:SecurityError` / `cors-reload-failed`) и **дамп кандидатов** (какие картинки/canvas/CSS-фон есть в шапке). Точные места фото на текущих версиях сайтов берутся ИЗ ЖУРНАЛА, не из головы. Так и нашли: Макс — `img.avatarImage` (адрес `i.oneme.ru`), у части картинок фон/`data:base64`; Telegram-web — фото в CSS-фоне кружка, не в `<img>`.
2. **CORS-обход.** `canvas.toDataURL` бросает `SecurityError` на cross-origin картинке (ВК). Обход: перезагрузить картинку `new Image(); crossOrigin='anonymous'` → холст не «пачкается», если CDN отдаёт CORS-заголовок. Запасной путь (если не отдаёт) — тянуть в главном процессе (пока не понадобился).
3. **Возврат к «только свой профиль».** Селекторы снова НАЦЕЛЕНЫ: WhatsApp только `#side`/`#pane-side` (НЕ `#main`), Макс только в контексте `settings/profile/account` (НЕ список чатов). Принцип: **лучше НЕТ фото, чем ЧУЖОЕ** — если своё не опознаётся надёжно, показываем логотип.
4. **Не обрывать поиск** на неудаче конвертации (пробовать следующие селекторы) и **обновлять фото при смене** (убран вечный `doneRef` — закрыт долг из ADR-034).

### Последствия
- Макс/Telegram могут остаться логотипом, если своё фото не в нацеленном месте (напр. Макс показывает свой аватар только в настройках) — это осознанный выбор в пользу правильности.
- Скрипт теперь опрашивает веб-webview раз в 12с постоянно (для обновления фото) — нагрузка минимальна (read-only DOM-запрос).

### Как проверено
Линт 0, guard 0, лимиты 583/583, RailWebIcon 8/8, полный vitest **2312/2312**. Извлечение фото — по журналу `[web-avatar…]` после перезапуска.

**Обновление 2026-08-18 (v1.2.282–283): ПОДТВЕРЖДЕНО журналом.** Все 4 веб-мессенджера получили фото своего аккаунта: Макс `sel=[class*="settings"] img.avatarImage` (снято в разовом заходе в Настройки), **Telegram `sel=stored`** (мини-аватар из `stripped_thumb` записи self в IndexedDB собрался — реконструкция стандартным JPEG-заголовком работает), ВК `TopNav`, WhatsApp `header img[draggable]`. Итоговая схема доставки: «свой профиль на экране» (ВК/WhatsApp) ИЛИ «из-за двери в карман `localStorage['__cc_account_avatar']`» (Макс — Настройки, Telegram — stripped_thumb), хук читает карман первым. v1.2.283 добавил проверку, что сохранённое фото реально открывается (иначе логотип, не пустой кружок). Долг: хук `useWebAccountAvatars.js` 139/150 — вынести скрипт-строку в отдельный файл.

## ADR-036 — Веб-Telegram аватар: чёткое фото авто-съёмкой из Настроек (эволюция ADR-034/035) (2026-08-19, v1.2.305–311)

**Статус**: 🟢 ПОДТВЕРЖДЕНО пользователем (журнал `corners TL=255,255,255…` + скриншот значка). Развивает [[ADR-034]]/[[ADR-035]]. Файл: `src/utils/webAvatarScript.js`.

### Контекст / проблема
По ADR-035 Telegram-веб показывал `sel=stored` — мини-аватар из `stripped_thumb` (бледная размытая запаска), пользователь видел бледный/белый кружок вместо фото. Разбор ПО ЖУРНАЛУ (диагностика ниже) вскрыл три проблемы подряд:
1. Чёткое фото (из Настроек) и бледная запаска (`stripped_thumb` из `constants.js`) писались в ОДИН ключ `localStorage['__cc_account_avatar']` → запаска затирала чёткое; отдельный флаг `__cc_tg_crisp3` залипал и блокировал переснятие. (v1.2.306; см. mistakes/electron-core.md «Два писателя в ОДИН ключ localStorage = гонка»)
2. Авто-съёмка ловила серый «кружок загрузки» Telegram — фото грузится СТУПЕНЬКОЙ (серое ~2с → чёткое). Замер углов снятого = 77,77,77 (серое). (v1.2.308)
3. `__grabBig` брал «просто самый большой» кружок — им часто была серая заглушка, а не настоящее фото. (v1.2.309)

### Решение (что зафиксировано как правило)
1. **Диагностика вместо угадывания** (как ADR-035): разовые дампы в журнал — полный DOM (где лежат аватарки) и замер цвета углов снятого фото; по ним точный диагноз, потом удалены.
2. **Раздельные ключи хранилища.** Чёткое → отдельный ключ `__cc_account_avatar_crisp2`; бледная запаска остаётся в `__cc_account_avatar` (быстрый fallback). Порядок чтения Telegram: онскрин-крупное → чёткое-из-ключа → авто-Настройки → запаска. Гейт авто-Настроек — по НАЛИЧИЮ чёткого ключа (`!crisp`), НЕ по отдельному флагу (флаг рассинхронивался с данными → залипал).
3. **Отсев заглушки загрузки** в `__grabBig`: бракуем почти-однотонное (`mx-mn<18`) И тёмное-малодетальное (`avg<100 И mx-mn<70`) = серый кружок; тёмное-но-ДЕТАЛЬНОЕ фото проходит (не режем настоящие тёмные аватары).
4. **Перебор ВСЕХ кандидатов + предпочтение своего.** Не «самый большой», а самый крупный НАСТОЯЩИЙ (не-заглушка); при наличии — тот, что внутри контейнера Настроек/профиля (`ae.closest('[class*="settings" i], [class*="profile" i], .sidebar-header')` = точно «свой»), иначе крупнейший (безопасный fallback).
5. **Запас на медленный интернет:** до 8 заходов в Настройки, до 5 ретраев внутри одного (ждём прогрузки чёткого, ~9с в Настройках).

### Отклонённая альтернатива
Читать ПОЛНЫЙ файл фото из IndexedDB Telegram (как `stripped_thumb` в `constants.js`, но полное) — крупнее по объёму работы; не понадобилось, раз авто-съёмка из Настроек сработала.

### Последствия / крайние случаи
- Съёмка чёткого зависит от DOM Telegram Web (кнопка «три полоски» + пункт «Настройки» + прогрузка фото ≥80px) — при смене их вёрстки может сломаться → fallback на бледную запаску. Хрупкость осознана.
- Настройки видны на экране ~9с при разовой съёмке (потом закрываются; при наличии `crisp2` больше не открываются — нет лишней нагрузки).
- Очень медленный интернет: 8 попыток могут не хватить → останется запаска (не поломка).
- Осиротевшие ключи от переименований (`_crisp`, `_crisp3`, `_tries6`) — мёртвый груз в localStorage веб-страницы, безвредны, осознанно не чистятся.

### Как проверено
Линт 0, синтаксис инъекции OK (`new Function`), лимиты 584/584, полный vitest **2312/2312**. ГЛАВНОЕ — журнал с машины пользователя 2026-08-19: `sel=crisp-stored | corners …TL=255,255,255…BR=255,255,255` (углы чисто белые = настоящее фото) + скриншот значка (белый круг + логотип). Нагрузка: повторных открытий Настроек нет, в обычном виде канвас не рисуется (мелкие <80px пропускаются до отрисовки).
