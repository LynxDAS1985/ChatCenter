### v1.2.423 — ФИКС чёрного экрана веб-МАКС: sandbox=no у `<webview>` МАКС (песочница ломала сокет) — единственное отличие от рабочего отдельного окна

**КАК НАШЛИ (доказательство, а не гипотеза)**: после 3 неудачных правок (пинок/SW/UA) и цепочки диагностик (сокет рвётся, не HTTP-429, не main-world WebSocket) — предложил пользователю ГОТОВЫЙ обходной путь: тумблер «🧪 Макс в отдельном окне» (`settings.useWebContentsView` → [maxTestWindowHandler.js](../../main/handlers/maxTestWindowHandler.js) открывает МАКС в обычном `BrowserWindow`). **Пользователь подтвердил: в отдельном окне МАКС РАБОТАЕТ полностью** (чаты, фото). А партиция и preload там ТЕ ЖЕ → значит дело НЕ в сессии, а в самом `<webview>`. Сравнил настройки: отдельное окно имеет `sandbox: false`, а `<webview>` МАКС — sandbox по умолчанию ВКЛючён. **Это единственное отличие.**

**КОРЕНЬ**: «песочница» (sandbox — усиленная изоляция рендера) у `<webview>` ломает сокет МАКС (WebSocket в Web Worker / транспорт) → `Socket disconnected` → МАКС переподключается по кругу → свой лимит «Too many requests» (~1740/сек) → чат не грузится → ЧЁРНЫЙ ЭКРАН. В отдельном окне (sandbox выключен) и в браузере — сокет живёт.

**ЧТО** ([App.jsx](../../src/App.jsx)): `webpreferences` вкладки для МАКС дополнен `,sandbox=no` (как в рабочем отдельном окне). Гейт по URL `/\bmax\.ru/i` — **только МАКС**; Telegram/ВК/WhatsApp/Ozon остаются в песочнице (у них проблемы нет).

**КАК РАБОТАЕТ / ОТКАТ**: `webpreferences` читается при создании `<webview>` → нужен ПОЛНЫЙ перезапуск. Откат — `git checkout src/App.jsx`.

**КАК ПРОВЕРЕНО**: линт 0; лимиты 606/606; appStructure 60/60; полный vitest. **Требует ПОЛНОГО перезапуска + визуальной проверки** (МАКС во ВСТРОЕННОЙ вкладке открывается с чатами и фото, без чёрного/шторма). Тумблер «отдельное окно» после этого можно выключить.

**ОПАСНАЯ ЗОНА (безопасность)**: sandbox=no снижает изоляцию именно у вкладки МАКС (web.max.ru — доверенный мессенджер, наш preload там и так работает; отдельное окно давно так работает). Другие мессенджеры НЕ затронуты.

**ДИАГНОСТИКИ (временные, оставлены до подтверждения, потом убрать)**: `[max-429]` ([sessionSetup.js](../../main/utils/sessionSetup.js)), `ws-close`/`wv-stack` свёртка ([webviewDiagnostics.js](../../src/utils/webviewDiagnostics.js)). Тупиковые версии v1.2.416/417/421/422 — см. их записи (правки безвредны, но были не той причиной; UA/SW оставлены как более «браузерные»).

По этой строке будет видно ТОЧНУЮ ручку (API/медиа/сокет), которую МАКС зацикливает при открытии фото-чата → фикс без гадания.

### v1.2.419 — Ozon «Отзывы» (⭐): новые отзывы поднимают счётчик в ФОНЕ (правило rv «start-only» → «только вверх»)

По коду ([[decisions]] ADR-038): фоновый счётчик отзывов принимался ТОЛЬКО как стартовое значение (`if cur.rv !== undefined → фон не трогает`, v1.2.392) — фон видел 10, но игнорировал. **ЧТО** ([ozonBgWatcher.js](../../src/utils/ozonBgWatcher.js)): правило rv из фона `start-only` → **«только вверх»** (`next = prevRv === undefined ? n : Math.max(prevRv, n)`). Фон может ПОДНЯТЬ ⭐ (новые отзывы видны сразу без открытия вкладки), но НЕ понизить. УМЕНЬШЕНИЕ (прочтения) по-прежнему ведёт ПЕРЕДНЯЯ вкладка прямым set ([consoleMessageHandler.js](../../src/utils/consoleMessageHandler.js) ozon_count) — она понижает мимо max.

**КАК РАБОТАЕТ / ОТКАТ**: «только вверх» НИКОГДА не прячет отзыв (max не занижает) — для счётчика отзывов лучше показать чуть больше, чем пропустить. Завышение (если фон транзиентно высок) чинит открытая вкладка. Откат — `git checkout src/utils/ozonBgWatcher.js` + вернуть тест.

### v1.2.416 — ФИКС чёрного экрана веб-МАКС: возвращён РЕАЛЬНЫЙ 1px-пинок раскладки при активации вкладки (Ловушка 64)

**ЗАЧЕМ / КОРЕНЬ**: при открытии веб-МАКС — чёрный пустой экран. По журналу: страница загрузилась (`ready=complete`, `innerLen` рос до 2.6 МБ, картинки/webgl есть), но `cover@center=BODY` — контента в центре нет. Это НЕ «Too many requests» (тот `health[err]` был побочным шумом, на нём я сначала ошибочно застрял) — это **layout lock-in адаптивного SPA** ([[webview-stack-grouping]] Ловушка 64): МАКС (Svelte SPA) при инициализации в НЕактивной вкладке (`zIndex:0, pointerEvents:none`) читает неверный/узкий первичный размер через `ResizeObserver` → фиксирует «мобильную» раскладку → область чата схлопывается в 0×0 → чёрное. После активации окно РЕАЛЬНО не меняет размер → ResizeObserver молчит → остаётся схлопнутым.

**ПОЧЕМУ раньше работало, а теперь нет**: фикс (реальный пиксельный ресайз) БЫЛ (v0.86.8), но его УДАЛИЛИ при переводе Telegram на нативный TDLib-канал (весь webview-recovery код убрали). Веб-МАКС остался webview — и без лечения.

**ЧТО** ([useWebViewLifecycle.js](../../src/hooks/useWebViewLifecycle.js)): при смене `activeId` на ВЕБ-вкладку (не native) на миг сужаем обёртку webview на 1px и возвращаем через 2×`requestAnimationFrame` (два раза: 200мс и 700мс — поймать SPA до и после готовности). Guest реально видит resize → `ResizeObserver` пересчитывает layout → область чата разворачивается. Лог `[webview-relayout] 1px-пинок раскладки для <id>`. **Синтетический `dispatchEvent('resize')` НЕ используем** — SPA слушают ResizeObserver = только РЕАЛЬНЫЙ пиксельный delta (доказано в Ловушке 64).

**КАК РАБОТАЕТ / ОТКАТ**: применяется ко ВСЕМ веб-вкладкам (МАКС/WhatsApp/ВК/Ozon) — тем, кому не нужно, 1px-пинок безвреден (просто пересчёт). Native (TDLib) вкладки не трогаются. Откат — `git checkout src/hooks/useWebViewLifecycle.js`.

**КАК ПРОВЕРЕНО**: линт 0; лимиты 605/605; appStructure 60/60; полный vitest. **Требует ПОЛНОГО перезапуска** (не хот-релоад: добавление хука на лету даёт разовую ошибку React «Rendered more hooks» — это артефакт HMR, при полном старте её нет) + визуальной проверки (МАКС открывается с чатами, не чёрный).

**ГРАНИЦА**: если у МАКС окажется НЕ layout lock-in, а внутренняя гонка (как Telegram K `peer-changed`, которую пиксельный ресайз не лечил) — понадобится полный reload вкладки; пока ставим на layout lock-in (симптом совпадает).
