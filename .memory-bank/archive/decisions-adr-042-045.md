## ADR-042 — Впрыски в чужую страницу ОБЯЗАНЫ иметь предохранитель по РАЗМЕРУ: «прятальщик плашек» мог скрыть всё приложение (2026-09-09, v1.2.434)

**Статус**: 🟢 Действующее, **ПОДТВЕРЖДЕНО ФАКТОМ 2026-09-09** (сеанс v1.2.434 12:42-12:48; пользователь подтвердил визуально). Журнал дал 8 строк `banner НЕ прячу DIV skip:текст-26230…33546` — восемь контейнеров МАКС с текстом переписки 26-33 тыс. символов, которые по СТАРОМУ правилу были бы скрыты. Геометрия контейнера чата `DIV.history` вернулась: `@0,0,0x0` → `@471,65,549x703`; снимок экрана: разброс 0 → 50.8; 1px-пинков 0. У ВК/Telegram/WhatsApp/Ozon строк `banner` нет ни одной — регресса нет.

### Контекст / проблема

С v0.82.6 (перенос из App.jsx, коммит e2e3f8b) в страницу КАЖДОГО мессенджера впрыскивался сторож, гасящий плашки «Обновите браузер» (мессенджеры их показывают, потому что видят Electron). Правило было:

> в `textContent` элемента есть «обновите»+«браузер» (или англ. «update»+«browser») И `children.length < 20` → `style.display = 'none'`

Разбор чёрного экрана веб-МАКС (сеанс 2026-09-09 11:17:42-11:20:30) показал: страница МАКС **полностью жива** (`connection opened` → `session inited` → `user logged in`, DOM 1,26 МБ, шапка чата с именем собеседника), но контейнер сообщений отдаёт `DIV.history.svelte-1prjz03@0,0,0x0`, а снимок экрана — 8935 точек ОДНОГО цвета (фон страницы `rgb(23,24,28)`). По MDN нули у `getBoundingClientRect()` = элемент **не отрисован**, а `textContent` читается и у скрытых узлов — то есть содержимое **спрятано**, а не «не нарисовано».

Правило выше умеет спрятать корень приложения: `textContent` верхней «коробки» = текст ВСЕЙ переписки (хватит слов в любом сообщении), а `children.length < 20` у корня SPA выполняется всегда. Плюс пересканирование на каждое изменение DOM — вечно, поэтому любые попытки поправить раскладку (1px-пинок, Ловушка 64) перебивались повторным `display:none`.

### Решение

1. **Гейт по размеру — обязателен.** Прятать по ТЕКСТУ можно только элемент, который физически похож на плашку: текст ≤300 символов, детей <20, элемент **отрисован** (ненулевые размеры), высота ≤200px, площадь ≤35% площади окна. Два последних условия делают «спрятать всё приложение» структурно невозможным.
2. **Нулевые размеры = не трогать.** Иначе инлайн `display:none` навсегда останется на элементе, который был скрыт родителем и потом должен показаться.
3. **Решение — чистая функция, а не текст внутри строки.** `bannerVerdict(el, win)` в [shared/browserBannerHider.js](../../shared/browserBannerHider.js); её исходник встраивается в впрыск через `Function.prototype.toString()` → один источник истины для теста и для чужой страницы. Отсюда ограничение: внутри такой функции нельзя ссылаться на внешние переменные (замыкания при `toString` теряются) и нельзя современный синтаксис (сборщик перепишет его через свои хелперы, которых в чужой странице нет).
4. **Впрыск, который что-то ПРЯЧЕТ, обязан отчитываться.** Пишем и «спрятал», и «НЕ прячу + причина» (`__CC_DIAG__banner`, до 8 отказов). Без этого причина чёрного экрана была невидима 5 версий подряд.
5. **Наблюдатель за DOM — с тормозом** (500мс), а не на каждое изменение.

### Почему так, а не иначе

- **Убрать впрыск совсем** — потеряем гашение плашек там, где класс неизвестен (плашки по известным классам гасит CSS `insertCSS`, включая полноэкранные модалки VK `BrowserUpdateLayer` — эта часть не тронута).
- **Оставить только гейт по длине текста** — недостаточно: короткая фраза внутри корня («Обновите браузер» как единственное сообщение в чате) снова спрятала бы приложение.
- **Гейт по мессенджеру (не трогать МАКС)** — лечит один случай, а грабля общая для всех впрысков.

### Ограничения / что осознанно принято

- Настоящая плашка выше 200px или занимающая >35% окна по тексту больше не спрячется (по классам — гасится CSS).
- Плашка, не разложенная браузером в момент первого прохода, пропускается — её поймают проходы на 2/5/10-й секунде и наблюдатель.
- ~~Что слова-триггеры реально были на странице МАКС — не доказано~~ → **ДОКАЗАНО** (см. Статус: 8 строк журнала).
- ~~🟡 Ключ дедупликации журнала включает ЧИСЛО → бюджет 8 отказов уходит на одну причину~~ → **ИСПРАВЛЕНО в v1.2.435**: ключ строится из причины БЕЗ цифр (`v.replace(/[0-9]+/g, '')`), число остаётся в тексте записи; при исчерпании бюджета пишется отдельная строка. Ловушка-тест: три элемента с разной длиной текста → в журнале ОДНА строка.
- 🟡 Запись идёт уровнем TRACE (консоль-мост — единственный канал из чужой страницы); при отключённом TRACE доказательства в журнале не видно.

**Общее правило на будущее (шире этого случая)**: любой наш код, который в чужой странице **скрывает или удаляет** узлы по ТЕКСТУ, обязан (а) ограничивать себя по РАЗМЕРУ элемента, (б) никогда не действовать на неотрисованный элемент, (в) писать в журнал каждое действие и каждый отказ, (г) **писать в журнал и СВОЙ СОБСТВЕННЫЙ сбой запуска** — добавлено v1.2.435. Пункт (г) появился по ревью: впрыск стоял с пустым `.catch(() => {})`, а по доке Electron 42 (`webview-tag.executeJavaScript`) обещание отклоняется при неудаче. Без записи о сбое «нет строк в журнале» невозможно отличить от «условие не сработало» — то есть диагностика из пункта (в) становится обманчивой. (д) Дедупликацию записей строить по КАТЕГОРИИ причины, а не по её полному тексту с числами — иначе бюджет записей съедает одна причина. Связано с [[ADR-041]] (подавление фантомов МАКС на общем узле) и с граблями впрысков в [[webview-injection]].

**Откат**: `git checkout HEAD -- src/utils/webviewSetup.js && rm shared/browserBannerHider.js src/__tests__/browserBannerHider.vitest.js` (вернёт прежнее широкое условие вместе с риском). Мягче — поднять `BANNER_MAX_HEIGHT` / `BANNER_MAX_AREA_RATIO`.

**Проверено**: [browserBannerHider.vitest.js](../../src/__tests__/browserBannerHider.vitest.js) 15/15 (в т.ч. ловушка «коробка во весь экран со словами → НЕ прячем» и живой прогон впрыска в happy-dom); полный vitest 188/188 файлов, 2451 тест; линт 0.

## ADR-043 — Команда, меняющая ЧУЖУЮ страницу, обязана менять и НАШЕ состояние; связь между хуками — событием окна (2026-09-09, v1.2.441)

**Контекст.** В v1.2.440 добавлен пункт меню «🖼 Обновить фото аккаунта»: он чистит наши служебные ключи (`__cc_*`) в хранилище страницы мессенджера, после чего сборщик аватарок должен переснять фото. По ревью выяснилось: команда работала «наполовину» — ключи удалялись, а на значке боковой полосы оставалось СТАРОЕ фото, потому что состояние React обновлялось только при появлении НОВОГО фото, а ветка «фото не нашлось» состояние не трогала. Для МАКС это гарантированный случай: его фото видно лишь при открытых Настройках. Со стороны пользователя это «кнопка не работает».

**Решение.**
1. Любая команда, которая сбрасывает КЭШ в чужой странице, обязана в том же действии сбросить и НАШУ копию этих данных — иначе интерфейс показывает то, чего в кэше уже нет.
2. Сброс делается ТОЛЬКО после подтверждённой удачи (обещание `executeJavaScript` разрешилось). В ветке ошибки состояние не трогаем — иначе потеряли бы рабочее фото из-за неготовой страницы.
3. Связь «пункт меню → сборщик аватарок» сделана событием окна `cc-avatar-reset` (`CustomEvent`, id в `detail`), а НЕ пробросом функции через `App.jsx`: файл `src/App.jsx` ровно на потолке 1075/1075 (новую строку проводки туда не добавить), а приём «одно место шлёт событие, другое слушает» в проекте уже есть — `useConsoleErrorLogger.js` → `UncaughtErrorToast.jsx` (`cc-uncaught-error`). Никакой новой сущности не заведено.
4. Чистая логика (ключ записи журнала, снятие гейтов, «забыть фото», применение сброса, ТЕКСТЫ записей) вынесена в корневой `shared/webAvatarGate.js`. Причина: правки вывели renderer-бюджет за предел (36128 > 36090), и вместо ЧЕТВЁРТОГО за один день поднятия планки бюджет оставлен прежним, а логика ушла в `shared/` (вне бюджета) — приём уже применялся: `shared/notifAlbum.js` (v1.2.95), `shared/ozonNotifDedup.js`, `shared/activeTabChoice.js`. Итог: бюджет 36088 < 36090, планка не поднята.

**Факты, на которых стоит решение.**
- 🥇 MDN `EventTarget.dispatchEvent()` — вызывает слушателей синхронно, в отличие от событий, идущих через цикл событий; MDN `CustomEvent.detail` — «any data passed when initializing the event». Значит id источника доедет до слушателя без своей шины сообщений.
- 🥇 React (`useState`) — функция-обновитель должна быть ЧИСТОЙ (в строгом режиме вызывается дважды). Поэтому запись в журнал сделана СНАРУЖИ обновителя, а `forgetAvatar(prev, id)` — чистая функция, возвращающая тот же объект, если фото и не было (нет лишней перерисовки).
- 🥈 Код проекта: [RailWebIcon.jsx:65](../../src/native/components/RailWebIcon.jsx#L65) рисует логотип, когда фото нет → удаление ключа из состояния действительно возвращает значок к логотипу (видимый эффект команды).
- 🥈 Код проекта: `sel: 'onscreen-big-' + big.sz` в `src/utils/webAvatarScript.js` → в ключе записи журнала оказывалось ЧИСЛО. Тот же класс ошибки уже закрыт в [[ADR-042]] (пункт «д»), здесь он повторился в другом месте — значит правило общее: **ключ дедупликации записей строить по КАТЕГОРИИ, число оставлять в тексте**.

**Ограничения / что осознанно принято.**
- После сброса значок КРАТКО показывает логотип. Это намеренно: пользователь видит, что команда принята. Если фото так и не найдётся (МАКС с закрытыми Настройками), логотип останется до следующей удачной съёмки.
- Пункт меню виден и у Ozon, где фото аккаунта не собирается: нажатие даст «удалено ключей=0». Безвредно; скрывать не стали (потребовался бы отдельный список «кто умеет фото» — сложность больше пользы).
- Событие окна не переживает перезагрузку страницы приложения — но и не должно: сброс это разовая команда.

**Откат**: `git checkout HEAD -- src/hooks/useWebAccountAvatars.js src/hooks/useTabContextMenu.js && rm shared/webAvatarGate.js` (кнопка снова будет чистить кэш без отклика на значке).

**Проверено**: [webAvatarGate.vitest.js](../../src/__tests__/webAvatarGate.vitest.js) 19/19; [useWebAccountAvatars.vitest.jsx](../../src/hooks/useWebAccountAvatars.vitest.jsx) 16/16 (фейковые таймеры, `renderHook`); полный vitest 194 файла / 2531 тест; линт 0; лимиты 622/622 без поднятия бюджета. Связано с [[ADR-042]], [[features]] v1.2.441 и граблями в [[webview-injection]].

## ADR-044 — Что НЕ входит в бюджет renderer: данные и код проверок. Планку опускаем, а не поднимаем (2026-09-09, v1.2.442)

**Контекст.** Тест `fileSizeLimits.test.cjs` держит общий бюджет строк на `src/` без тестов. За один день 2026-09-09 планка поднималась ТРИ раза (35990 → 36010 → 36040 → 36090), запас упал до 2 строк, а `src/App.jsx` встал ровно на свой потолок 1075/1075. Практическое следствие: в v1.2.441 пункт меню пришлось связывать со сборщиком аватарок через событие окна — не потому, что так лучше, а потому что в `App.jsx` не было места ни под одну строку проводки. Это признак, что бюджет мерил НЕ ТО.

**Решение (три правила).**

1. **ДАННЫЕ не считаются кодом интерфейса.** Файл, который растёт по одной записи на каждую версию и никогда не перестанет расти (`changelogData.js` — текст окна «Что нового», и его архив), в бюджете кода не место. Такие файлы живут в корневой `shared/`. Признак «это данные»: только массив/объект записей, нет ветвлений и работы с DOM, разбивать бессмысленно.
2. **КОД ПРОВЕРОК не считается кодом интерфейса.** Из бюджета исключена вся папка `src/__tests__/`, а не только имена с `.test.`/`.vitest.`: файлы-помощники тестов (`fileSizeLimitsExceptions.cjs`, `fileSizeLimitsRules.cjs`) в приложение не попадают. Раньше они съедали бюджет, и разбиение теста «наказывалось» ростом бюджета — прямо противоположно тому, чего добивается лимит.
3. **После разгрузки планка ОПУСКАЕТСЯ.** 36090 → 35300 при факте 35100. Иначе освободившееся место молча зарастёт, и мы вернёмся к «запас 2 строки».

**Как разбивался `App.jsx` (образец на будущее).** Из корневого компонента вынимается КОНЕЧНАЯ, самодостаточная группа — все модалки вместе с их «ленивой» загрузкой (`src/components/AppModals.jsx`). Данные передаются ОДНИМ объектом `ctx` (приём уже был у `NotifLogModal`) — иначе 60 отдельных пропсов съели бы выигрыш. В корне остаётся то, что часть основного экрана: `NativeApp`, `AISidebar`. Хуки НЕ переносятся (порядок вызова сторожит `hookOrder.test.cjs`).

**Про тесты-стражи.** `appStructure.test.cjs` и `integrationChains.test.cjs` проверяли «модалка грузится лениво и используется» по тексту `src/App.jsx`. Такие проверки после переноса надо ПЕРЕНАСТРАИВАТЬ на склейку файлов оболочки (`allAppCode`, `appShellCode`), а не удалять и не ослаблять: смысл («модалка есть и грузится лениво») сохраняется, меняется только место строк. Удаление модалки по-прежнему валит проверку.

**Факты, на которых стоит решение.**
- 🥇 Дока проекта в CLAUDE.md («Правило превышения лимита строк»): при превышении **не резать комментарии**, а разделять файл на модули. Отсюда: разбиение, а не подчистка.
- 🥈 Код проекта: `shared/notifAlbum.js` (v1.2.95) вынесен в `shared/` именно чтобы НЕ поднимать бюджет renderer — прецедент, а не новая выдумка; сюда же `shared/ozonNotifDedup.js`, `shared/activeTabChoice.js`, `shared/webAvatarGate.js` (v1.2.441).
- 🥈 Код проекта: фильтр бюджета `f.startsWith('src/') && !/\.(test|vitest)\./.test(f)` пропускал `src/__tests__/fileSizeLimitsExceptions.cjs` (156 строк) — измеримая дыра, а не предположение.
- 🥇 Дока Vite/electron-vite: корень dev-сервера renderer здесь `.` (см. `electron.vite.config.js`), поэтому импорт `../../shared/...` из `src/components/` отдаётся сервером — перенос данных в `shared/` не ломает разработку.

**Ограничения / что осознанно принято.**
- `shared/` перестаёт означать строго «общее для main и renderer» и означает «вне бюджета renderer, обособленный модуль или данные». Это уже фактически так с v1.2.95.
- `nativeStore.js` (1301) и `InboxMode.jsx` (1119) НЕ разбивались: они под своими индивидуальными потолками, а резать хранилище состояния и экран без возможности запустить приложение — риск больше пользы. Режем под конкретную задачу.
- Модалок 15, и автотесты проверяют их НАЛИЧИЕ, а не реальный показ — нужна ручная проверка (окна без запуска приложения не проверяются).

**Откат**: `git checkout HEAD -- src/App.jsx src/__tests__/ && git mv shared/changelogData.js src/utils/changelogData.js && mv shared/changelogDataArchive.js src/utils/changelogDataArchive.js && rm src/components/AppModals.jsx`.

**Проверено**: линт 0; полный vitest 194 файла / 2533 теста; лимиты 624/624 (бюджет 35100/35300); `appStructure` 60/60; `integrationChains` 18/18; `componentScope` 23/23. Связано с [[ADR-043]], [[features]] v1.2.442 и снапшотом [[code-limits-status]].

## ADR-045 — Знак приложения РИСУЕТСЯ КОДОМ из единого источника, а не хранится набором картинок (2026-09-10, v1.2.443)

**Контекст.** У приложения не было своей иконки: `build.win.icon` не задан (журнал сборки: «default Electron icon is used, reason=application icon is not set»), в трее рисовался синий круг телеграмного цвета, у окна значок не задавался вовсе. Знак нужен сразу в шести местах: трей, окно, установщик/ярлык, папка `PNG/` рядом с иконками мессенджеров, стартовая заставка, экран загрузки чатов.

**Решение.** Геометрия и цвета знака живут в ОДНОМ модуле `shared/appIconMark.js`; из него:
1. **трей и окно** получают готовый буфер картинки прямо в память (`nativeImage.createFromBuffer`) — файл на диске не нужен, а значит нет разницы между запуском из терминала и установленной версией (это регулярный источник ошибок: пути `__dirname` в них разные, см. ловушку про `.cjs`→`.mjs` в v1.2.318);
2. **файлы** (`build/icon.png`, `PNG/chatcenter-icon*.png`) делает скрипт `scripts/make-app-icon.cjs` — одной командой, из того же рисунка;
3. **разметка заставок** повторяет те же числа геометрии, и это закреплено тестом «геометрия одинаковая в трёх местах».

**Почему не хранить просто картинки.** Набор PNG под все размеры разъезжается: поправили цвет в одном месте — забыли перегенерировать остальные. Здесь цвет меняется одной строкой в `MARK`, затем `node scripts/make-app-icon.cjs`, и трей с окном подхватывают новое сами (они рисуют в момент запуска).

**Почему свой кодировщик PNG, а не библиотека.** Нужен ровно один формат — RGBA без палитры. Это подпись + три блока (IHDR/IDAT/IEND), CRC32 и сжатие встроенным `node:zlib`. Новая зависимость ради этого не оправдана, тем более что в проекте уже есть ручное рисование картинок (`main/utils/overlayIcon.js` собирает бейдж по пикселям). Проверяется тестом: подпись, размер в заголовке, завершающий блок, реальное сжатие.

**Почему `.ico` не собираем сами.** ⚠️ **ЭТОТ ПУНКТ ОТМЕНЁН — см. [[ADR-046]] (v1.2.444)**: оказалось, что electron-builder делает `.ico` УМЕНЬШЕНИЕМ большой картинки, и знак на 16 точках превращается в серое пятно. Ниже — исходное (ошибочное) обоснование.

 Его делает electron-builder из `build/icon.png`. Факт из его кода (`app-builder-lib/out/util/iconConverter.js`): принимает `icon.png`/`icon.svg`/`icon.ico`, ищет в папке `build/`, и требует размер **не меньше 256×256** («Icon must be at least 256x256 pixels»). Мы даём 512×512. Свой формат `.ico` (контейнер с несколькими картинками внутри) писать руками — риск без выгоды.

**Отдельная толщина линии для мелких размеров — обязательна.** Тонкий контур при уменьшении превращается в серую нитку: при отступе 14% и линии 7 знак на 16 px стал пятном (проверено увеличением каждого пикселя в 14 раз). Правило: ≤24 px — линия 9.5 и отступ плитки 5%; ≤48 px — линия 7.5; крупные — 4.5. Это не «подгонка на глаз», а стандартная практика: под каждый размер свой рисунок.

**Число проб сглаживания зависит от размера.** Мелким нужно 4×4 на пиксель, крупным хватает 2×2: при 16 пробах значок окна 256 px отнимал 278 мс при запуске (замерено), а старт приложения и без того не быстрый. Сейчас: 32 px — 12 мс, 128 px — 62 мс.

**Ограничения / что осознанно принято.**
- Выбранная лазурь (#38BDF8) близка к синему Telegram. Пользователь предупреждён отдельно и выбрал сознательно — это его решение, зафиксировано.
- Вид (трей, заставки) автотестами не проверяется, только наличие строк и цвета в буфере — нужна визуальная проверка человеком.
- Знак нарисован под тёмную плитку. Для случаев, где нужен знак без фона (например, монохром в системном меню), в `drawMark` есть `tile: false`, но нигде пока не используется.
