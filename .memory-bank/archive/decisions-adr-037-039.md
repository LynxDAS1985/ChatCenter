## ADR-037 — Ozon: слежка за НЕСКОЛЬКИМИ разделами (Сообщения/Вопросы/…) через DOM-слежку в фоне, БЕЗ официального API (2026-09-02, план v1.2.341+)

### Контекст / задача
Пользователь работает с покупателями Ozon в нескольких разделах кабинета: «Сообщения» (`/app/messenger`, покупатели — сторож уже есть, v1.2.329-331) и «Вопросы и ответы» (`/app/reviews/questions`, подтверждён журналом 2026-09-02). Планируется третий источник (назовёт позже). Нужно: уведомления из ВСЕХ разделов **одновременно и независимо** от того, какой раздел открыт, под ОДНОЙ учёткой Ozon, + виджет для быстрого перехода.

### Решение по способу чтения данных
**Официальный Ozon Seller API (`api-seller.ozon.ru`) — НЕ используем.** По решению пользователя (2026-09-02): **API платный** (нужна подписка/тариф для чатов/вопросов) и **не подходит**. **НЕ предлагать API повторно, пока пользователь сам не попросит.**

**Выбрано: DOM-слежка через фоновые страницы.** Каждый раздел — отдельная страница Ozon, загруженная в фоне на ОБЩЕЙ партиции Ozon (`persist:ozon` → один вход/учётка), сторож читает разметку («Новое N» / новые строки) и шлёт `__CC_NOTIF__` в общий конвейер — как сторож «Покупателей» (`ozon.hook.js`).

### Факты (основание)
- 🥇 Ур.1 Electron `<webview partition>`: одинаковая партиция = общая сессия (вход) → одна учётка, несколько страниц.
- 🥈 Ур.2 `App.jsx` (стр. 755-759): скрытые вкладки НЕ усыпляются (`visibility:hidden` не используется — Chromium остановил бы загрузку) → фоновая слежка реальна.
- 🥈 Ур.2 `ozon.hook.js`: DOM-слежка за списком уже работает (Сообщения) — проверенный образец для новых разделов.
- 🥈 Ур.2 журнал 2026-09-02: адрес вопросов `/app/reviews/questions`, страница грузится (`ready=complete`), тот же хост `seller.ozon.ru` → сторож рекламы (v1.2.338) её не блокирует (тот же хост).

### Ограничения / риски (честно)
- Каждая фоновая страница = ещё одна тяжёлая страница в памяти (терпимо для 3, тяжелее для 10 — но пользователь принял: «не важно сколько кода»).
- DOM-слежка ломается при переверстке Ozon (классы случайные) — лечится подстройкой сторожа, не редизайном.
- НЕ подтверждено (нужна разведка): обновляется ли «Новое N» на странице вопросов В ФОНЕ без клика (у Сообщений — да; у Вопросов — проверить; если нет — тихо «будить» страницу раз в N минут).

### План (фазы) — реализация отдельными версиями
Фаза 1: механизм фоновой страницы (скрытый webview на партиции Ozon) + разведка «Вопросов». Фаза 2: сторож «Вопросов». Фаза 3: виджет быстрого перехода. Фаза 4: обобщение под третий источник. Связано с [[code-todo]].

## ADR-038 — Ozon: КТО ведёт счётчик по каждому разделу (msg/qa — фон; rv-отзывы — передняя вкладка, фон только стартовое) (2026-09-03, v1.2.386–392)

**Статус**: ✅ Действующее. Продолжает [[decisions]] ADR-037 (фоновая DOM-слежка Ozon).

### Контекст / почему запись нужна
За одну сессию правило «кто пишет цифру раздела» менялось **5 раз** (v1.2.386→388→390→391→392) — каждый раз чинили один симптом и ломали другой. Чтобы не ходить по кругу снова, фиксирую итоговое разделение владения. Разделы Ozon: `msg` (Сообщения/Покупатели 💬), `qa` (Вопросы ❓), `rv` (Отзывы ⭐). Состояние: `ozonCounts[id] = {msg, qa, rv}`; сумма → значок в рейле; виджет читает по-раздельно. Сигнал считает и ПЕРЕДНЯЯ открытая вкладка Ozon ([[consoleMessageHandler]]), и три СКРЫТЫЕ фоновые страницы ([[ozonBgWatcher]]).

### Ключевой факт (основание, 🥈 Ур.2 — журнал + код)
- `msg`, `qa`: фоновая страница видит **актуальное** «Новое N» (мессенджер живёт по websocket; вопросы — проверено журналом). → фон надёжен.
- `rv` (Отзывы): фоновая скрытая страница `/app/reviews` держит **ЗАСТРЯВШИЙ снимок** — Ozon НЕ обновляет её по прочтениям (в отличие от мессенджера). Подтверждено журналом: цифра не менялась даже ПОСЛЕ авто-перезагрузки фоновой страницы. → фону для rv доверять «в динамике» НЕЛЬЗЯ.

### Решение (итог, Вариант C)
| Раздел | Стартовое значение (при запуске) | Обновления (прочтения/новые) |
|---|---|---|
| `msg`, `qa` | фон | фон (всегда) |
| `rv` (Отзывы) | **фон — но ТОЛЬКО если ещё не задан** (`cur.rv === undefined`) | **передняя вкладка** (любое значение, отражает прочтения) |

Фон для rv ставит цифру только как СТАРТОВУЮ (чтобы значок ⭐ показывал число сразу после запуска, не открывая раздел), но НЕ перетирает уже заданное — иначе застрявший снимок вернул бы старую цифру после того, как пользователь прочитал отзывы в открытой вкладке.

### Почему не иначе (отвергнутые ветки)
- **Фон ведёт rv всегда** (как msg/qa) — v1.2.391 до этого: цифра застревала при прочтении (симптом «прочитал, не убавилось»).
- **Фон вообще не трогает rv** — v1.2.391: на старте ⭐ показывала 0, пока не откроешь раздел (сломало саму фичу «видеть число новых сразу»).
- **Авто-reload фона + стабильный отпечаток по SKU** («Вариант A») — НЕ помог бы: журнал доказал, что перезагруженная фоновая страница всё равно видит застрявшую цифру.

### Компромисс (принятый)
Если в одной сессии прочитать все отзывы (rv=0) и затем придёт новый — уведомление придёт (фон), но цифра ⭐ обновится, когда rv переведёт передняя вкладка при открытии раздела «Отзывы» (фон rv уже задан → не двигает). Это меньшее зло: живой правды по rv в фоне нет.

**ОБНОВЛЕНИЕ (2026-09-07, v1.2.419) — правило rv изменено: «start-only» → «только вверх» (Math.max)**. Причина: пользователь пожаловался, что новые отзывы не поднимают ⭐, пока не откроешь вкладку (было 4, реально 10 — фон видел 10, но игнорировал, т.к. rv уже задан). Плюс журнал показал, что фоновая цифра отзывов на самом деле ОТСЛЕЖИВАЕТ состояние (`rv из фона=10→5→0`), а не «намертво застревает» как опасались в v1.2.392. Новое правило ([[ozonBgWatcher]]): фон может ТОЛЬКО ПОДНИМАТЬ ⭐ (`Math.max(prevRv, n)`) — новые отзывы видны сразу без открытия вкладки; УМЕНЬШЕНИЕ (прочтения) по-прежнему ведёт ПЕРЕДНЯЯ вкладка прямым set (она понижает мимо max). Почему безопасно: «только вверх» НИКОГДА не прячет отзыв (max не занижает) — для счётчика отзывов лучше показать чуть больше, чем пропустить; завышение (если фон транзиентно высок) чинит открытая вкладка. Остаточный риск: пока вкладка ОТКРЫТА, редкий фон-эмит (раз в ~3 мин) может на миг поднять ⭐ выше живого числа передней вкладки, но следующий её эмит поправит. Тест `ozonBgWatcher.vitest.js` (+2: поднимает на новые, не занижает). Таблица владения выше (строка «rv») этим ОБНОВЛЕНИЕМ заменяется на «фон — только вверх (Math.max); передняя — любое (в т.ч. понижение)».

### Файлы / тесты / откат
Файлы: [[ozonBgWatcher]] (маршрут rv — только стартовое), [[consoleMessageHandler]] (передняя вкладка ведёт rv), `consoleMessageParser.js` (rv не сваливается в msg — фикс v1.2.387). Тесты: `ozonBgWatcher.vitest.js` (rv-стартовое ставится; rv из фона НЕ перетирает заданное). Откат: `git checkout src/utils/ozonBgWatcher.js`. Ловушки — [[webview-navigation-ui]] (Ozon: snapshot отзывов застревает; parser section-collapse).

## ADR-039 — Значок ВК в рейле = число непрочитанных ЧАТОВ (не сообщений); VK не отдаёт «сумму сообщений» (2026-09-03, разбор при v1.2.393)

**Статус**: ✅ Действующее (описывает уже существующее поведение; кода не меняли).

### Контекст / вопрос
Жалоба: «на значке ВК показывать количество непрочитанного». Развилка была: значок = число ЧАТОВ (диалогов с непрочитанным) или сумма СООБЩЕНИЙ. Пользователь выбрал **Вариант А — число чатов**.

### Решение / факт (по коду и журналу)
Значок ВК УЖЕ показывает число непрочитанных **чатов** — отдельного кода не потребовалось. Цепочка (🥈 Ур.2, прочитал файлы):
1. `countUnreadVK` ([unreadCounters.js:125-191](../../main/preloads/utils/unreadCounters.js)) берёт число из бейджа пункта «Мессенджер N» бокового меню ВК (метод 2) — это число непрочитанных ДИАЛОГОВ, не сообщений.
2. Шлётся `ipcRenderer.sendToHost('unread-count', allTotal)` ([monitor.preload.cjs:258](../../main/preloads/monitor.preload.cjs)).
3. Обработчик [webviewSetup.js:475-513](../../src/utils/webviewSetup.js) кладёт в `unreadCounts[vk]` (в фоне — только рост; при просмотре вкладки — можно уменьшать) → значок рейла.

Журнал (🥇 Ур.1 для факта значения, 2026-09-03): `vk-src msgBadge=2 msgTx="Мессенджер2"` → бейдж ВК = 2 непрочитанных чата (у пользователя Елена=2 сообщения + Др=5 = 7 сообщений, но ВК на кнопке пишет «2» = 2 чата).

### Почему НЕ «сумма сообщений» (Вариант Б отклонён)
VK **не отдаёт** странице общее число непрочитанных сообщений: в заголовке окна числа нет (`titleN=нет`), доступен только счётчик диалогов «Мессенджер N». Просуммировать маленькие бейджи чатов можно лишь по ВИДИМЫМ строкам списка (ВК виртуализирует список — грузит по мере прокрутки) → сумма была бы неточной/заниженной при длинном списке. Поэтому «число чатов» — надёжный выбор.

### Ловушка диагностики (записать, чтобы не повторить)
`console.log('__CC_DIAG__…')` из preload-**утилиты** (`unreadCounters.js`, изолированный мир preload) НЕ перехватывается webview-логгером и НЕ попадает в `chatcenter.log` — так же давно не виден `__CC_DIAG__unread_max` из `countUnreadMAX`. Виден только `console.log` из ГЛАВНОГО мира webview (инъекции `*.hook.js`, напр. `vk-src`). Вывод: для диагностики счётчика логировать из hook-скрипта (главный мир) или из renderer через `app:log`, а не из preload-утилиты. Подробнее — [[webview-navigation-ui]].

### Ожидает / откат
Ожидает визуальной проверки: стоит ли «2» на значке ВК. Если пусто — метод 2 `countUnreadVK` не совпал с вёрсткой vk.ru; готовый мелкий фикс — расширить селектор поиска «Мессенджер N» до `a,[role="link"]` (как в рабочем `vk-src`). Кода по этому ADR не вносили → откатывать нечего.

**РЕШЕНО (2026-09-04, v1.2.410)**: подтверждено логом — значок ВК был пуст при непрочитанном (`vk-src msgBadge=1`, но рейл 0). Причина именно предсказанная: `countUnreadVK` метод 2 искал «Мессенджер» узко (`a[href*=im], nav a, aside a`), а на vk.ru это `[role="link"]` вне nav. Фикс внесён — селектор метода 2 расширен до `a, [role="link"]` (текст-фильтр `/мессенджер/i` оставлен → «Друзья»/«Игры» не подхватываются). Тест `unreadCountersVK.vitest.js` (4). Откат: `git checkout main/preloads/utils/unreadCounters.js`. Ожидает визуальной проверки пользователем (значок ВК показывает число).

**Уточнение (2026-09-04, v1.2.411, по ревью)**: метод 2 сделан точным — сначала берём число из бейджа-счётчика ВНУТРИ пункта, а число из текста только для КОРОТКОЙ подписи (≤30 симв.). Причина: `Node.textContent` (MDN) склеивает текст всех вложенных узлов → «первое число» у длинного превью чата (со случайным словом «мессенджер») могло быть чужим. Тест `unreadCountersVK.vitest.js` расширен до 6. Нагрузку широкого поиска (троттлинг) осознанно не трогали — преждевременная оптимизация неизмеренного пути. Урок про два расходящихся счётчика ВК — в [[webview-navigation-ui]].
