### v1.2.433 — Сторож пустого экрана переведён на признак «ровная заливка» (порог яркости оказался негодным) + исправлена НЕВЕРНАЯ запись о корне провала

**Что показал журнал после v1.2.432** (сторож наконец заговорил): `[black-watchdog] проверка #1: пиксели через bitmap, яркость 32, точек 8935, чёрный=false`.

**ДВА ВЫВОДА ИЗ ЭТОЙ СТРОКИ**:
1. **Моя догадка v1.2.432 была НЕВЕРНОЙ и опровергнута фактом.** Я записал, что причина провала — «`getBitmap()` возвращает `Buffer`, которого нет при `nodeIntegration: false`, поэтому пиксели не читались». Журнал показал `пиксели через bitmap` + 8935 точек → **чтение работает**. Неверная запись исправлена в [[webview-injection]] (помечена как опровергнутая, рядом записан настоящий корень) — чтобы не уводить будущего читателя не туда.
2. **Настоящий корень: порог «чёрного» по ЯРКОСТИ негодный.** Порог стоял `BLACK_LUM = 12`, а «чёрный» на вид экран МАКС меряется как **яркость 32** — у МАКС тёмный фон `rgb(23, 24, 28)` ≈ 25 (эта строка была в журнале и раньше: `fullOverlay=DIV. bg=rgb(23, 24, 28)`) плюс немного светлых точек. 32 > 12 → сторож честно решал «не чёрный». Поднять порог до 35 НЕЛЬЗЯ: нормально нарисованный тёмный чат тоже даёт 25-35 → начали бы пинать рабочую вкладку.

**ФИКС v1.2.433** ([webviewBlackWatchdog.js](../../src/utils/webviewBlackWatchdog.js), 160/300): главный признак — **РАЗБРОС** яркости, а не её величина. У ровной заливки (ничего не нарисовано) разброс ≈0; у нарисованного чата (текст, аватарки, пузыри) — десятки. Новые чистые функции: `frameStats(bytes)` → `{avg, stdev, min, max, samples}` и `isBlankFrame(stats)` → «пусто = ровный (`stdev < FLAT_STDEV=6`) ИЛИ почти чёрный (`avg < BLACK_LUM=12`)». Порог яркости оставлен вторым (запасным) признаком. В журнал пишутся ВСЕ цифры (`яркость, разброс, мин, макс, точек`) → порог настраивается по факту, а не на глаз.

**Тесты** ([webviewBlackWatchdog.vitest.js](../../src/__tests__/webviewBlackWatchdog.vitest.js), 165/400, **18/18**) — две ловушки на реальные провалы: (а) **ровная тёмная заливка яркостью 32 → ОБЯЗАН быть пинок** (ровно тот случай, что не срабатывал); (б) **нечем прочитать пиксели → ОБЯЗАНО быть предупреждение** (ловушка провала v1.2.431). Плюс: нарисованный чат (большой разброс) → пинка НЕТ; почти чёрный → пусто по яркости; мало точек → решения не принимаем; предохранитель 3 пинка; спрятанная вкладка; предупреждение один раз.

**Заодно (вынужденно): разбит `changelogData.js`** — при добавлении записи он стал 901 строки против потолка 900, и тест лимитов потребовал разбить (а не поднимать лимит). Старые записи вынесены в новый [changelogDataArchive.js](../../src/utils/changelogDataArchive.js) (371 строка, исключение 400 — чистый файл-данных) и подставляются обратно в общий массив через `...CHANGELOG_ARCHIVE`. **Данные НЕ удалены** — это принципиально: `changelogData.vitest.js` проверяет наличие старых версий (0.95.20-25), и прошлое «подрезание древних записей» уже ломало этот тест (регресс v1.2.418). Потребители не изменились (`CHANGELOG` и `getChangelogSince` те же). `changelogData.js` 901→537.

**Проверки**: node --check (3 файла) OK; линт 0 (`src/` + `main/`, 0 предупреждений); сторож 18/18; changelog 8/8 (данные целы после разбиения); лимиты 611/611 (бюджет renderer 35940→35990); полный vitest. **Требует ПОЛНОГО перезапуска.**

### v1.2.432 — Сторож чёрного экрана научен ПИСАТЬ в журнал (был молчаливым) + запасной способ чтения пикселей

**ПРОВАЛ (фиксируется честно).** Сторож чёрного экрана из v1.2.431 **не сработал ни разу**: пользователь установил сборку v1.2.431, чат МАКС снова стал чёрным, а в журнале — **0 записей `black-watchdog`**.

**Как нашли**: журнал сеанса v1.2.431 (старт 09:30:37) — `black-watchdog` встречается 0 раз, ошибок 0, при этом рядом `[webview-relayout] 1px-пинок … для custom_1772704264107` в 09:59:15. Оба механизма стоят под ОДИНАКОВЫМИ условиями (`activeId` + не-нативная вкладка) → значит эффект сторожа монтировался и таймер тикал (~4 тика за 47с), но каждый раз тихо выходил.

**ДВА КОРНЯ (🟢, по коду + офиц. доке)**:
1. **Пиксели читались способом, недоступным в этом окне.** Использовался только `NativeImage.getBitmap()`, а он по офиц. доке Electron возвращает **`Buffer`** — тип Node.js. Главное окно создаётся с `nodeIntegration: false` ([windowManager.js:70-76](../../main/utils/windowManager.js)) → `Buffer` в контексте страницы отсутствует. Ветка `typeof img.getBitmap === 'function' ? … : null` давала `null` → `frameBrightness(null)` → `{avg:-1, samples:0}` → условие `samples < 10` → выход.
2. **Выход был МОЛЧАЛИВЫМ.** Логи стояли только на «пнул» и «исключение». Путь «не смог прочитать пиксели» ничего не писал → по журналу нельзя было отличить «проверил, кадр не чёрный» от «не измерил вообще». Это скрыло корень №1 на целый цикл (сборка + установка + проверка пользователем).

**ФИКС v1.2.432** ([webviewBlackWatchdog.js](../../src/utils/webviewBlackWatchdog.js), 130/300):
- Чтение пикселей вынесено в отдельную `readFramePixels(img)` с ДВУМЯ способами: (1) `getBitmap()` — если доступен; (2) **запасной** `toDataURL()` → `new Image()` → `<canvas>` → `getImageData()`. Второй способ — чистый веб (офиц. `NativeImage.toDataURL()` возвращает **строку**, `Buffer` не нужен), поэтому работает при `nodeIntegration: false`. Кадр уменьшается до ≤160px по большей стороне (скорость).
- Функция **никогда не молчит**: возвращает `{bytes, via}` либо `{bytes:null, via:'none', err:<причина>}`.
- Сторож пишет в журнал: первые **2** проверки всегда (`INFO`: чем прочитал, яркость, точек, чёрный=да/нет), далее — только при чёрном кадре (`WARN` + пинок) либо при неудаче чтения (`WARN`, **один раз**, без спама).
- Сохранены: порог `BLACK_LUM=12`, предохранитель «не больше 3 пинков на открытие», приём пинка (1px обёртки + возврат через 2 кадра отрисовки, Ловушка 64).

**Тест-ловушка на этот провал** ([webviewBlackWatchdog.vitest.js](../../src/__tests__/webviewBlackWatchdog.vitest.js), 122/400, **14/14**): отдельный тест «пиксели прочитать нечем → ОБЯЗАНО быть предупреждение» (раньше тут была тишина), плюс «светлый кадр → пинка нет, но проверка записана», «предупреждение пишется один раз», «нет capturePage → предупреждение», яркость (пусто/чёрный/белый), предохранитель, спрятанная вкладка.

**Проверки**: node --check OK; линт 0; сторож 14/14; лимиты; полный vitest. **Требует ПОЛНОГО перезапуска.**

**Что теперь увидим в журнале (это и есть цель правки)**: при открытии веб-вкладки — 2 строки `[black-watchdog] проверка #N: пиксели через bitmap|dataurl, яркость …, чёрный=…`. Если чёрный — `WARN … → 1px-пинок перерисовки #1`. Если пиксели не читаются ни одним способом — `WARN … не смог прочитать пиксели кадра: <причина>` (тогда следующий шаг — перенести замер в главный процесс, там `Buffer` есть).

**Остаточный риск (честно)**: не проверено живьём, даёт ли `toDataURL()` пиксели в этом окне — **если и он окажется недоступен, сторож теперь об этом ПРЯМО напишет** (в прошлый раз молчал). Это и есть главный смысл правки: следующий круг диагностики не будет вслепую.

### v1.2.430 — Анти-завал уведомлений: лавина из одного чата не топит оператора (счётчик растёт, карточек ≤ порога)

**Жалоба**: из чата «Общий чат» МАКС «бесконечно сыплются уведомления» (20+ карточек/сек).

**РАЗБОР (почему прежние правки мимо — важный урок)**: сначала думал «наблюдатель дёргается на мельтешение картинок» и поставил троттл наблюдателя (v1.2.428). Троттл СРАБОТАЛ (журнал: `[MAX-QUICK] start` теперь 3/сек вместо 420), НО поток остался 20+/сек. Пересчитал по журналу v1.2.429: **251 уведомление, 244 РАЗНЫХ текста** («Ыыы/Ыыв/Ыва/Увв/👍/👎»…) от одного отправителя → это **реальные разные сообщения** (кто-то спамит группу набором с клавиатуры), дедуп работает. Значит корень НЕ в детекте (сообщения настоящие), а в том, что **на КАЖДОЕ сообщение из одного чата — отдельная карточка, и нет ограничителя на выходе** (`COOLDOWN_MSG` для МАКС отключён, `monitor.preload.cjs:122`).

**ФИКС (на ОБЩЕМ узле-выходе [webviewHandleNewMessage.js](../../src/utils/webviewHandleNewMessage.js), а не в детекторе)**: скользящее окно по каждому чату (ключ `messengerId+sender`). Если из одного чата **>5 сообщений за 5с** — лавина: карточка+звук+автоответ подавляются, но счётчик непрочитанных (badge) РАСТЁТ — **сообщения не теряются**. Порог высокий → обычная переписка (≤5/5с из одного чата) не задета; ДРУГИЕ чаты не затронуты (ключ пер-чат); ловит поток из ЛЮБОГО источника (стоит на выходе). Счётчик учёта живёт в замыкании фабрики `createHandleNewMessage` (MDN «Замыкания») — новых зависимостей нет. Единый для всех веб-мессенджеров (правило «стандарт одинаков»).

**Остаток (не в этой правке)**: чёрный экран тяжёлого чата «Общий чат» — отдельная беда ПРОРИСОВКИ (DOM загружен, не рисуется); при желании — принудительный «толчок». Причину спама (человек лупит по клавиатуре) не устраняем — это сторона МАКС.

Файлы: `src/utils/webviewHandleNewMessage.js` (221/300), `src/__tests__/chatFloodThrottle.vitest.js` (new, 3 проверки), `src/__tests__/fileSizeLimits.test.cjs` (бюджет 35745→35770). Проверки: node --check OK; линт 0; flood-тест 3/3; лимиты 608/608; полный vitest. **Требует ПОЛНОГО перезапуска + визуальной проверки** (спам в группе МАКС → нет ливня карточек, но badge растёт; другие чаты уведомляют как обычно).

### v1.2.429 — Убрано предупреждение MaxListenersExceeded (11 did-stop-loading) + закрыт TODO-34

**Что**: в журнале красным светилось `MaxListenersExceededWarning: 11 did-stop-loading listeners added to [WebContents]`. Это предупреждение (не падение).

**КОРЕНЬ (доказан стек-трейсом из журнала, 🟢)**: временная ловушка `process.on('warning')` (v1.2.332, TODO-34) поймала стек — он ЧИСТО внутренний для Electron: `WebContents.executeJavaScript` → `waitTillCanExecuteJavaScript` → `once('did-stop-loading')`. То есть `executeJavaScript` ждёт готовности страницы через одноразовый слушатель; при медленной загрузке (в dev старт ~2 мин) несколько параллельных `executeJavaScript` копят 11 самоснимающихся `once`-слушателей → предел 10 → предупреждение. **Утечки НЕТ** — слушатели срабатывают и снимаются, когда страница догрузится. Проявилось 1 раз при долгом dev-старте.

**ФИКС**: (1) удалена отработавшая временная диагностика `process.on('warning')` из [main.js](../../main/main.js) (TODO-34 закрыт — стек найден); (2) `app.on('web-contents-created')` → `wc.setMaxListeners(30)` для всех webContents — предупреждение больше не шумит (это и рекомендует само сообщение Electron: «Use emitter.setMaxListeners()»). ### v1.2.426 — МАКС: убран ДУБЛЬ карточки уведомления (наблюдатель + список на одно сообщение) — наблюдатель ждёт enriched дольше
