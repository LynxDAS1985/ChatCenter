# Архив changelog: v1.2.463 – v1.2.465

Вынесено из [`../features.md`](../features.md) 2026-09-16 (v1.2.469), чтобы активный файл
остался в пределах лимита 100 КБ. Правила архива — в [`README.md`](README.md).

Темы этих версий:
- **v1.2.465** — честная подпись вместо «[медиа]» для сообщений, которые библиотека Telegram
  не понимает (`messageUnsupported`), + прогрев файлов против долгого первого запуска.
- **v1.2.464** — вместо красного экрана при сорванной догрузке поднимается окно «Повторить»:
  сигнал до него не доходил, потому что React перехватывал отказ сам.
- **v1.2.463** — МАКС: свои отправленные сообщения перестали уведомлять (признак исходящего
  измеряли, но решения по нему не принимали).

⚠️ Действующие правила НЕ в архиве: решения — ADR-059…ADR-062 в `decisions.md`, ловушки —
`mistakes/webview-injection.md` и `mistakes/electron-core.md`, отладка уведомлений —
`notifications-debug.md`.

#### ЧАСТЬ 1 — «[медиа]» превратилось в честную подпись (закрыт вопрос из v1.2.461)

**ЧТО БЫЛО**: сообщение показывалось как «[медиа]» в уведомлении, «📎 вложение» в списке чатов и
ПУСТОЙ пузырь в переписке. В v1.2.461 показ сознательно НЕ трогали: вид сообщения был неизвестен, а
любая подпись наугад могла оказаться неправдой.

**ЗАПИСЬ ИЗ v1.2.461 СРАБОТАЛА И НАЗВАЛА ВИД.** Журнал `chatcenter.log` 2026-09-16 08:30:51:
`[tdlib-empty] вид сообщения "messageUnsupported" — показывать нечего`.
Заодно журнал назвал ещё два: `messageChatJoinByLink` и `messageChatAddMembers` (служебные записи).

🥇 **ФАКТ УРОВНЯ 1** — официальная документация TDLib, класс `messageUnsupported`:
«A message content that is not supported in the current TDLib version.»
(Содержимое сообщения, не поддерживаемое текущей версией библиотеки.)
Значит содержимое показать **НЕВОЗМОЖНО в принципе** — из трёх исходов, перечисленных в v1.2.461,
подтвердился первый. Правильный ответ — честная подпись.

**ВЫБОР СПОСОБА**
| Способ | Что даёт | Цена | Риск |
|---|---|---|---|
| ❌ Заменить заглушку в трёх местах показа | тот же результат | больше кода | **три копии** подписи разъедутся при первой же правке |
| ✅ **Взято**: подставить текст в РАЗБОРЕ сообщения | текст подписи живёт в ОДНОМ месте | ~15 строк | нет — показ берёт текст оттуда же, откуда и раньше |

🔴 **ДОВОДКА v1.2.466 (находка придирчивого ревью)**: сначала здесь было записано, что правка «чинит
все три места разом». Это оказалось **неправдой** — проверка запуском показала: список чатов строится
отдельной функцией `messagePreview`, которую зовут НАПРЯМУЮ ([tdlibMapper.js](../main/native/backends/tdlibMapper.js),
строка 363), минуя разбор, и он продолжал отдавать «⚙️ служебное сообщение». В v1.2.466 эта функция
тоже спрашивает общий словарь — ПОСЛЕ знакомых видов, чтобы не перекрыть реальный текст сообщения.
Теперь три места действительно согласованы; закреплено проверкой «список чатов и разбор дают ОДИН
И ТОТ ЖЕ текст» и отдельной проверкой ПОРЯДКА обращения к словарю.

**ЧТО СДЕЛАНО**: новая чистая `emptyMessageFallbackText(вид)` в
[tdlibMapperMedia.js](../main/native/backends/tdlibMapperMedia.js) — короткий словарь видов, про
которые ТОЧНО известно, что содержимого нет. В [tdlibMapper.js](../main/native/backends/tdlibMapper.js)
подпись подставляется сразу после записи в журнал, если сообщение вышло пустым.

🔴 **СЛОВАРЬ УМЫШЛЕННО КОРОТКИЙ — В НЁМ ОДНА СТРОКА.** Служебные записи («добавлен участник»,
«присоединился по ссылке») туда НЕ добавлены: у них уже есть свои подписи в `messagePreview`
для списка чатов, а показ их в переписке — отдельная задача (записана в `code-todo.md`).
Незнакомый вид подписи не получает — выдумывать за пользователя нельзя.

🔴 **ПОЧЕМУ ПОДПИСЬ СТАВИТСЯ ПОСЛЕ РАСЧЁТА «ЭТО ЭМОДЗИ?»**: иначе подпись из слов сочли бы
эмодзи-сообщением и нарисовали гигантским шрифтом. Закреплено отдельной проверкой.

#### ЧАСТЬ 2 — прогрев файлов против долгого первого запуска (лечит корень жалобы v1.2.464)

**ЧТО БЫЛО** (жалоба 2026-09-16): вместо приложения красный экран
`Failed to fetch dynamically imported module: …/src/native/NativeApp.jsx`.
В v1.2.464 починили СЛЕДСТВИЕ — вместо тупика поднимается окно «Повторить». Причина осталась.

**РАЗБОР ПРИЧИНЫ** (журнал запуска 08:30:44):
| Что смотрел | Что нашёл |
|---|---|
| запросов к серверу разработки | **443** |
| коды ответов | **410 из 410 успешных**, ни одного отказа |
| самые медленные | **80–82 секунды** |
| как отвечал | **волнами**, с паузами до **116 секунд** между ними |
| те же файлы на тёплом сервере | **0,003 секунды** |

🥇 **ФАКТ УРОВНЯ 1** — документация Vite (`DOCS/Vite docs/guide/performance.md`):
«Связь между файлами становится известна только ПОСЛЕ обработки файла. Если один файл обрабатывается
долго, следующий ждёт своей очереди, и так далее. Это создаёт внутренний водопад даже при встроенной
предварительной обработке.» Лекарство там же — `server.warmup`: «готовит файлы заранее и кэширует
результат; улучшает первую загрузку страницы и предотвращает водопад обработки».

**ЧТО СДЕЛАНО**: в [electron.vite.config.js](../electron.vite.config.js) добавлен `server.warmup` с
**пятью** файлами — ровно теми, что в журнале жалобы либо упали, либо шли дольше всех (точка входа,
главный экран, стили и два ленивых куска). Документация предупреждает не перегружать список — поэтому
он короткий. На сборку не влияет: прогрев работает только у сервера разработки.

**СОВМЕСТИМОСТЬ ПРОВЕРЕНА ПО ТИПАМ ПАКЕТОВ** (не по памяти):
`BaseViteConfig<T> extends Omit<UserConfig, 'build'>` в `electron-vite` 5 — значит раздел renderer
принимает весь конфиг Vite, кроме сборки; `warmup?: { clientFiles?: string[] }` есть в типах Vite 7.3.1.

🟡 **ЧЕСТНАЯ ОГОВОРКА**: это лечит ОДНУ из трёх версий причины (водопад обработки). Две другие —
несколько приложений на один сервер (в тот день их стартовало три: 08:30:44, 08:34:01, 09:39:35) и
общая занятость машины при старте — настройкой не лечатся. **(не доказано, что прогрев уберёт тормоза
полностью)**

**СТРАЖ**: [projectHealth.test.cjs](../src/__tests__/projectHealth.test.cjs) проверяет, что прогрев на
месте и все перечисленные файлы СУЩЕСТВУЮТ. Нужен потому, что Vite на несуществующий файл в списке
прогрева **не ругается** — просто молча его не греет; переименовали файл → прогрев тихо умер.

🔴 **МОЯ ОШИБКА, КОТОРУЮ ПОЙМАЛ СОБСТВЕННЫЙ ПРОГОН «НАОБОРОТ»**: первая редакция стража искала
подстроку `warmup` — и подмена `warmup:` на `warmupOFF:` её не смутила. Переписано на поиск точного
объявления. Урок: страж, ищущий подстроку, ловит только удаление, но не подмену.

**ЧТО ПРОВЕРЕНО ПО АУДИТУ И ОСТАВЛЕНО КАК ЕСТЬ**

### v1.2.464 — 🔴 ЖАЛОБА «красный экран Failed to fetch вместо окна повтора»: окно было, но сигнал до него не доходил

**ЖАЛОБА** (2026-09-16, скриншот): вместо приложения — красный текст
`⚠ Ошибка рендера: Failed to fetch dynamically imported module: http://localhost:5173/src/native/NativeApp.jsx`.
Тупик: ни причины понятным языком, ни кнопки, ни повтора.

**СНАЧАЛА РАЗОБРАЛИСЬ, ПОТОМ ЧИНИЛИ.** Разбор жалобы (код НЕ менялся) дал точную картину:
| Что смотрел | Что нашёл |
|---|---|
| журнал старта 08:30:44 (v1.2.463) | приложение запросило **443** куска кода по одному |
| коды ответов | **410 из 410 — «всё хорошо»**, ни одного отказа сервера |
| время ответов | самые медленные — **80–82 секунды** |
| когда сдалось | 08:36:20 (AISidebar) и 08:36:57 (NativeApp) |
| те же файлы сейчас | отдаются за **0,003 секунды** |

То есть сбоя в коде НЕ было: dev-сервер всё отдал, но так медленно, что ленивая догрузка не
дождалась. Это НЕ было следствием правок v1.2.461-463 (коммиты 2026-09-15 19:07–19:14, жалоба
2026-09-16 08:36; упали ДВА разных куска — одинаковой опечатки в двух файлах быть не может).

**КОРЕНЬ ПОЧЕМУ НЕ БЫЛО ОКНА (🟢, доказан журналом + чтением кода)**: окно повтора у приложения
**уже есть** с v1.2.452 — встроенный скрипт в [index.html](../index.html) с причиной, обратным
отсчётом, лестницей пауз и кнопкой «Повторить сейчас». Оно не поднялось:
- `grep -c "boot-net"` по журналу за день = **0** — окно не показывалось ни разу;
- заставка висела до 08:37:07 («дальний предохранитель 180с»), то есть панель окна была НА ЭКРАНЕ
  в обе минуты падения → показать было КУДА;
- значит до окна не дошёл сигнал. Оно слушало только `unhandledrejection`, а `React.lazy`
  перехватывает отказ догрузки САМ и превращает его в ошибку отрисовки → отказ становится
  обработанным → событие не возникает. Оба перехватчика ошибок отрисовки
  ([main.jsx](../src/main.jsx) и [ErrorBoundary.jsx](../src/components/ErrorBoundary.jsx))
  рисовали тупик и про окно не знали.

Два сторожа стояли у разных дверей и не разговаривали друг с другом.

**ВЫБОР СПОСОБА (сравнивались два)**
| Способ | Что даёт | Цена | Риск |
|---|---|---|---|
| ❌ Проверять текст ошибки в КАЖДОМ перехватчике | то же поведение | мало кода | **три копии** маски (index.html + 2 файла) → правку одной забудут в других |
| ✅ **Взято**: «пульт» окна получает метод `onLoadError(текст)` | маска одна на всех; перехватчики просто передают сообщение | +2 строки в бюджет интерфейса | нет |

**ЧТО СДЕЛАНО**
1. [index.html](../index.html): маска сбоя загрузки вынесена в одну переменную `LOAD_FAIL`;
   добавлен `onLoadError(message)` — сам решает, сбой ли это догрузки, и поднимает окно.
   Старый путь (`unhandledrejection`) теперь ходит через ту же дверь.
2. [main.jsx](../src/main.jsx) и [ErrorBoundary.jsx](../src/components/ErrorBoundary.jsx):
   в перехват ошибки отрисовки добавлена одна строка — передать сообщение в `onLoadError`.
   Красный экран НЕ убран: обычные ошибки в коде по-прежнему видны разработчику.

🔴 **МОЯ ОШИБКА, КОТОРУЮ ПОЙМАЛ ТЕСТ**: первая редакция `onLoadError` возвращала «показал окно»
даже когда показывать было НЕКУДА (приложение уже запустилось, заставку сняли). Починено:
`show()` теперь возвращает, есть ли окно на экране после вызова, а `onLoadError` возвращает
именно её ответ. Урок: если функция отвечает «да», это «да» должно быть проверяемым.

**ЧЕГО ОКНО ДЕЛАТЬ НЕ ДОЛЖНО** (закреплено ловушками в тесте):
- не подниматься на ЧУЖУЮ ошибку отрисовки (опечатка в коде) — иначе оно скрывало бы настоящие поломки;
- не подниматься, когда приложение уже работает и заставки нет — там у панелей своя кнопка «Повторить».

**КАК ПРОВЕРЕНО**
- [bootNet.vitest.js](../src/__tests__/bootNet.vitest.js) 23 → **30 проверок**: тот самый текст из
  жалобы поднимает окно; второй упавший кусок тоже; чужие ошибки НЕ поднимают; маска одна на всех
  (и её копий нет в `src/`); проводка обоих перехватчиков; старый путь цел; «приложение работает → окна нет».
- Прогон «наоборот», **5 из 5 пойманы**: убрать вызов из общего перехватчика; убрать из
  компонентного; размножить маску; поднимать окно на любую ошибку; вернуть `show()` без ответа.
- Линт 0; лимиты **654/654**; бюджет интерфейса 34632/34640.

**ЧТО ПРОВЕРИТЬ ВРУЧНУЮ**: запустить при выключенном dev-сервере (или остановить его на старте) —
вместо красного экрана должно появиться окно «Не удалось загрузить приложение» с отсчётом и кнопкой

**ОСТАТОЧНЫЕ РИСКИ**: (а) 🟡 сама причина тормозов dev-сервера (80 секунд на файл при холодном

### v1.2.463 — 🔴 ЖАЛОБА «почему мои сообщения приходят в уведомления» (МАКС): признак «своё» измеряли, но решения по нему не принимали

**ЖАЛОБА** (2026-09-15, скриншот): карточка уведомления «Цывилько Дмитрий Николаевич / Макс / 18:20 /
смотрю». Слово «смотрю» — СОБСТВЕННОЕ только что отправленное сообщение пользователя.

**КОРЕНЬ (🟢 доказан журналом + чтением кода)**: у МАКС **не было проверки «это моё исходящее»**.
С v1.2.427 в [maxDiagnostics.js](../main/preloads/utils/maxDiagnostics.js) жила ВРЕМЕННАЯ диагностика
`maxOutgoingReport` — она считала признаки исходящего и возвращала **строку для журнала**. Поиск по
всему `main/` и `src/` давал ровно два упоминания: объявление и подстановка в текст записи.
**Потребителя вывода не было.** Охранник записывал «прошёл свой» и открывал дверь.
