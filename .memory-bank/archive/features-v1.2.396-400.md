### v1.2.400 — Ранний экран загрузки «ЦентрЧатов» = живая заставка с кружками (а не сухое «Загрузка…»)

**ЗАЧЕМ**: жалоба — после старта на «ЦентрЧатов» (v1.2.399) в главной области сухая надпись «Загрузка…», а не наша заставка с кружками («где наша разработка?»). Причина: `NativeAppFallback` ([appFallbacks.jsx](src/appFallbacks.jsx)) показывается, ПОКА грузится КОД нативного интерфейса (в dev ~115с), а наша `ChatListLoadingSplash` живёт ВНУТРИ NativeApp → может показаться только после его монтирования. Т.е. ранний экран был отдельным «Загрузка…».

**ЧТО** ([appFallbacks.jsx](src/appFallbacks.jsx)): `NativeAppFallback` теперь рисует ЖИВУЮ заставку — 5 градиентных кружков, вспыхивающих по очереди (как `ChatListLoadingSplash`), + «Загрузка чатов…». **Самодостаточно**: этот компонент грузится РАНЬШЕ нативного CSS (`styles-chatlist-loading.css` импортится из NativeApp) и без `store` → используются ТОЛЬКО инлайн-стили + инлайн-`@keyframes ccNfPop` (className-классы заставки тут ещё не подгружены; кружки без реальных имён — их нет до загрузки store). Так «наша разработка» видна С НАЧАЛА загрузки, а не только в конце. После монтирования NativeApp эстафету принимает настоящая `ChatListLoadingSplash` (с реальными именами чатов).

**КРАЙНИЕ СЛУЧАИ**: инлайн-keyframes глобальны, но имя `ccNfPop` уникально (без конфликтов). **DEV-оговорка**: в dev эта заставка висит ~115с (медленная сборка), в установленной сборке — секунды. **КАК ПРОВЕРЕНО**: `lint` 0; `startupDiagnostics` 4/4, `appStructure` 60/60, `rendererConsoleGuard` 0; `fileSizeLimits` 602/602 (бюджет 35510); полный `vitest`. **Требует визуальной проверки**: перезапуск → на раннем экране «ЦентрЧатов» кружки, а не сухое «Загрузка…». **ОТКАТ**: `git checkout src/appFallbacks.jsx` + версия на 1.2.399.

### v1.2.399 — Старт открывается на «ЦентрЧатов» (чаты+заставка), а НЕ на первом веб-мессенджере (Макс) + фикс лога заставки

**ЗАЧЕМ**: жалоба — при запуске сначала грузится окно Макс, потом резко все чаты; заставки не видно; чаты должны грузиться С НАЧАЛА, а не после Макса.

**КОРЕНЬ (по коду + журналу, 🟢)**: [useAppBootstrap.js:54](src/hooks/useAppBootstrap.js) на старте ставил активной `withNative[0]?.id` — ПЕРВЫЙ веб-мессенджер. А нативная вкладка «ЦентрЧатов» (`NATIVE_CC_TAB`) добавляется В КОНЕЦ списка ([useAppBootstrap.js:50](src/hooks/useAppBootstrap.js)) → `withNative[0]` = первый webview (у пользователя `custom_1772704264107` = Макс, подтверждено журналом `messengers loaded ids=custom_1772704264107,...`). Итог: приложение всегда открывалось на Максе, он грузился первым, чаты — потом. Веб-вкладки видны стопкой (активная сверху, z-index 2 — [App.jsx:774](src/App.jsx)), поэтому был виден Макс.

**ЧТО**:
1. [useAppBootstrap.js:54](src/hooks/useAppBootstrap.js): активной на старте ставим **`NATIVE_CC_ID`** («ЦентрЧатов»), если он в списке (иначе запасной прежний — первый веб). Веб-мессенджеры всё равно грузятся в фоне (стопка, НЕ `display:none` — иначе Chromium усыпит) → уведомления из них работают; меняется только КАКАЯ вкладка видна первой. Теперь старт: «Загрузка» → список чатов + заставка сборки, без Макса впереди.
2. [ChatListLoadingSplash.jsx](src/native/components/ChatListLoadingSplash.jsx) — фикс лога v1.2.398: метку времени показа ставили по `!rendered`, но при первом монтировании `rendered` уже мог быть `true` (`useState(show)`) → метка не ставилась → в лог шла мусорная «длительность» = сам таймстамп (`~1788506507794мс`). Теперь метка по `shownAtRef` (первый раз, когда show=true) + сброс после скрытия. Лог `заставка ПОКАЗАНА` / `скрыта, была видна ~Nмс` теперь корректен.

**КРАЙНИЕ СЛУЧАИ**: native_cc нет в списке (сбой) → запасной вариант прежний (первый веб). Веб-уведомления работают (вкладки в фоне). **DEV-оговорка**: native грузится ~+115с в dev (медленная раздача модулей) — на это время видно «Загрузка», затем чаты+заставка; в установленной сборке — секунды. **КАК ПРОВЕРЕНО**: `lint` 0; `ChatListLoadingSplash.vitest` 8/8; `fileSizeLimits` 602/602; полный `vitest`. **Требует визуальной проверки**: перезапуск → приложение открывается на ЦентрЧатов (не Макс); в журнале `[chatload] заставка ПОКАЗАНА` + корректная `видна ~Nмс`. **ОТКАТ**: `git checkout src/hooks/useAppBootstrap.js src/native/components/ChatListLoadingSplash.jsx` + версия на 1.2.398.

### v1.2.398 — Заставка сборки чатов: гарантия минимального времени видимости (мелькала) + точная запись показа/скрытия в журнал

**ЗАЧЕМ**: жалоба — «где заставка загрузки чатов? сразу Макс опять» (после перезапуска заставки НЕ видно). Разбор: логика заставки отрабатывала (журнал `[chatload] первая загрузка завершена`), НО по журналу было видно только ЗАВЕРШЕНИЕ, а не показалась ли заставка и на сколько. Загрузка чатов из КЭША быстрая (`loadCachedChats` мгновенно) → `loadChats` резолвится за ~2с, а часть перезапусков — ещё быстрее → заставка мелькала доли секунды и терялась среди появления окна/Макса. **Причина не подтверждена замером** (гипотеза: слишком короткое время видимости) → добавлены И запись, И гарантия.

**ЧТО** ([ChatListLoadingSplash.jsx](src/native/components/ChatListLoadingSplash.jsx)):
1. **Гарантия видимости**: если заставка стала видимой — держим её МИНИМУМ `MIN_VISIBLE=2200мс` (даже если загрузка завершилась быстрее), потом плавный финал. Быстрый кэш больше не «съедает» показ.
2. **Точная запись в журнал**: `[chatload] заставка ПОКАЗАНА` при появлении + `[chatload] заставка скрыта, была видна ~Nмс` при скрытии. Теперь по логам ТОЧНО видно, показалась ли заставка и на сколько (раньше — только «загрузка завершена»).

**КРАЙНИЕ СЛУЧАИ**: загрузка дольше 2200мс → держим по факту загрузки (min не мешает); повторный show во время ожидания min → таймеры чистятся (`clear()` в начале эффекта). Существующие тесты 8/8. **DEV-оговорка**: заставка живёт в панели списка чатов, показывается после монтирования NativeApp (в dev ~+105с из-за медленной раздачи модулей); ускорение старта — отдельная тема. **КАК ПРОВЕРЕНО**: `lint` 0; `ChatListLoadingSplash.vitest` 8/8; `fileSizeLimits` 602/602 (бюджет 35480); полный `vitest`. **Требует визуальной проверки + журнала**: перезапуск → заставка видна ≥2с; в журнале строки `заставка ПОКАЗАНА`/`скрыта … Nмс`. **ОТКАТ**: `git checkout src/native/components/ChatListLoadingSplash.jsx` + версия на 1.2.397.

### v1.2.397 — Старт: ХОЛОДНЫЙ старт — убран пустой экран по-настоящему (страховка заставки без ложной проверки «жив ли main.jsx»)

**ЗАЧЕМ**: жалоба (со скриншотами) — «Загрузка…» → ДОЛГИЙ пустой тёмный экран → значок Макс → чат Макс → чаты; заставки сборки чатов не видно. v1.2.395 это чинил, но НЕ на холодном старте — я нашёл баг ещё в ревью v1.2.395, но не успел закрыть (переключились на счётчик Ozon). Журнал v1.2.396 подтвердил на живой машине.

**КОРЕНЬ (по журналу v1.2.396, 2026-09-04)**: страховка боот-заставки ([boot-probe.js](src/boot-probe.js)) на 30с проверяла `window.__ccHideSplash` (жив ли main.jsx) и, если его нет, убирала заставку. Но на ХОЛОДНОМ старте (пустой кэш dev-сервера / первый запуск) тело `main.jsx` (которое и ставит `__ccHideSplash`) выполняется ПОЗЖЕ 30с — журнал: `splash +30006ms safety hid splash: main.jsx не запустился за 30с`, а `main +60738ms react root created` (main.jsx реально запустился на 60с). Итог: на 30с заставку убрали ложно → ~30-105с пустого экрана (`NativeApp mounted +105249ms`). Проверка `__ccHideSplash` на фиксированной ранней секунде НЕНАДЁЖНА (метку ставят поздно).

**ЧТО** ([boot-probe.js](src/boot-probe.js)): убрана ложная проверка. Страховка теперь — ПРОСТО дальний таймер **180с**. В норме заставку убирает `appReady` ([useAppBootstrap.js:87](src/hooks/useAppBootstrap.js) → `__ccHideSplash`) и на холодную (~60с), и на тёплую (быстро). Таймер 180с — лишь предохранитель на реально зависший запуск (битый бандл / appReady не наступил). 180 > худшего холодного (~105с) с запасом. Заглушка `NativeAppFallback` (v1.2.395) закрывает промежуток appReady→монтирование «Загрузкой…».

**ПРО ЗАСТАВКУ СБОРКИ ЧАТОВ**: она РАБОТАЕТ (журнал `[chatload] первая загрузка завершена: чатов=241`), но показывается ~2с ПОСЛЕ монтирования NativeApp (+105с на холодную dev) — на фоне 105с боота теряется. Это DEV-артефакт: в реальной сборке боот — секунды, и последовательность «Загрузка → заставка сборки чатов → список» видна нормально. Сам dev-старт (~105с) НЕ ускоряли (это раздача сотен модулей dev-сервером).

**ОПАСНАЯ ЗОНА (boot)**: правка чисто ВИЗУАЛЬНАЯ (тайминг снятия заставки), на загрузку кода/данных не влияет. **КАК ПРОВЕРЕНО**: `node --check` OK; `lint` 0; `startupDiagnostics` 4/4, `appStructure` 60/60, `rendererConsoleGuard` 0; полный `vitest`. **Требует визуальной проверки на ХОЛОДНОМ старте** (`rm -rf node_modules/.vite` → запуск: «Загрузка…» держится без пустоты до списка). **ОТКАТ**: `git checkout src/boot-probe.js` + версия на 1.2.396.
