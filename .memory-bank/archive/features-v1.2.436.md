### v1.2.436 — ФИКС «выкидывает в ЦентрЧатов»: загрузка списка мессенджеров отбирала активную вкладку на каждом монтировании (в dev — на каждую горячую перезагрузку)

**ЖАЛОБА (2026-09-09)**: «постоянно выкидывает сюда, очень часто, с озона сейчас например выкидывает, я сам не переходил». Пользователь работал в Ozon, его выбрасывало на нативную вкладку «ЦентрЧатов».

**КОРЕНЬ (🟢 доказан журналом + кодом)**: в [useAppBootstrap.js](../../src/hooks/useAppBootstrap.js) стояло `setActiveId(withNative.some(m => m.id === NATIVE_CC_ID) ? NATIVE_CC_ID : withNative[0]?.id)` — **БЕЗУСЛОВНО**. Писалось это как стартовое поведение (v1.2.399: открывать «ЦентрЧатов», а не первый веб-мессенджер), но у эффекта пустой список зависимостей `[]`, т.е. он выполняется на КАЖДОЕ монтирование дерева. Плюс те же безусловные сбросы были в двух запасных путях (нет `window.api` / загрузка не удалась) — а в шапке файла прямо написано «Защита от HMR (window.api может быть undefined)», т.е. запасной путь и есть путь горячей перезагрузки.

**ДОКАЗАТЕЛЬСТВО ИЗ ЖУРНАЛА** (сеанс 12:42:11): `messengers:load` выполнился **6 раз** — 12:43:27 (штатный старт), затем 13:12:57, 13:13:09, 13:13:36, 13:13:55, 13:14:05. Каждому из ПЯТИ лишних раз за ~1 секунду предшествовал `dev-request … /src/App.jsx?t=<метка>` — сигнатура горячей перезагрузки Vite; в тех же пачках перезапрашивались именно те файлы, которые в тот момент правились (`/src/utils/webviewSetup.js`, `/src/hooks/useWebViewLifecycle.js`). Между 12:43 и 13:12 (полчаса без правок кода) — ни одной перезагрузки. Пользователь запускает приложение в режиме разработки из терминала, поэтому для него это происходило постоянно.

**ЧТО ОПРОВЕРГНУТО ПО ХОДУ** (чтобы не искать снова): настройка «автопереключение на новое сообщение» (`autoSwitchOnMessage`) в настройках пользователя ОТСУТСТВУЕТ (выключена) и переключает на сам мессенджер, а не на «ЦентрЧатов»; закреплённых задач в доке 0 (путь `dock:go-to-chat` невозможен); в карточке уведомления кликабельны только кнопки, не вся площадь; `globalShortcut` в проекте нет (горячие клавиши не ловятся, пока фокус внутри страницы мессенджера).

**ФИКС**: выбор вкладки вынесен в чистую функцию `pickActiveTabId(prevId, messengers, nativeId)` — новый [shared/activeTabChoice.js](../../shared/activeTabChoice.js) (в `shared/`, т.к. renderer-бюджет `src/` был на исходе — 22 строки запаса; так же поступили с `shared/notifAlbum.js` в v1.2.95). Правило: **если вкладка уже выбрана и существует — не трогаем**; иначе «ЦентрЧатов»; иначе первая живая запись списка; иначе null. Текущее значение читается через функцию-обновитель `setActiveId(prev => …)` — по доке React (`useState`): *«If you pass a function as nextState, it will be treated as an updater function. It must be pure, should take the pending state as its only argument»* — то есть зависимости эффекта менять не пришлось. Оба запасных пути закрыты минимально: `setActiveId(prev => prev || DEFAULT_MESSENGERS[0].id)` (цель фолбэка сохранена, отбор вкладки убран).

**Стартовое поведение НЕ изменилось**: при первом запуске `activeId === null` ([App.jsx](../../src/App.jsx)) → открывается «ЦентрЧатов», как задумано в v1.2.399.

**Крайние случаи**: вкладка, на которой был пользователь, УДАЛЕНА из списка → уходим на «ЦентрЧатов» (иначе остались бы на несуществующей вкладке с пустым экраном); пустой список / не массив → null; битая запись в начале списка → берём первую ЖИВУЮ (эту слабость поймал собственный тест крайних случаев — сначала функция возвращала null).
