### v1.2.129 — ВК: переносы строк/абзацы поста в уведомлении (не «простыня»)

Дата: 24 июля 2026. Жалоба (со скриншотом): длинный пост канала ВК приходит в карточке уведомления одной сплошной строкой — абзацы и пункты 1️⃣2️⃣ слиплись, хотя в самом ВК форматирование есть.

**Корень (по коду + MDN).** Текст строки списка собирает `_vkNodeText` ([vk.hook.js](../../main/preloads/hooks/vk.hook.js)): обходит дочерние узлы, берёт текст и `alt` у картинок-эмодзи, но НЕ добавляет `\n` для `<br>` и блочных тегов — т.е. ведёт себя как `textContent`. Факт уровня 1 (MDN Node.textContent, <https://developer.mozilla.org/en-US/docs/Web/API/Node/textContent>): `textContent` НЕ отражает переносы от `<br>`/блочных элементов (в отличие от `innerText`, который учитывает рендер). У ВК переносы поста хранятся РАЗМЕТКОЙ (`<br>` / отдельные блоки-абзацы), а не символами `\n` → при сборе терялись. Прошлый фикс v1.2.122 (`_cleanMultiline` сохраняет `\n`) на этот случай не действовал: сохранять было нечего.

**Проверено, что виноват именно сбор (не показ/доставка).** Показ раскрытой карточки — `white-space:pre-wrap` ([notification.css:176,187](../../main/notification.css)) + текст через `textContent` ([notification.js](../../main/notification.js)) → переносы показались бы, если бы были. Обработчик входящих ([webviewHandleNewMessage.js:100-108](../../src/utils/webviewHandleNewMessage.js)) убирает только хвост «#N», `\n` не трогает; отправка из хука через `JSON.stringify` сохраняет `\n`. На скрине текст пришёл ПОЛНЫЙ и в режиме переноса, но без абзацных разрывов → разрывов в тексте нет = потеря при сборе.

**Что сделано.** В `_vkNodeText`: `<br>` → `\n`; блочные теги (DIV/P/LI/UL/OL/BLOCKQUOTE/PRE/SECTION/ARTICLE) → перенос вокруг вложенного текста. `_cleanMultiline` (без изменений) схлопывает лишние пустые строки (максимум одна пустая). Эмодзи (img alt) и инлайн-теги (SPAN и пр.) не затронуты — инлайн НЕ добавляет переносов.

**Тест.** `vkNotifyLogic.vitest.js` +3: `<br>`→перенос; блочные абзацы (DIV/P)→перенос между ними; инлайн (SPAN) без лишних переносов.

**Остаток (не закрыт).** Запасная ветка `_vkRowText` (когда спец-блок превью не найден — собирает листья через пробел + `_cleanToastText`, который `\s+`→пробел) переносы всё ещё теряет. Для каналов работает ОСНОВНАЯ ветка (есть `ChannelPostPreview`), поэтому этот пост чинится; для некоторых личных чатов возможна отдельная доработка.

**Проверка:** `node --check` OK; линт 0; лимиты 515/515 (`vk.hook.js` 253/300); `vkNotifyLogic` 12/12; `notifHooks` 87/87. Ловушка — [[webview-injection]].

### v1.2.128 — Уведомления: «невидимая стена» гаснет вместе с карточкой (по видимому, а не по счётчику)

Дата: 24 июля 2026. Жалоба: после закрытия уведомления (✕ / «Прочитано» / автотаймер) иногда остаётся невидимый след, ловящий клики; убирался только сторожем через ~15с. Требование юзера: гасить СРАЗУ при закрытии, а не через 15с.

**Корень (по коду).** Окно уведомления прячется, только когда список main `notifItems[]` становится пустым (`hideIfEmpty`, [notifHandlers.js]). Но в этом списке копятся «фантомы» от стопки/альбома (ghost-накопление — прямо задокументировано в комментариях #26). Спасательный сигнал «renderer пуст» (`rendererPure`) в `reportHeight` считался по числу записей ОКНА: `items.size===0 && container.children===0` ([notification.js:64]). Если после закрытия в `items`/DOM завис невидимый огрызок высотой 0 — счётчик >0 → `rendererPure=false` → `decideNotifResize` возвращает `ignore` (h≤0 && items>0) бесконечно ([notifResizeDecision.js]) → окно висит невидимым и ловит клики. В логе `IGNORE stale 0 (items=1)` ×196.

**Что сделано.** В `reportHeight(heartbeat, dismissFinal)` добавлен флаг `dismissFinal`. В финальном отчёте ПОСЛЕ завершения закрытия карточки (стадия 3, после `el.remove()`+`items.delete()`) вызывается `reportHeight(false, true)`. Если видимого на экране не осталось (`calcHeight()===0`), `rendererPure` становится `true` по ВИДИМОЙ высоте: `(itemsCount===0 && containerCount===0) || (dismissFinal && h===0)`. Тогда существующая ветка `clear-hide` очищает фантомы (`setNotifItems([])`) и прячет окно сразу.

**Почему безопасно.** Флаг ставится ТОЛЬКО в финале закрытия. Момент добавления карточки (slideIn, где `calcHeight===0` = карточка ещё выезжает) НЕ затронут. Правило показа `decideNotifResize` не менялось. `calcHeight` считает только видимые карточки ([notification-helpers.js:40]).

**Факты.** (1 уровень) MDN `HTMLElement.offsetHeight` возвращает 0 для скрытых/удалённых элементов → `calcHeight()===0` надёжно = «видимого нет». (2 уровень) `rendererPure` формула — [notification.js:64].

**Тестируемость.** Формула вынесена в чистую `computeRendererPure({ itemsCount, containerCount, visibleHeight, dismissFinal })` ([notification-helpers.js](../../main/notification-helpers.js)). Тест `albumLiveCard.vitest.js` (+5). Родственный путь `forceRemoveItem` проверен — правки не требует (code-todo TODO-13).

**Проверка:** `node --check` OK; линт 0; лимиты 515/515; тесты `albumLiveCard`+`notifResizeDecision` 28/28. Ловушка — [[notifications-ribbon]]. Сторож 15с оставлен запаской.

### v1.2.127 — Уведомления: heartbeat-сторож без спама в лог

Дата: 24 июля 2026. Доводка v1.2.126 по ревью (тот heartbeat спамил лог каждые 5с).

**Проблема.** v1.2.126: пока окно уведомления видимо, сторож каждые 5с писал `[notif-watchdog] alive` и слал `notif:remeasure` → renderer слал `notif:resize` → обработчик писал `[notif-resize]`. Для непропадающего уведомления (`dismissMs=0`) — бесконечный спам.

**Что сделано.** (1) Heartbeat шлётся ТОЛЬКО когда окно давно молчит: `msSinceResize > 12000` мс. (2) `reportHeight(heartbeat)`: heartbeat-отчёт отдаёт только высоту + флаг `heartbeat:true`, БЕЗ диагностики. (3) Main НЕ логирует `[notif-resize]`, если heartbeat-отчёт с действием `show` (тихий no-op). (4) Вместо `alive` — `[notif-watchdog] STUCK` только если после «поко» renderer НЕ ответил (реальный признак застрявшей стены), редко.

**Проверка:** `node --check` OK; лимиты 515/515; `mainRuntime` 98/98; линт 0. Ловушка — [[notifications-ribbon]].

### v1.2.126 — Уведомления: закрыта дыра «невидимой стены» (heartbeat-сторож)

Дата: 24 июля 2026. Возврат бага «после уведомления остаётся невидимый след, ловящий клики».

**Что показал лог.** Два цикла: первый закрылся чисто. Второй ЗАСТРЯЛ: счётчик карточек упал 5→4, renderer прислал транзиентный `raw=0 items=4 rendererPure=false` (корректно проигнорирован), и ПОСЛЕ этого отчёты `notif:resize` оборвались — окно осталось `visible`, события hide не было.

**Корень (дыра в защите).** Вся защита от «стены» завязана на «карточек = 0»: `decideNotifResize` прячет только при `h<=0` или `rendererPure`; сторож гасит только `isVisible && getNotifItems().length===0`. Если renderer перестал слать размер, а счётчик main остался >0 — НИ проверка размера, НИ сторож не срабатывают → окно висит на старых bounds, пустая часть ловит клики.

**Фикс (heartbeat + запись).** (1) Сторож (`setInterval` 5с): пока окно НА ЭКРАНЕ, шлёт `notif:remeasure` → renderer вызывает `reportHeight()` → авторитетный отчёт через ту же `decideNotifResize` (живой renderer поправит размер или скроется даже при счётчике>0; для реальных карточек no-op). (2) Запись `[notif-watchdog] alive items=… bounds=… msSinceResize=… onTop=…`. Каналы: `notification.preload.cjs` `onRemeasure`, `notification.js` `onRemeasure?.(reportHeight)`.

**Крайние случаи.** Скрытое/офскрин окно — heartbeat не шлётся. Реальные карточки — тот же размер, окно не дёргается.

**Проверка:** `node --check` OK; лимиты 515/515; `mainRuntime` 98/98; линт 0. Ловушка — [[notifications-ribbon]].
