## 📐 Раскладка главного окна: кто уступает место (v1.2.454)

**Порядок блоков в главном ряду** ([App.jsx](../src/App.jsx)):

```
[ боковая полоса ][      СЕРЕДИНА      ][|][   панель ИИ   ]
   shrink-0          flex-1 + min-w-0   6px  shrink-0 + width из настроек
   (не сжимается)    (уступает место)        (не сжимается)
```

**🔴 ПРАВИЛО (нарушение = панель уезжает за край окна, МОЛЧА)**
Любой тянущийся блок (`flex-1` / `flex: 1`), у которого есть несжимаемый сосед, ОБЯЗАН иметь `min-width: 0`
(`min-w-0` в классах, `minWidth: 0` в стилях). Причина: у флекс-элемента `min-width` по умолчанию `auto`,
то есть он не сжимается ниже минимальной ширины своего содержимого. А так как ряд помечен `overflow-hidden`,
лишнее не даёт прокрутки — оно просто уходит за край окна без ошибки и без записи в журнале.

Приём в проекте принят давно (~20 мест: `ChatListItem`, `AccountContextMenu` и др.). Три места, где его
не хватало, и были причиной жалобы «окно чата уехало за границы»: середина в `App.jsx` и два уровня
в `InboxMode.jsx` (ряд «список чатов + переписка» и область переписки).

**Метки `data-cc-layout`** (`row` / `middle` / `ai-panel` / `inbox-row` / `messages`) — не оформление.
По ним измеритель находит блоки; их удаление ослепляет проверку. Сторожит [layoutShrinkGuard.test.cjs](../src/__tests__/layoutShrinkGuard.test.cjs).

**Как посмотреть раскладку, не гадая**: в журнале строка со словом `layout` (через 12 с после старта) —
размеры каждого блока и пометка «НЕ ВЛЕЗАЕТ по ширине на N». Вручную в любой момент: `__ccLayoutProbe('проверка')`.

**v1.2.455-456 — ПОТОЛОК ПАНЕЛИ ИИ**: её ширина не просто «сохранённое число», а «не больше
половины окна». Источник один — [shared/panelWidthCap.js](../shared/panelWidthCap.js); ширина
задаётся постоянным числом, а потолок ОТДЕЛЬНЫМ правилом `max-width` (почему именно так — ловушка 2
в [mistakes/app-layout.md](mistakes/app-layout.md)). Внутренний слой панели держит вид `min(...)`,
потому что у него есть минимум ширины. Сторожат [AISidebar.vitest.jsx](../src/components/AISidebar.vitest.jsx)
и [panelWidthCap.vitest.js](../src/__tests__/panelWidthCap.vitest.js).

**v1.2.457 — ШИРИНА СПИСКА ЧАТОВ** ограничена 40 % окна, но ограничено САМО ЧИСЛО, а не вёрстка:
«узкий вид» списка включается по этому же числу (`chatListMaxPx` в
[useChatListResize.js](../src/native/hooks/useChatListResize.js), остаток — TODO-40 в [code-todo.md](code-todo.md)).

**v1.2.457 — «ПИНОК РАСКЛАДКИ»** при открытии веб-вкладки (ширина на миг меньше на 1 точку, чтобы
расклеить адаптивный сайт) делается ТОЛЬКО при первом открытии каждой вкладки — иначе картинка
дёргалась на каждом переключении. Отметка — на самом элементе (`wrap.__ccRelayoutKicked`).

🔴 **ЛОВУШКИ этого раздела вынесены отдельно**: [mistakes/app-layout.md](mistakes/app-layout.md)
(5 штук: тянущийся блок не сжимается; потолок в анимируемом свойстве; приём, меняющий геометрию, на
каждом показе; «немой страж»; почему нельзя слушателем размера окна). Читай их ПЕРЕД правкой раскладки.

Решения целиком — ADR-054, ADR-055 (с уточнением v1.2.456) и ADR-056 в [decisions.md](decisions.md).

## Компонент: Вкладка мессенджера (MessengerTab)

Размеры: `h-[40px] px-3` — бейдж и крестик в flex-потоке (`ml-auto shrink-0`), вкладка расширяется автоматически (v0.19.6)

### Состояния вкладки

**Активная вкладка:**
- `backgroundColor: ${color}1A` — 10% прозрачность бренд-цвета
- `borderBottom: 2px solid ${color}` — нижняя линия бренд-цвета
- `borderRadius: 6px 6px 0 0`
- Индикатор-точка: `backgroundColor: ${color}` — полный цвет
- Название: `color: ${color}` — бренд-цвет

**Неактивная вкладка:**
- Фон: `transparent`
- `borderBottom: 2px solid transparent`
- Hover: `backgroundColor: rgba(255,255,255,0.06)`
- Индикатор-точка: `backgroundColor: ${color}55` — 33% прозрачность
- Название: `color: rgba(255,255,255,0.45)` — приглушённый белый

### Структура вкладки (JSX)

```jsx
<button style={{ backgroundColor, borderBottom, borderRadius }}>
  {/* Цветная точка-индикатор */}
  <span style={{ backgroundColor: isActive ? color : `${color}55` }} />

  {/* Название + зум + аккаунт (центрировано) */}

      {name}
    </span>
    {accountInfo && (
      <span className="text-[10px] max-w-[110px] overflow-hidden text-ellipsis"
            style={{ color: isActive ? `${color}AA` : 'rgba(255,255,255,0.25)' }}>
        {accountInfo}
      </span>
    )}
  </span>
</button>
```

## Извлечение информации об аккаунте

Реализовано в `src/App.jsx` через `webview.executeJavaScript()`.

**Алгоритм:**
1. WebView вешает слушатель `dom-ready`
2. После `dom-ready` ждём **4 секунды** (страница продолжает загружаться асинхронно)
3. Выполняем `executeJavaScript(accountScript)` — обходим список CSS-селекторов
4. Если результат не найден — повтор через 4 сек., максимум 10 попыток (~40 сек.)
5. Длинные строки (>100 символов) игнорируются (защита от мусора)

**Скрипты по мессенджерам (`accountScript`):**

| Мессенджер | Пробуемые селекторы |
|-----------|---------------------|
| Telegram | **IndexedDB cursor (v0.19.2)**: без DOM! Cursor по `users` store → `pFlags.self === true` → `first_name + last_name` / `+phone` fallback |
| WhatsApp | `[data-testid="profile-details-header-name"]`, `[data-testid="user-preferred-name"]` |
| ВКонтакте | `.TopNavBtn__title`, `.header__top--uname`, `.vkuiSimpleCell__content .vkuiTypography--weight-1` |

⚠️ **Важно**: Селекторы могут устареть при обновлении мессенджеров. Нужно периодически проверять.
⚠️ **Telegram**: НЕ использовать DOM-селекторы для имени аккаунта — все они возвращают имя открытого чата. Использовать только IndexedDB-подход (v0.19.0).

## Компонент: SystemDiagnosticsModal (v1.2.31)

Открывается из настроек кнопкой `🩺 Диагностика системы` в существующем блоке **Диагностика**. Старые кнопки `Загрузить лог ошибок` / `Очистить` остаются для `userData/ai-errors.log` и не смешиваются с общей диагностикой.

Обновление 22 июня 2026: модалка должна оставаться поверх настроек и других overlay даже после Alt-Tab/возврата в приложение. Для этого у overlay высокий `zIndex: 1000001`. Кнопки внутри модалки используют общий `ActionButton`: есть hover, нажатое состояние, focus-состояние с клавиатуры, `disabled` и стабильная ширина для `Обновить/Проверка...`, чтобы интерфейс не прыгал. Переключатели используют текст `вкл/выкл`, а не символы, потому что состояние должно быть понятно без догадок.

Важно для будущих правок: `load()` намеренно читает `runtimeContext`, флаг глубокой проверки и callback глубокой проверки через `useRef`. Не возвращать эти значения в dependency list `useCallback`, иначе при новом объекте `runtimeContext` от родителя окно начнёт повторно загружаться/дёргаться на каждый рендер.

Что показывает:
- сводку по ошибкам, предупреждениям, цепочкам событий и количеству мессенджеров;
- список подозрительных проблем по текущему снимку;
- цепочки notification/WebView/native из `chatcenter.log`;
- путь к файлу `userData/system-diagnostics-report.json` для Codex/другого ИИ;
- последние ошибки из общего системного лога.

Управление:
- `Включить запись` — запускает фоновую запись вручную;
- `Пауза` / `Продолжить` — временно останавливает или возобновляет запись;
- `Отключить и сохранить` — останавливает запись и сохраняет отчёт;
- `Свернуть в фон` — закрывает большую модалку, маленькая панель остаётся и запись продолжается;
- `Сохранить для ИИ` / `Скопировать для ИИ` — сохраняет или копирует текущую сессию/отчёт;
- `Очистить экран` — очищает только буфер модалки, не удаляет `chatcenter.log` и не чистит `ai-errors.log`;
- глубокая WebView-проверка включена всегда, отдельного переключателя нет.

Правило закрытия (v1.2.31): кнопка `Закрыть` в маленькой панели сначала сохраняет активную или накопленную сессию в `userData/system-diagnostics-report.json`, и только потом сбрасывает экранный буфер. Большая модалка при открытии читает последний сохранённый отчёт через `app:diagnostics-read-report`; если текущая запись пустая, live-лента показывает события из сохранённого файла. Поэтому после закрытия панели пользователь не должен видеть "пустой отчёт", если до закрытия события были записаны.

Файл отчёта нужен для удалённого разбора: пользователь запускает диагностику, а ИИ читает `system-diagnostics-report.json` и видит факты без скриншотов и ручного пересказа.

### Цветовая индикация качества подключения (v0.87.136)

Точка-индикатор на вкладке и на аватарке native/API аккаунта отражает только качество подключения, а не внутренний статус monitor.preload:

- ⚪ Серая `#9ca3af` — ожидание первой проверки (`connectionHealth.state = 'pending'`)
- 🟢 Зелёная `#22c55e` — последнее подключение/ответ прошли нормально (`connectionHealth.state = 'ok'`)
- 🟡 Жёлтая `#eab308` — подключение есть, но ответ долгий (`connectionHealth.state = 'slow'`)
- 🔴 Красная `#ef4444` — загрузка/ответ завершились ошибкой (`connectionHealth.state = 'error'`)

Клик по любой такой точке открывает общий экран `Подключения`. Hover показывает краткую диагностику: последний ответ, время проверки, URL/ошибку при наличии.

Экран `Подключения` не показывает отдельный общий статус сверху: у каждого подключения свой статус в списке и в правой панели деталей. В списке у каждой строки показываются: название, статус, цветное время последнего ответа и время последней проверки.

### Принцип проверки подключений

Проверка не идёт постоянным фоновым опросом каждую секунду. Статус обновляется по реальным событиям:

**WebView вкладки:**

- вкладка начала загрузку (`did-start-loading`) → `Ожидание проверки`;
- страница дошла до `dom-ready` / `did-finish-load` / `did-stop-loading` → запускается лёгкий probe внутри WebView;
- probe делает короткий `network-fetch` внутри текущей WebView-вкладки и возвращает `probeMs`;
- порядок WebView probe: текущий URL страницы без hash → `/favicon.ico` → `/`;
- успешный probe → `Работает` или `Медленно отвечает` по времени сетевого ответа вкладки;
- загрузка/проверка дольше 10 секунд → `Медленно отвечает`;
- `did-fail-load`, crash WebView, ошибка загрузки → `Не отвечает / ошибка`;
- полезный `__CC_*` ответ от страницы подтверждает живость, но не подменяет время последнего network probe.

Для native/API аккаунтов время ответа берётся из реальных IPC/API операций:

- `tg:get-chats`
- `tg:rescan-unread`

`tg:get-cached-chats` не является сетевой проверкой, потому что читает локальный кэш. Общий замер операции по всем аккаунтам нельзя показывать как личное время каждого аккаунта: `tg:rescan-unread` должен отдавать per-account статистику.

`Not connected` и другие ошибки Telegram API отображаются пользователю как красный статус `Не отвечает / ошибка`.

**Кнопки:**

- `Проверить все` — запускает WebView probe без reload вкладок и проверку native/API;
- `Обновить проблемные` — перепроверяет только `Медленно отвечает` и `Не отвечает / ошибка`;
- `Открыть лог` — открывает системный лог для ручной диагностики.

Внутренние monitor.preload/hooks/`__CC_*` остаются рабочим механизмом уведомлений и unread, но их `monitorStatus` больше не является UI-смыслом точки.

## Логотипы мессенджеров: MessengerIcon + реестр data-URI (v1.2.182 → v1.2.316)

- Логотипы хранятся строкой (data-URI base64) в `src/native/utils/messengerLogos.js` — реестр `MESSENGER_LOGOS`, ключ = ТИП мессенджера (`telegram`/`whatsapp`/`vk`/`max`). Приём выбран в ADR-027 (архив `decisions-adr-023-027.md`): НЕ импорт-ассет сборщика — иначе ломается в упакованном приложении. CSP `index.html` разрешает `img-src … data:`.
- Компонент `MessengerIcon` (`{messenger, size}`) рисует `<img>`, если `getMessengerLogo(messenger)` вернул data-URI; иначе эмодзи из `getMessengerEmoji` (`messengerBranding.js`). Битая картинка → `onError` тихо переключает на эмодзи (никогда не показываем «поломашку»). Логи не нужны — синхронный рендер без сети.
- **Добавить логотип нового мессенджера = 3 шага**: (1) ключ в `MESSENGER_LOGOS` (base64 из PNG, проверь round-trip); (2) ветка в `RailWebIcon.jsx` → `logoType`; (3) тест в `MessengerIcon.vitest.jsx`. Плюс поднять бюджет строк renderer в `fileSizeLimits.test.cjs` (каждый логотип = 1 длинная строка + комментарий ≈ +2-3 строки).
- Где виден: боковой рейл (`RailWebIcon`), окно «Добавить» (`AddSourceModal` → `MessengerIcon messenger={m.id}`, id из `DEFAULT_MESSENGERS`), угловой значок у `AccountAvatar`. Нативный список чатов/шапка — только Telegram (веб-мессенджеры в WebView, там не появляются).
- Реализовано: Telegram (v1.2.183), WhatsApp (v1.2.314), ВКонтакте (v1.2.315), МАКС (v1.2.316).

### 🪤 Грабля: определение типа по имени у веб-значка (RailWebIcon)

`RailWebIcon` не может доверять только `m.id`: у веб-аккаунта, добавленного вручную, id = `custom_<число>`, а не `vk`/`max`. Поэтому тип берётся как `m.id === 'vk' || <маска по имени>`. Два подводных камня:
1. **Имя кириллицей**: дефолтные веб-имена — «ВКонтакте», «Макс» (`constants.js`). Латинская маска `/vk/`, `/max/` их НЕ ловит → нужна кириллическая `/вконтакте/i`, `/макс/i`.
2. **Короткая латинская подстрока → ЛОЖНОЕ срабатывание** (🟡 было в v1.2.315-316, **исправлено в v1.2.317**): маски `/vk|вконтакте/i`, `/max|макс/i` искали ПОДСТРОКУ → кастомная вкладка «Vkusvill», «MaxBet», «Climax» получала логотип ВК/МАКС. Фикс: латинские `vk`/`max` убраны из масок — дефолтные ловятся по `m.id`, кастомные по кириллическому имени `/вконтакте/i`, `/макс/i` (длинное слово, коллизий нет). Урок: **не используй короткий латинский маркер (2-3 буквы) в маске-подстроке** — бери либо точный id, либо длинное/кириллическое имя, либо якоря `^…$`. Тест-ловушки в `RailWebIcon.vitest.jsx` («Vkusvill»/«MaxBet» → НЕ логотип).

## Правила UI

1. Использовать **Tailwind CSS** для статичных классов, **inline styles** только для динамических цветов
2. Избегать хардкода цветов в Tailwind (невозможно использовать `bg-[${dynamicColor}]` в runtime)
3. Hover-эффекты на кнопках — через `onMouseEnter`/`onMouseLeave` для inline-стилей ИЛИ Tailwind `hover:` для статичных
4. Scroll-контейнеры должны быть явно ограничены `overflow-hidden` / `overflow-x-auto`
5. Текст в шапке: `select-none` — нельзя выделять
6. Кнопки в drag-зоне: обязательно `style={{ WebkitAppRegion: 'no-drag' }}`
