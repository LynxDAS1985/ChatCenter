**Как пользоваться при новой жалобе** (порядок отработан на разборах 2026-09-15):
1. Спросить время и мессенджер → открыть `%APPDATA%/ЦентрЧатов/chatcenter.log`.

## 1. Общая схема: как рождается уведомление

Два принципиально разных мира:

```
РОДНОЙ Telegram (через TDLib, вкладка «Общий чат»)
  TDLib → разбор сообщения (tdlibMapper.js) → состояние приложения
        → nativeStoreIpc.js решает «показывать ли» → app:custom-notify → окно

ВЕБ-МЕССЕНДЖЕРЫ (Telegram Web, МАКС, ВК, WhatsApp, Ozon — каждый в своём <webview>)
  страница мессенджера
    ├─ хук мессенджера (max.hook.js / vk.hook.js / …) → console.log('__CC_NOTIF__…')
    ├─ общий наблюдатель «QUICK» (monitor.preload.cjs) → ipc 'new-message'
    └─ запасной наблюдатель (monitor.preload.cjs) → console.log('__CC_MSG__…')
         ↓ всё сходится в ОДНОМ узле
    webviewHandleNewMessage.js (мьют → повторы → спам → звук) → app:custom-notify → окно
```

🔴 **ГЛАВНОЕ, ЧТО НАДО ПОНИМАТЬ**: у одного веб-мессенджера может быть **до трёх независимых
«доносчиков»**, и они НЕ знают друг о друге. Каждый сам решает, что «пришло новое сообщение».
Именно отсюда берутся дубли.

### Защита от повторов — где она и как устроена

Живёт в `src/utils/webviewHandleNewMessage.js`, сами правила — в `src/utils/messageProcessing.js`:

| Правило | Что делает | Окно времени |
|---|---|---|
| `isDuplicateExact` | точно такой же текст уже был | 10 секунд |
| `isDuplicateSubstring` | один текст является КУСКОМ другого (в любую сторону) | 5 секунд |
| `isOwnMessage` | это наше собственное отправленное | — |

🔴 **КЛЮЧЕВОЕ ОГРАНИЧЕНИЕ**: ключ сравнения складывается из **имени отправителя** и текста
(`buildMessageDedupScope`). Если два пути назвали отправителя ПО-РАЗНОМУ — сравнение вообще
не состоится, и оба уведомления пройдут. Это не теория: см. случай МАКС от 2026-09-15 ниже.

✅ **v1.2.462 — защита теперь пишет и про ПРОПУСК.** Раньше строка появлялась, ТОЛЬКО когда повтор
пойман. Теперь на каждое пропущенное сообщение пишется:
`ПРОПУЩЕНО | scope=<ключ сравнения> key="<ключ целиком>" вМоменте=<сколько записей в памяти>`.
Именно по этой строке и надо разбирать «почему пришло несколько карточек»: если у двух карточек
`scope` РАЗНЫЙ — значит пути назвали отправителя по-разному, и сравнение не могло состояться.

✅ **v1.2.462 — имя отправителя чистится сильнее.** `cleanSenderStatus` теперь дополнительно
схлопывает подряд идущие пробелы, срезает подпись времени в конце («Только что», «1 мин назад»,
«вчера», «12:30») и схлопывает ТОЧНЫЙ повтор имени целиком. Это закрыло задвоение имени у МАКС.

## 2. Метки в журнале (что грепать)

> ⭐ **С v1.2.462 первым делом грепай `ПРОПУЩЕНО`** — это строка защиты от повторов о каждом
> пропущенном сообщении (ключ сравнения виден целиком). До v1.2.462 таких строк в журнале нет.

| Метка | Где рождается | Что означает |
|---|---|---|
| `[NotifManager] show` | `main/handlers/mainIpcHandlers.js` | **карточка реально показана**. Считать их — самый быстрый способ понять, сколько дублей |
| `[notif-ipc] custom-notify recv` | `main/handlers/mainIpcHandlers.js` | запрос на показ дошёл до главного процесса; видно `sender=`, `bodyLen=` |
| `[native-notif] emit` | `src/native/store/nativeStoreIpc.js` | РОДНОЙ Telegram решил показать; `bodyLen=0` = тело пустое |
| `[native-notif] skip muted` / `skip backlog` | там же | сознательно НЕ показали (заглушённый чат / старьё при старте) |
| `[tdlib-empty]` | `main/native/backends/tdlibMapperMedia.js` | вид сообщения не разобран → пустой пузырь (добавлено v1.2.461) |
| `[TRACE] … Источник:` / `Обработка:` / `Ribbon:` | `src/utils/…` трассировка | путь одного уведомления по шагам; в `Источник` виден `src=` |
| `[TRACE] … dedup … block` | `webviewHandleNewMessage.js` | повтор ПОЙМАН. **Ноль таких строк при видимых дублях = защита не сработала** |
| `[MAX-QUICK]` | `main/preloads/monitor.preload.cjs` | общий быстрый наблюдатель (подробности включены для МАКС) |
| `[MAX-SNAPSHOT]` | `main/preloads/utils/maxDiagnostics.js` | снимок страницы МАКС: размеры, строки списка, заголовок |
| `[notif-resize]`, `[notif-watchdog]` | `main/handlers/notifHandlers.js` | размер/скрытие окна уведомлений, сторож «невидимой стены» |
| `__CC_DIAG__*` | хуки мессенджеров | временная диагностика внутри чужой страницы |

### 3.1 Telegram — РОДНОЙ (TDLib, «Общий чат»)

**Доносчик один**: `src/native/store/nativeStoreIpc.js` по событию нового сообщения от TDLib.
Дублей по устройству быть не должно — путь единственный.

**Что берётся в текст**: `message.text`, а если его нет — подпись по виду вложения
(`🖼 Фото`, `📹 Видео`, `📎 вложение` и т.п.). Если пусто и то и другое → **`[медиа]`**.

✅ **v1.2.465 — для известных «нечего показывать» видов подпись теперь честная.**
Запись `[tdlib-empty]` из v1.2.461 сработала: журнал 2026-09-16 08:30:51 назвал вид —
**`messageUnsupported`**. По официальной документации TDLib это «содержимое сообщения, не
поддерживаемое текущей версией библиотеки», то есть показать его НЕВОЗМОЖНО. Теперь в разборе
([tdlibMapperMedia.js](../main/native/backends/tdlibMapperMedia.js), `emptyMessageFallbackText`)
подставляется текст «⚠️ Сообщение не поддерживается этой версией программы» — и он приходит сразу
во все три места (уведомление, список чатов, пузырь). ⚠️ Важно: уведомление и пузырь берут текст из
разбора `mapMessage`, а список чатов — из ОТДЕЛЬНОЙ функции `messagePreview`, поэтому её пришлось
научить спрашивать тот же словарь отдельно (v1.2.466; изначально забыли, и список чатов показывал
«⚙️ служебное сообщение» — поймано придирчивым ревью).
Словарь умышленно короткий: незнакомый вид подписи НЕ получает, `[медиа]` для него остаётся.

**Известные беды**:

### 2026-09-15 — МАКС: СВОИ отправленные сообщения приходят как уведомления 🔴 открыто

- **Что видел пользователь** (скриншот): карточка уведомления «Цывилько Дмитрий Николаевич Ц… /
  Макс / 18:20 / смотрю». Слово «смотрю» — это ЕГО СОБСТВЕННОЕ только что отправленное сообщение
  (в самом МАКС оно справа, фиолетовым).
- **Что в журнале** (`chatcenter.log`, 18:20:23–24), восстановлена вся секунда:

  | Время | Что произошло |
  |---|---|
  | 18:20:23 | быстрый наблюдатель увидел новый кусок страницы: `[MAX-QUICK] send new-message text="смотрю"` |
  | 18:20:23 | рядом же: `[MAX-OUT-DIAG] text="смотрю" … ticks=2 bubbleL=848 rowL=471 rowW=524` — **программа измерила, что сообщение исходящее, и просто записала это** |
  | 18:20:23 | путь №1 (запасной, через 500 мс) → `✗ Видимость: MAX: вкладка открыта — фантом подавлен` — **заблокирован** |
  | 18:20:24 | путь №2 (`__CC_MSG__`, через 1200 мс) → `✓ Видимость: focused=false` → звук → **карточка id=39 показана** |

- **Ключевая улика про фокус**: в 18:20:23 во всех строках `focused=true`, в 18:20:24 — `focused=false`.
  Человек отправил сообщение и перешёл в другое окно. Путь №1 успел до перехода и был отсечён,
  путь №2 пришёл после — и правило «ты же смотришь на вкладку» больше не сработало.
- **КОРЕНЬ (🟢, открыл и прочитал код)**: `maxOutgoingReport` ([maxDiagnostics.js](../main/preloads/utils/maxDiagnostics.js))
  возвращает СТРОКУ для журнала. Поиск по всему `main/` и `src/` даёт ровно два упоминания — объявление
  и одна подстановка внутрь диагностической строки в [monitor.preload.cjs](../main/preloads/monitor.preload.cjs).
  **Ни одна строка кода не принимает по этому измерению решение.** Проверки «это моё исходящее» у МАКС нет вообще.
- **Почему не помогли соседние защиты** (проверено чтением):
  - `isOwnMessage` ([messageProcessing.js](../src/utils/messageProcessing.js)) — это правило ВК
    («текст сам похож на Имя Фамилия»). Для слова «смотрю» оно не срабатывает и срабатывать не должно.
  - единственный фильтр исходящих во всех хуках — `/^(вы:\s|you:\s)/i`. Он ловит подпись «Вы: …»,
    которую мессенджер ставит в СПИСКЕ ЧАТОВ. В окне переписки текст идёт голым — фильтру не за что зацепиться.
  - у ВК настоящая проверка ЕСТЬ (`emitBlockedBy = 'outgoing-own-message'`,
    [vkDiagnostics.js](../main/preloads/utils/vkDiagnostics.js)). МАКС — исключение.
- **Насколько часто** (посчитано по журналу за 2026-09-15): быстрый наблюдатель поймал в окне переписки
  **4 своих исходящих**; **2 стали уведомлениями** («Понял, отлично» → карточка id=12, «смотрю» → id=39),
  **2 были подавлены случайно** («3 340 получено», «Нет, он придёт завтра» — фокус в тот момент не терялся).
  То есть примерно каждое второе своё сообщение уходит в уведомление.
- **Данные для будущей проверки** (из тех же строк `[MAX-OUT-DIAG]`, строка чата = `rowCls=item.svelte-rg2upy`,
  `rowL=471 rowW=524`):

  | Что | Входящее | Исходящее |
  |---|---|---|
  | левый край пузыря `bubbleL` | **всегда 487** (= край строки + 16) | 634 / 724 / 791 / 848 |
  | `ticks` (значки в строке) | 1 у текста, **2 у файла** | 2 |

  🔴 **Ловушка**: по `ticks` различать НЕЛЬЗЯ — у входящего файла («Новые сообщения … PDF check.pdf»)
  тоже `ticks=2`. Надёжен только отступ пузыря от левого края строки.
  ⚠️ **Чего не хватает, чтобы сделать проверку безопасно**: правый край пузыря. У очень длинного
  исходящего сообщения пузырь занимает почти всю ширину и начинается тоже близко к левому краю —
  на таком случае правило «отступ больше 16» может не сработать. Строки `[MAX-OUT-DIAG]` правый край
  не записывают. Это одно число, и оно добавляется в уже работающую запись.
- **ЧТО СДЕЛАНО В v1.2.463 (в тот же день)**: измерение превращено в решение. Правило — чистая
  `maxOutgoingDecision(координаты)`: сравниваем отступ пузыря СЛЕВА и СПРАВА, «своё» ставим только при
  перевесе больше 40 точек. Вердикт спрашивается ДО попадания текста в список на отправку, своё
  прерывает обработку. Правый край пузыря теперь измеряется прямо в коде (`bubbleR` в записи журнала) —
  отдельный день сбора данных не понадобился.
- 🔴 **ОСОЗНАННАЯ ОДНОСТОРОННЯЯ ОШИБКА**: пузырь во всю ширину строки (очень длинное своё сообщение) и
