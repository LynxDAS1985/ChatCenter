## 🔴 `git checkout -- <файл>` уничтожает незакоммиченную работу; а тест «внутренностей» модуля не доказывает, что модуль ПОДКЛЮЧЁН (v1.2.446, 2026-09-10)

**Как получилось**: файл `src/utils/webviewSetup.js` стоял на своём потолке строк, я не смог добавить в него две строки и вернул файл в исходное состояние командой `git checkout -- src/utils/webviewSetup.js`. В этом проекте десятки файлов месяцами живут без коммита (последний коммит был на 18 версий позади), поэтому «исходное состояние» = состояние 18 версий назад. Две сделанные ранее правки (v1.2.434 и v1.2.435) исчезли, и вместе с ними — защита от чёрного экрана веб-МАКС.

**Почему это не поймали ни линт, ни 2606 тестов**: вынесенный модуль `shared/browserBannerHider.js` остался на диске, его 16 тестов были зелёными. Но ВЫЗОВ из приложения пропал. Все проверки смотрели внутрь модуля; ни одна не проверяла проводку. Признак «осиротевшего» модуля: на него ссылаются только тесты и комментарии.

**Правила из этого случая**
1. Отменять свою правку — только тем же способом, каким её делал (правкой вперёд), НИКОГДА через `git checkout` по файлу. Если очень нужно — сначала `git diff <файл>` и убедиться, что там только СВОИ строки.
2. Каждый вынесенный в отдельный файл модуль обязан иметь тест ПРОВОДКИ: «вызывающий файл действительно его импортирует и зовёт» + «старое опасное поведение не вернулось». Проверка внутренностей модуля без этого — иллюзия.
3. Быстрый способ найти такие потери: пройти все файлы `shared/*.js` и посмотреть, есть ли на каждый живой вызов из `src/`/`main/` (без тестов). Ноль вызовов = потерянная проводка.

**Где закреплено**: `src/__tests__/browserBannerHider.vitest.js` — блок «Проводка: приложение действительно зовёт безопасный прятальщик» (3 проверки).

## 🔴 Слои мессенджеров БЕЗ своего фона просвечивают: пустой слой показывает нижний (выглядит как «вместо WhatsApp данные Telegram») (v1.2.445, 2026-09-10)

**Симптом**: пользователь переключается на WhatsApp и видит чаты Telegram. Похоже на подмену данных или перепутанные вкладки — но это не так.

**Причина**: в `App.jsx` все мессенджеры лежат ОДИН НА ДРУГОМ и переключаются только слоем: `zIndex: activeId === m.id ? 2 : 0`. Своего фона у слоя нет. Если страница верхнего слоя пустая (не загрузилась после обрыва связи, упала, ещё не отрисовалась) — сквозь неё видно нижний слой, а нижний в проекте это нативный «Общий чат» с чатами Telegram.

**Как отличить от настоящей подмены**: в журнале НЕТ ни строки о смене адреса или аккаунта, зато есть `did-fail-load`. И «чужое» видно ровно там, где верхняя страница пуста, а не целиком.

**Правило**: любой экран-заглушка на месте упавшей страницы ОБЯЗАН иметь непрозрачный фон (плотный цвет, не полупрозрачный) и `position:absolute; inset:0` внутри слоя. Полупрозрачная «шторка» тут не годится — она как раз и оставляет просвет.

**И отдельно**: саму страницу при этом прятать (`display:none`, нулевой размер) НЕЛЬЗЯ — скрытую страницу движок усыпляет, она не догрузится и не пришлёт событие «загрузилась». Экран рисуем ПОВЕРХ живой страницы.

**Где закреплено**: `src/components/WebviewOfflineOverlay.jsx` + тест `useWebviewReconnect.vitest.jsx` (проверка, что фон непрозрачный). Решение — [[decisions]] ADR-047, план — `.memory-bank/reconnect-plan.md`.

## 🔴 Удалил код — ищи ТЕСТЫ, которые его цитируют (иначе ломается обязательная цепочка) (v1.2.444, 2026-09-10)

**Симптом**: правка выглядит завершённой, «свои» тесты зелёные, но `npm test` падает и отправить код нельзя.

**Что было**: в v1.2.443 из `main/utils/overlayIcon.js` убран простой синий круг (значок трея) и заменён настоящим знаком. А в `src/__tests__/overlayIcon.test.cjs` стояла проверка `code.includes('42, 171, 238')` — она сторожила ИМЕННО цвет этого круга. Результат: `36 ✅ / 1 ❌`, и `overlayIcon` есть в списке хука `scripts/hooks/pre-push` → push заблокирован.

**Почему пропустил**: прогнал 14 тестов «по смыслу задачи» из 34 в цепочке — и не тот единственный, который относился к изменённому файлу.

**Правило**:
1. Удаляя/меняя строку с числом, цветом, именем или текстом — сделать `grep` этой строки по `src/__tests__/` ПЕРЕД правкой. Тесты проекта в основном «сторожа по тексту» (читают файл и ищут подстроку), поэтому ловятся именно так.
2. Перед сдачей гонять ВСЮ цепочку из `scripts/hooks/pre-push`, а не выборку: `for t in $(…список…); do node src/__tests__/$t.test.cjs; done`. Один прогон — 3 минуты.
3. Упавшую проверку не удалять, а ПЕРЕНАСТРАИВАТЬ на то, что теперь важно (у нас: 1 проверка про цвет круга → 3 проверки про единый источник знака, порядок цветов и запасной путь).

## 🟡 Сборщик установщика УМЕНЬШАЕТ большую картинку: мелкий значок становится пятном (v1.2.444, 2026-09-10)

**Симптом**: иконка приложения красивая, а в панели задач — серое пятно.

**Причина**: electron-builder делает файл иконки Windows (`.ico`) уменьшением ОДНОЙ большой картинки. Замер: 512→16 оставляет 1 белую точку вместо 41. Отдельно нарисованные мелкие картинки он не берёт — даже если положить их рядом (`collectIconsFromDir` выбирает самую большую и снова уменьшает).

**Правило**: если у знака тонкие линии — собирать `.ico` самим, кладя внутрь картинку под КАЖДЫЙ размер. Готовый `.ico` electron-builder не перекодирует (его код, `iconConverter.js:190-203`: «If source already has the target extension … return it directly»), только требует размер ≥ 256.

**Как проверить, не собирая установщик**: разобрать `.ico` тем же порядком, что и он (`getIcoMaxSize`), и сверить вложенные картинки побайтово с нарисованными — это и делает тест `appIconMark.vitest.js`.

**Родня**: [[decisions]] ADR-046 (отменяет пункт ADR-045 «`.ico` не собираем сами») и грабля выше про мелкие размеры.

## 🟡 Иконку нельзя «просто уменьшить»: на 16 px знак превращается в пятно (v1.2.443, 2026-09-10)

**Симптом**: знак, красивый на 256 px, на 16 px (панель задач, трей) — серо-белое пятно: контур слился, полосы слиплись, хвостик исчез.

**Причина**: два числа, которые для крупного размера правильные, для мелкого — губительны. (1) Отступ знака внутри плитки 14% с каждой стороны: на 16 px самому знаку остаётся ~11 px. (2) Толщина линии 7 (в клетке 64) при уменьшении в 4 раза даёт ~1.7 px — с учётом сглаживания это полупрозрачная нитка.

**Как ловить, не запуская приложение**: увеличить каждый пиксель в 8–14 раз БЕЗ сглаживания (простое копирование точек) и посмотреть глазами — видно каждый настоящий пиксель. Так и был найден дефект.

**Правило**: у иконки под каждый диапазон размеров свои числа. В `shared/appIconMark.js`: ≤24 px — линия 9.5 и отступ 5%; ≤48 px — линия 7.5; крупные — 4.5. Тест-ловушка не «смотрит», а СЧИТАЕТ пиксели по цветам и падает, если на 16 px не видно и белого пузыря, и лазурных полос (`appIconMark.vitest.js`).

**Родня**: то же правило проговаривалось в макетах плит 01–03 («что проходит 16 px, а что нет») — там половина вариантов отпала именно по этой причине.

## 🟡 Градиентный текст делает ПРОЗРАЧНЫМ вложенный рисунок (v1.2.443, 2026-09-10)

**Симптом (поймано до отправки, но легко наступить)**: вставляешь картинку/`<svg>` внутрь красивой градиентной надписи — картинка исчезает.

**Причина**: приём «градиент вместо цвета текста» = `background: linear-gradient(...)` + `background-clip: text` + **`color: transparent`**. Если он висит на ОБЩЕМ блоке (а не на самой надписи), то `color: transparent` наследуется внутрь, а фон-градиент обрезается по буквам — вложенный `<svg>`, который рисуется `currentColor` или наследует цвет, становится невидимым.

**Правило**: градиент текста держать на элементе САМОЙ надписи (`<span>`), а не на контейнере, куда потом что-то вкладывают. Блок-контейнер делать обычным (`display:flex`) без цветовых свойств.

**Где было**: `.native-chatload-brand` (шапка заставки загрузки чатов) — градиент перенесён на новый `.native-chatload-brandtext`. Тест-ловушка проверяет, что на общем блоке `color: transparent` больше нет.

## 🟡 Переносишь файл — у пользователя падает окно: «Failed to fetch dynamically imported module» (v1.2.442, 2026-09-09)

**Симптом**: пользователь работает в запущенном из терминала приложении, и на экране появляется красное «⚠️ Ошибка рендера: Failed to fetch dynamically imported module: http://localhost:5173/src/components/WhatsNewModal.jsx».

**Причина**: файл `src/utils/changelogData.js` переносился в `shared/` в тот момент, когда приложение РАБОТАЛО, и как раз открылась модалка «Что нового» (версия сменилась). Dev-сервер отдаёт модули по запросу — он попытался собрать окно, чей импорт в этот миг указывал на уже уехавший файл. Код при этом был верным: путь `../../shared/changelogData.js` из `src/components/` разрешается, корень dev-сервера `.` (см. `electron.vite.config.js`), а `shared/` отдаётся — этим же путём давно живут `shared/accountFilter.js` и другие.

**Как отличить от настоящей поломки** (по шагам, до правок кода):
1. `ls` целевого файла — он существует?
2. `node -e "…path.resolve…"` от папки файла-импортёра — путь разрешается?
3. корень dev-сервера в `electron.vite.config.js` покрывает новую папку?
Все три «да» → это временный след переноса, лечится перезагрузкой окна (Ctrl+R), правок не требует.

**Правило**: перенос/переименование файлов в работающем dev-приложении даёт разовые ошибки загрузки модулей. Предупреждать пользователя заранее и просить перезагрузить окно после переноса — вместо того чтобы «чинить» несуществующую поломку.

## 🔴 Эффект «только при старте» с зависимостями `[]` выполняется на КАЖДОЕ монтирование — в dev это каждая горячая перезагрузка (v1.2.436, 2026-09-09)

**Симптом (реальная жалоба)**: «постоянно выкидывает в ЦентрЧатов, очень часто, с озона, я сам не переходил» — активная вкладка сама переключалась на нативную.

**Корень**: в `useAppBootstrap.js` загрузка списка мессенджеров БЕЗУСЛОВНО ставила активной вкладку `NATIVE_CC_ID`. Комментарий говорил «на старте» (v1.2.399), но пустой список зависимостей `[]` означает «один раз за МОНТИРОВАНИЕ», а НЕ «один раз за жизнь приложения». В режиме разработки любая правка файла вызывает горячую перезагрузку → дерево пересобирается → эффект выполняется снова → выбор пользователя стирается.

**Как увидеть в журнале (подпись)**: `messengers:load` встречается несколько раз за сеанс, и каждому лишнему разу за ~1 секунду предшествует `dev-request … /src/App.jsx?t=<метка>` (перезапрос с меткой времени = горячая перезагрузка). Реальные числа: 6 загрузок за сеанс, 5 из них — за 70 секунд правок кода; в полчаса без правок — ни одной.

**Правила**:
1. Стартовая установка того, что потом МЕНЯЕТ ПОЛЬЗОВАТЕЛЬ (активная вкладка, открытый чат, позиция прокрутки, ширина панели), обязана быть **условной**: «поставить, только если ещё не выбрано». Безусловная установка = отбор выбора при каждом монтировании.
2. Текущее значение состояния для такой проверки читать через функцию-обновитель `setX(prev => …)` — дока React (`useState`): обновитель получает актуальное значение и обязан быть чистым. Так не нужно добавлять зависимость в эффект.
3. Не доверять комментарию «на старте» — смотреть список зависимостей эффекта.
4. Запасные пути (`catch`, «нет `window.api`») подчиняются тому же правилу: в `useAppBootstrap` их два, и оба тоже сбрасывали вкладку — причём шапка файла прямо предупреждала «Защита от HMR (window.api может быть undefined)», т.е. запасной путь и есть путь горячей перезагрузки.
5. Для пользователя, который работает в режиме разработки (а он так и работает), любая наша правка файла = пересборка его интерфейса. Нельзя считать «монтирование бывает только один раз».

**Где живёт решение**: чистая функция `pickActiveTabId` в [shared/activeTabChoice.js](../../shared/activeTabChoice.js) (вынесена в `shared/`, т.к. renderer-бюджет `src/` был на исходе) + тест-ловушка [activeTabChoice.vitest.js](../../src/__tests__/activeTabChoice.vitest.js) «повторная загрузка НЕ отбирает вкладку».

**Статус**: фикс внесён, тесты зелёные, **ожидает подтверждения пользователем** в работе.

## 🟡 webview.loadURL() — это Promise: ERR_ABORTED при редиректе не ловится sync try/catch (v1.2.350)

**Симптом**: после клика по виджету Ozon (переключение раздела) в журнал падал `[ERROR] Error occurred in handler for 'GUEST_VIEW_MANAGER_CALL': ERR_ABORTED (-3) loading '.../app/messenger'` + `[R:ERROR] renderer-unhandled-rejection`. Раздел при этом открывался нормально.

**Две причины**:
1. **Ozon ВСЕГДА переадресует** `/app/messenger` → `/app/messenger?group=customers_v2`. Исходная навигация отменяется с `ERR_ABORTED (-3)` — это НОРМА для редиректа (и для быстрого повторного `loadURL`, когда новая навигация вытесняет старую).
2. **`<webview>.loadURL()` возвращает Promise**, который на `ERR_ABORTED` **отклоняется**. Код оборачивал вызов в СИНХРОННЫЙ `try/catch` — он async-отказ НЕ ловит → отказ всплывает как `renderer-unhandled-rejection`.

**Решение (v1.2.350)**: (1) `.catch` на Promise от `loadURL`; `ERR_ABORTED`/`-3` глотать тихо, прочее — в лог WARN. (2) Вести сразу на конечный URL редиректа (`?group=customers_v2`) → отмены не будет вовсе.

**Ключевой урок**: `loadURL`/`reload`/`loadFile` у `<webview>` — **асинхронные (Promise)**. Ошибку навигации (особенно безобидный `ERR_ABORTED -3` при редиректе/вытеснении) ловить через `.catch()`, а НЕ через `try/catch` вокруг вызова. Если сайт всегда редиректит на URL с query — грузить сразу конечный URL.

## 🟡 Ozon reload «Отзывов»: в КОДЕ включён, в features написано «убран» — доверяй КОДУ + правь условие точечно (v1.2.396)

**Симптом**: правил ускорение reload «Вопросов» в [App.jsx:850](../../src/App.jsx). Опирался на features v1.2.390 («убрана авто-перезагрузка страницы отзывов») и переписал условие `(bgI === 0 || bgI === 2) ? 180000 : 0` → `bgI === 0 ? 60000 : 0`. Так СЛУЧАЙНО выключил reload «Отзывов»(2) — которого по доке «не было», а в коде он БЫЛ (добавлен v1.2.383, комментарий прямо в строке: «и Отзывы(2) — база _rPrev персистится»).

**Корень**: рассинхрон память↔код. features v1.2.390 утверждал «reviews reload убран», но в реальном коде HEAD стоял `(bgI === 0 || bgI === 2) ? 180000` — reviews reload РАБОТАЛ. Правило проекта (CLAUDE.md «Конфликт: память vs код») — доверять КОДУ. Я доверился доке → задел чужое поведение.

**Решение**: (1) перед правкой условия — `git show HEAD:src/App.jsx | grep` РЕАЛЬНОЙ строки, а не память/доку; (2) менять ТОЧЕЧНО, сохраняя ветки, которых задача не касается: `bgI === 0 ? 60000 : (bgI === 2 ? 180000 : 0)`; (3) после — сверить `git diff`, что задета ТОЛЬКО нужная ветка.

**Урок**: правка ОДНОГО значения в общем тернарном условии (`a || b ? X : Y`) легко меняет поведение ВСЕХ его веток. Всегда проверять по `git diff`, что не задел соседнюю ветку. Родственное — [[decisions]] ADR-038 (кто ведёт счётчики Ozon).

## 🟡 `console.log` из preload-УТИЛИТЫ webview НЕ попадает в `chatcenter.log` (v1.2.393)

**Симптом**: добавил временный лог `console.log('__CC_DIAG__unread_vk …')` внутрь `countUnreadVK` ([unreadCounters.js](../../main/preloads/utils/unreadCounters.js)), перезапустил — в журнале строки НЕТ (и никогда не было аналогичного давнего `__CC_DIAG__unread_max` из `countUnreadMAX`). При этом `vk-src` из `vk.hook.js` в журнал попадает исправно.

**Причина (по коду + журналу 2026-09-03)**: webview-логгер перехватывает `console` только из **главного мира** страницы (туда инъектится `*.hook.js` через `<script>`). `unreadCounters.js` подключается в **preload-мире** webview (`monitor.preload.cjs` → `require('./utils/unreadCounters')`) — его `console.log` идёт в отдельный контекст и в `chatcenter.log` НЕ пишется. Отсюда «немая» диагностика: строки нет, хотя код выполняется.

**Решение / правило**: диагностику счётчиков/логики из preload-мира выводить **не** через `console.log`, а:
- из ГЛАВНОГО мира — внутри `*.hook.js` (как `vk-src` → виден как `[ВКонтакте] debug: …`), либо
- из renderer — через `window.api?.send('app:log', {level, message})`.

## 🟡 Базовая линия сторожа живёт в контексте страницы → перезагрузка её теряет; хук-файл нельзя «разбить» (v1.2.371)

**Симптом.** Фоновая слежка Ozon за вопросами: после перезагрузки страницы (или перезапуска приложения) фон либо пропускал новые вопросы (считал их «старыми» = базовая линия), либо слал повторно.

**Корень.** «Базовая линия» (набор отпечатков уже-виденных элементов, чтобы слать только новые) хранилась в переменной внутри страницы (`_qPrev`). Перезагрузка = новый контекст страницы → переменная сброшена → сторож делает НОВУЮ «фотографию», текущие элементы считает старыми. **Решение (v1.2.371).** Персистить базовую линию в `localStorage` (переживает перезагрузку): `_loadSeen(key)` при входе, `_saveSeen(key, cur)` после скана. После перезагрузки сторож помнит, о чём уже уведомлял, и шлёт только новое. Пусто → первый запуск = базовая линия без шторма. **Осторожно**: меняет поведение старта — шлются элементы, новые С МОМЕНТА последнего сохранения (для низкочастотных «вопросов» ок; для «сообщений» персист НЕ включали — риск «ночной стены»).

**Ключевой урок №2 (разгрузка).** Хук мессенджера впрыскивается как ОДИН самодостаточный файл (`app:read-hook` читает один файл, `executeJavaScript` его выполняет) → «разбить на модули» под лимит строк НЕЛЬЗЯ (импортов нет). Разгружать = удалять отработавшую диагностику/разведку, а не выносить в отдельные файлы.

## 🟡 ВАЖНОЕ: history.pushState override НЕ работает из preload (context isolation) (v0.60.0)

**Ключевой урок**: В WebView с context isolation НЕЛЬЗЯ переопределить глобальные объекты main world из preload. `window`, `document`, `history`, `Notification` — все изолированы. Для перехвата используй: (1) `executeJavaScript` (выполняется в main world), (2) polling, (3) `console.log` канал.

## 🔴 КРИТИЧЕСКОЕ: CSS-анимация `.fade-out` вызывает мигание при смене классов (v0.60.4 → v0.60.5)

### ❌ При dismiss ribbon мигает (показывается на 1 кадр перед исчезновением)

**Симптом**: Нажатие "Прочитано" или закрытие → ribbon исчезает → мигает обратно → исчезает снова.

**Причина**: CSS `animation: fadeSlide 250ms forwards` держит opacity=0 через `forwards` fill mode. Но `el.classList.remove('fade-out')` УБИРАЕТ анимацию → opacity МГНОВЕННО возвращается к исходному значению (1) на 1 кадр → затем `classList.add('collapsing')` ставит opacity:0 снова.

1. `el.style.animation = 'none'` — отменить slideIn
2. `el.style.opacity = '1'` — зафиксировать текущее состояние
3. `void el.offsetHeight` — force reflow
4. `el.style.transition = 'opacity 250ms...'` + `el.style.opacity = '0'` — fade
5. `setTimeout(260)` → `el.style.height = '0'` — collapse
6. `setTimeout(210)` → `el.remove()` — удалить

**Ключевой урок**: НИКОГДА не используй `classList.remove()` для CSS-анимации с `forwards` fill mode, если после этого нужно продолжить анимацию. `forwards` держит конечное состояние ТОЛЬКО пока класс присутствует. При удалении класса — мгновенный откат. Используй inline `style.transition` + inline `style.opacity` для многоэтапных dismiss-анимаций.

**Причина**: Regex `/^[\u{1F000}-\u{1FFFF}\u{2600}-\u{27BF}...]+$/u` слишком узкий. Не покрывает: ❤ (U+2764), ❤️‍🔥 (ZWJ sequence), многие символы из Misc Symbols, Dingbats, Variation Selectors. Также `naturalWidth` для img может быть 0 если изображение ещё загружается.

**Решение (v0.61.2)**: Вместо whitelist Unicode ranges — blacklist: `!/[a-zA-Zа-яА-Я0-9]/.test(t)`. Текст <= 30 символов без букв и цифр = эмодзи. Для img: дополнительно проверяем `style.width`, `style.height`, `getAttribute('width')`.

**Ключевой урок**: Emoji regex — ловушка. Unicode постоянно расширяется (ZWJ sequences, skin tones, flags). Вместо whitelist ranges лучше использовать blacklist (нет букв/цифр = эмодзи). Также DOM-элементы img могут иметь naturalWidth=0 до полной загрузки.

## 🔴 КРИТИЧЕСКОЕ: Анимированный dismiss + FIFO = deadlock (v0.60.5-0.60.6 → v0.60.7)

### ❌ Ribbon зависают при быстром потоке (10+ сообщений)

**Симптом**: При 10+ сообщениях подряд ribbon зависают, не закрываются кнопками, пустые места в стеке.

**Причина**: `dismissItem()` удаляет элемент из `items` Map только через 520мс (fade 250мс + пауза 80мс + collapse 180мс). Когда приходит 7-й ribbon, `addNotification` проверяет `while (items.size >= MAX_ITEMS)` и вызывает `dismissItem()` на самый старый. Но `dismissItem` проверяет `if (item.dismissing) return` — элемент уже в процессе dismiss → `items.size` НЕ уменьшается → бесконечный цикл `while`.

**Решение (v0.60.7)**: Отдельная функция `forceRemoveItem(id)` для FIFO вытеснения — мгновенное `el.remove() + items.delete(id)` без анимации. `dismissItem()` используется только для пользовательского dismiss (клик "Прочитано", таймер).

**Ключевой урок**: Если `dismissItem` асинхронный (с анимацией), НЕЛЬЗЯ использовать его в синхронном цикле `while (size >= max)`. Асинхронное удаление не уменьшает коллекцию мгновенно → deadlock. Для FIFO вытеснения всегда используй синхронное удаление.

## 🔴 SW-«сторож» на уровне сессии убивает ServiceWorker МАКС по кругу → 429-шторм → ЧЁРНЫЙ ЭКРАН (v1.2.417, 2026-09-07)
